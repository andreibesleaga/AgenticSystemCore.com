1. Terms of the specification (spec/00 §0.2)

  • Bundle — one directory tree of Markdown items plus exactly one agsc.config.json; the unit of publication and of conformance. (AGSC-00-04)
  • Item — one .md file with YAML frontmatter whose type is one of concept, episode, procedure, lesson, cluster, gate. "Item" is a term of this specification only; no common superclass exists in the ontology (§05). (AGSC-00-05)
  • Concept (with a kind qualifier), Episode, Procedure, Lesson, Cluster, Gate are the six item types. Link, Source, Proposal, Review, Bundle, Harness complete the ubiquitous language; Proposal and Review have no file (they are a forge pull request and its verified[] evidence), Source is an inline sources[] entry, and a Harness is generated output only. (AGSC-00-06)
  • NOW is generated context, never an item and never hand-edited. (AGSC-00-07)
  • Card, page, deck and note are UI or import vocabulary; they MUST NOT appear as a type, a schema key or an ontology term. (AGSC-00-08)
  • (added at rc.4) Agent lane and live board complete the language for Mode 5. An agent lane is the OPTIONAL, configured capability by which a model-driven or programmatic agent creates, edits, reviews and updates items non-deterministically — always as Proposals, never as writes (AGSC-01-36, AGSC-08-28…30). A live board is a Bundle used as the shared working memory and pull-based task board of people and agents, local or remote: work is pulled by whoever claims a task, at most max_claims at a time, until the board is done (AGSC-10-16…18). The name says what it is — a board that is live, shared and always current; its operating discipline is Kanban's pull with a work-in-progress limit, and the blackboard architectural pattern (Hayes-Roth 1985, Nii 1986 — docs/RELATED-WORK.md) is its lineage (named Blackboard on 2026-09-17 and Kanban on 2026-09-18; live board on 2026-09-18). Neither adds a type, an item key or an ontology term; both are realised entirely with the objects §0.2 already names. (AGSC-00-19)
  • (added at rc.4) Declared scope by version. The whole of this specification's scope is named here with the version at which each part becomes normative, so that a reader of any version sees the whole and a conforming tool never claims more than its version specifies. 1.0 (normative in this document): the Bundle and the six item types (§1, §2), the fourteen Links (§3), canonical forms (§4), the graph (§5), the surfaces (§6), composition and the Harness (§7), governance with the agent lane (§8), conformance (§9), Levels 0–3, project mode and Mode 5 (§10), the boundary with federation, the plugin contract, visibility, the declaration-only surfaces solid and a2a-card, the responder surface served by an MCP transport (AGSC-11-21), retirement and tombstones (§11). 1.1 (MINOR, AGSC-00-14 — keys, values and vectors added, nothing removed): the memory:// resolver (AGSC-05-04a), build.rdfxml (AGSC-01-18), build.feed together with the pinned bytes of /feed.xml (AGSC-06-01; both reserved at rc.5, because no 1.0 rule pins a feed's bytes), a registry for extension keys in place of the x-<vendor>-<key> namespace (docs/SPEC.md §8(2)), an order for a Level's vector-area set (AGSC-10-15), the .diagram source grammar together with the compiled bytes it produces (AGSC-01-07, implementation-defined at 1.x and added to this list at rc.5), a per-chunk abstract and a tabular chunk index (AGSC-06-29), the typed cross-node Link peer-ref, contribute[].repository and contribute[].branch so that a node states where its source files live instead of a writer inferring it from a contribution endpoint (AGSC-11-14, added to this list at rc.6, 2026-09-22), weighted Links through the reserved item key weights, model-routing declarations through the reserved configuration name routing, and an executable Harness through the reserved compose --emit target executable together with the optimisation step that produces it, which runs after Step 5 and is verdict-neutral (all three reserved at rc.6 and stated in full in AGSC-00-25), a registered short relation if IANA grants one, the agsc-profile-encrypted and signatures profiles, the incremental build and the memory pack, language variants — <slug>.<lang>.md files beside a primary, the route /<type-plural>/<slug>/<lang>/, hreflang alternates and the shared-Links check (AGSC-01-13, AGSC-01-13a; 2. The fourteen Link keys (AGSC-03-01)

related · broader · narrower · uses · requires · excludes · derived-from · contradicts · supersedes · implements · verifies · covers · blocked-by · decided-by

Core nine carry composition semantics (spec/03 §3.5); the Mode-2 five (implements, verifies, covers, blocked-by, decided-by) are navigational and provenance edges. Inverses are computed, never authored (spec/03 §3.2).

4. Boundary vocabulary (spec/11)

  • Surface — an agent-facing entry a node serves and declares: llms-txt, chunks, mcp, webmcp, a2a-card, solid, responder (AGSC-11-16).
  • Access class — what a reader needs before invoking a surface: none, consent, credential (AGSC-11-16).
  • Visibility — public or restricted (AGSC-11-20); the discovery document is readable at both.
  • Contribute mode — pr, channel or form (AGSC-11-14): where a proposal from anyone goes.
  • Peer — another node named by its canonical well-known URL (AGSC-11-06); checked mutually, never fetched at build.
  • Walk — a client-side traversal of peers bounded by hop_limit, fan_out and max_requests (AGSC-11-10).
  • Origin marking — every peer-derived result carries trust: untrusted and the peer Bundle IRI (AGSC-11-11).
  • Tombstone — the state of a node that stopped publishing: a valid link set with agsc-tombstone (AGSC-11-23).
  • Retired — an item status that keeps the IRI and page and leaves every export (AGSC-11-22).
  • Plugin contract — declare · pin · inherit · prove (AGSC-11-16…19).
