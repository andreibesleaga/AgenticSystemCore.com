AGSC-06 — Published surfaces: routes, discovery files, llms.txt

SummaryEverything a node publishes: the fixed route set, the discovery document, llms.txt, the chunk export, the JSON-LD context, headers and budgets.

Status of this document

Specification 1.0.0-rc.4, a release candidate tagged on 2026-09-18. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no body has endorsed it. Released sections are immutable; a correction ships as a new version.

In plain language

Routes. A writer emits a fixed set of pages and files — item pages, clusters, tags, search, NOW, compose, skills, specs, the graph files, llms.txt, sitemap, robots, the ledger, the chunk export, the context file, boards when tasks exist — and nothing else.

The discovery file. /.well-known/knowledge-linkset is an RFC 9264 link set: one document that points at every machine artefact with its SHA-256 digest, the spec version, counts, the ledger head, peers, surfaces and contribution targets. Pages point at it with the standard describedby relation; the well-known name and the profile identifier are requested from IANA through the Internet-Draft. The file can also carry optional links to related systems — an llms.txt file, an agent card, a server card, a memory or ontology endpoint — using standard relations only.

llms.txt. The agent-facing text file has a fixed byte layout — a provenance header, the title, the description, one section per cluster with one line per item — so two tools produce the same file.

The chunk export. /chunks.jsonl is the Bundle pre-split for agents: one line per chunk, cut at headings outside code fences and at a size bound, with a stable id, the text, provenance, licence and terms, and a digest. No embeddings.

Headers. No third-party scripts, no beacons; strict security headers; public artefacts readable cross-origin.

This box explains; the rules below decide. New to the notation? See how to read the specification.

6.1 Route set

  • AGSC-06-01 A writer MUST emit exactly this route set into build.out (default www/): /; /concepts/ and /concepts/<slug>/, plus /<type-plural>/<slug>/<lang>/ for every language variant (AGSC-01-13); /procedures/, /lessons/, /episodes/, /gates/ with their item pages; /clusters/ and /clusters/<slug>/; /tags/<tag>/; /search/ with /search.json, plus /search-<nn>.json shards and /<route>/page-<n>/ index pages above the bounds of AGSC-06-21; /now/ and /now.md; /compose/; /skills/, /skills/index.json, /skills/<cluster>/SKILL.md; /specs/ and /specs/agentic-knowledge/, plus /specs/mcp/ when the mcp surface is declared (AGSC-11-16) (the published specification of the AGSC-06-07 profile URI, the 303 target of the w3id profile/agentic-knowledge rule, which MUST carry an anchor #link-relations and one #rel-<name> anchor per AGSC-06-10 extension relation so that every extension relation URI dereferences to its documentation, RFC 8288 §2.1.2); /ns/ and its vocabulary files; /about/; /legal/; /changelog/; /graph.jsonld, /graph.ttl and /graph.nq; /pages/<slug>.md and /pages/<slug>.jsonld; /attachments/<slug>/<file> for every attachment an item names (AGSC-02-98; the served bytes are the hashed bytes of AGSC-05-29 — AR2-23); /llms.txt and /llms-full.txt; /sitemap.xml; /robots.txt; /.well-known/tdmrep.json; /feed.xml; /ledger.jsonl; /chunks.jsonl and its /chunks-<nn>.jsonl shards (AGSC-06-26/31); /ns/context.jsonld (AGSC-06-32); /boards/index.json and /boards/<cluster-slug>.json when the Bundle holds at least one task item (AGSC-10-13); optionally /graph/fragments/** with /graph/fragments/index.json (AGSC-06-33); /.well-known/knowledge-linkset; /.well-known/security.txt; /404.html; _headers; _redirects.

    /ledger.jsonl is the derived ledger of §08, published so that a reader can recompute the chain offline (AGSC-08-23) and so that the rel#ledger link of AGSC-06-10 has a target. /search/ and /search.json are unconditional (AGSC-06-16 MUSTs the index); /feed.xml is emitted only when build.feed is true (default true) — the other conditional routes are the shards and index pages of AGSC-06-21/06-31 (by size), /boards/** (by the presence of a task), /specs/mcp/ (only when the mcp surface is declared, AGSC-11-16), /.well-known/agent-card.json (only under AGSC-06-34; /graph.rdf is reserved, D82 Q21) and the optional /graph/fragments/** (AGSC-06-33); no other route is conditional.

    SECURITY.md, CODE_OF_CONDUCT.md, CITATION.cff, CONTRIBUTING.md, GOVERNANCE.md and the REUSE layout are repository files, not routes (PRD-047); only security.txt is published, at its RFC 9116 location above. [PRD-011 ← R36, audit/D §5, V2-05/06/07]

  • AGSC-06-02 Item pages MUST link their own /pages/<slug>.md and .jsonld. An empty type folder MUST be omitted from navigation but MUST still resolve. [audit/D §5]
  • AGSC-06-03 The site identity is software plus registry. A reading order, a "start here" sequence, chapter structure or companion framing MUST NOT be emitted. [R23, Art. XIII]
  • AGSC-06-04 /404.html, _headers and _redirects MUST be generated, never hand-maintained; a renamed or superseded slug MUST produce a _redirects entry. [PRD-018, PRD-020]
  • AGSC-06-05 Pages MUST NOT reference a third-party origin, load a font, script or image from another host, set a cookie, use localStorage, or emit a beacon. [PRD-046 ← R52, N4]
  • AGSC-06-06 /ns/ conneg is done by the w3id .htaccess, mapping Accept to a fixed table of same-origin static targets (text/turtle → /ns/agsc.ttl, application/ld+json → /ns/context.jsonld, application/rdf+xml → /ns/agsc.rdf, else the HTML index) — plus the legacy Accept aliases application/x-turtle (→ Turtle) and application/json (→ JSON-LD), which a node MAY accept and no node need send — plus one path rule that sends /ns/<major>.<minor>.<patch>(/…)? to the immutable versioned copy of that release before any term rule can capture it (owl:versionIRI must resolve). No project-owned server code exists; /ns/<version>/… copies are immutable. [D41, D47, ADR-005]

6.2 The well-known file

  • AGSC-06-07 There MUST be exactly one discovery file, /.well-known/knowledge-linkset, served as application/linkset+json carrying the RFC 9264 §5 profile parameter profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge". Where the hosting platform cannot carry a parameter on Content-Type, the node MUST instead send the response header Link: <https://w3id.org/agentic-system-core/profile/agentic-knowledge>; rel="profile" (RFC 6906); at least one of the two MUST be present, and a reader MUST accept either. No vendor media type is defined, registered or served (D55 amends D21-final/D41/D47-note(c)). Separate manifests MUST NOT be emitted; a release MAY carry a copy named knowledge-linkset.json. agent-card.json MUST NOT be published unless the node declares it as the a2a-card surface and declares a responder surface it points at (AGSC-06-34, AGSC-11-16); a card without an endpoint is AGSC-E210. The well-known suffix knowledge-linkset (D60 supersedes D56's ordering) is pending registration under RFC 8615 through the Internet-Draft, and the Profile URI is filed under RFC 7284 (First Come First Served); the discovery link uses the already-registered relation describedby (AGSC-06-25, D82 Q3), so no relation is requested. Until the suffix is granted, a node MAY additionally serve the same document at a path it controls, linked with describedby and the linkset media type — nothing in this specification says "registered" of the suffix or the profile before the registry does. The suffix is a single point of substitution (D82 Q4): the reference implementation holds it as one constant (WELLKNOWN_SUFFIX) from which the peers[] schema pattern, the _redirects alias of AGSC-06-17, the vector paths and the rule texts derive, so a refused registration substitutes the next rung of the D60 ladder by one PATCH and a regeneration. [PRD-024 ← D55, D56, D60, RFC 9264, RFC 9727 §7.3, RFC 6906]
  • AGSC-06-08 The document is a JSON object — JCS-canonical at Level ≥2 (AGSC-04-04), valid I-JSON at Level 0 (AGSC-06-08a, AGSC-10-02) — whose sole top-level member is linkset (RFC 9264 §4.2.1); no other top-level member may be present; the linkset array holds exactly one link context object whose anchor is the Bundle IRI (AGSC-05-03), its relation-name members ordered as JSON member names (AGSC-04-05) — AR2-38. Integrity and bundle facts ride on the links as extension target attributes (RFC 9264 §4.2.4.3), whose values are ALWAYS arrays of strings. Every artefact link MUST carry digest, a Dictionary with a single member whose key is the RFC 9530 algorithm name sha-256 and whose value is an RFC 9651 §3.3.5 Byte Sequence, serialised per RFC 9651 §4.1 as sha-256=:<base64>: and carried as one string in the attribute's array, over the canonical bytes of the target. Bundle-level facts ride on the anchor's describedby link to graph.jsonld and nowhere else: agsc-spec-version (one value), agsc-generated-at (one value, an AGSC-04-10 instant derived from SOURCE_DATE_EPOCH), agsc-counts (one "<type-plural>=<n>" string per item type, in code-point order of the type name, counted over the published set — release-gated, draft and retired items excluded, AGSC-06-30 (AR2-39)), and agsc-bundle-hash (the AGSC-04 bundle hash, RFC 9530 syntax). The ledger is the link https://w3id.org/agentic-system-core/rel#ledger, carrying digest and agsc-ledger-head (one value, the lowercase hex head of the derived ledger of §08). [PRD-024 ← D55, RFC 9264, RFC 9530, RFC 9651 ← V5-3 S3-04, S3-08]

Example — the document served at /.well-known/knowledge-linkset:

{
  "linkset": [
    {
      "alternate": [ { "digest": ["sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:"], "href": "https://example.org/llms.txt", "type": "text/plain" } ],
      "anchor": "https://example.org/",
      "describedby": [ { "agsc-bundle-hash": ["sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:"], "agsc-counts": ["clusters=0","concepts=0","episodes=0","gates=0","lessons=0","procedures=0"], "agsc-generated-at": ["2026-01-01T00:00:00Z"], "agsc-spec-version": ["1.0.0-rc.3"], "digest": ["sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:"], "href": "https://example.org/graph.jsonld", "type": "application/ld+json" } ],
      "https://w3id.org/agentic-system-core/rel#graph": [ { "digest": ["sha-256=:…:"], "href": "https://example.org/graph.ttl", "type": "text/turtle" } ],
      "https://w3id.org/agentic-system-core/rel#ledger": [ { "agsc-ledger-head": ["bee9ba6593162f59dae28f42ba25fa04ea3fd65ae4f80685fb1c4ede151189ac"], "digest": ["sha-256=:…:"], "href": "https://example.org/ledger.jsonl", "type": "application/jsonl" } ],
      "license": [ { "href": "https://example.org/legal/" } ],
      "service-doc": [ { "href": "https://example.org/specs/" } ]
    }
  ]
}

The example is shown pretty-printed for review; the served bytes are JCS-canonical with exactly one trailing LF (AGSC-04-04).

  • AGSC-06-08a At Level 0 (AGSC-10-02) the document is the same link set with every digest and every agsc-* attribute of AGSC-06-08 (agsc-spec-version, agsc-generated-at, agsc-counts, agsc-bundle-hash, agsc-ledger-head) omitted — the §11 attributes (agsc-surface, agsc-surface-version, agsc-access, agsc-visibility, agsc-contribute-mode, agsc-tombstone) are Level-independent (V7-06) — a CMS export has no ledger, no graph.nq and no build instant, and Level 0 does not ask for one. At Level 2 and above every digest REQUIRED by AGSC-06-08, and every agsc-* attribute on the describedby and rel#ledger links, MUST be present. There is no structural difference between the two: linkset is the sole member at every Level. [PRD-055 ← D52(3), D55, V3-03]
  • AGSC-06-09 The linkset member MUST conform to RFC 9264: an array of link-context objects, each with anchor and relation-keyed arrays of objects carrying href and optionally type. [PRD-024, RFC 9264]
  • AGSC-06-10 Relation names MUST be either IANA-registered short names (describedby, alternate, license, service-doc, author) or extension URIs of the form https://w3id.org/agentic-system-core/rel#<name> with <name> ∈ graph, ontology, context, now, skills, ledger, peer, and (rc.3) surface, contribute, access — the first six each having a route in AGSC-06-01; peer naming another node's well-known URL for the mutual-conformance test of AGSC-10-12; surface, contribute and access defined in AGSC-11-16, AGSC-11-14 and AGSC-11-20, whose targets are surfaces, contribution endpoints and credential pages and need not be routes of this node. shapes is NOT a 1.x relation: SHACL shapes stay in the development lane (AGSC-05-24), so no /ns/shapes.ttl is published and a relation with no target would be a dangling promise. Unregistered short names MUST NOT be used. Extension target attributes (RFC 9264 §4.2.4.3) MUST use the prefix agsc- (agsc-spec-version, agsc-generated-at, agsc-counts, agsc-bundle-hash, agsc-ledger-head) so that they can never collide with the target attributes RFC 8288 §3.4 defines (hreflang, media, title, title*, type) or with those RFC 9264 §4.2.4 serialises — no registry of target attributes exists; digest is deliberately unprefixed (D82 Q12): RFC 9530 supplies its algorithm token and RFC 9651 its value syntax, and the plain name keeps RFC 9727-style link-set consumers able to read it. Every attribute value is an array of strings. Within one relation's array, link objects are ordered by href (code point), and every href is absolute — the Bundle base plus the route (V7-27). type values are advisory hints (RFC 9264 §4.2.2); application/jsonl is used for /ledger.jsonl and is deliberately unregistered — a reader MUST NOT depend on it. [audit/G §1 RFC 9264 row, RFC 8288, RFC 9530, V2-05, D55]
  • AGSC-06-11 digest values are defined once, in AGSC-06-08 (R8); agsc-ledger-head MUST be the lowercase hex hash of the last entry of the derived ledger of §08 — the head that verify --ledger recomputes and compares. A ledger always has at least the trailing build entry (AGSC-08-20a), so the head is never undefined where the attribute is required; a Level-0 node publishes no rel#ledger link and therefore no head (AGSC-06-08a). agsc-generated-at MUST derive from SOURCE_DATE_EPOCH. [PRD-005, PRD-024, D44(h) as amended by D48(1) and D55]
  • AGSC-06-12 VoID (/.well-known/void, registered 2011) is prior art for dataset discovery and is cited as complementary wherever this specification describes its discovery layer (an editorial commitment, not a conformance requirement — AR2-46). This specification emits no VoID description: graph.jsonld on the describedby link already carries the bundle-level facts (AGSC-06-08), AGSC-06-01's route set is closed, and a SHOULD-emit with no route would be unimplementable. A node that publishes a VoID description independently SHOULD link it from the link set as a second describedby link (AGSC-06-09 admits several; AGSC-06-08's "nowhere else" binds the agsc-* bundle-facts attributes to the graph.jsonld link, not the number of describedby targets — V6-B U9). [audit/G §1 VoID row ← V5-3 S3-09]
  • AGSC-06-35 (added 2026-09-17, D82) Related-system links, OPTIONAL and extensible. The discovery document MAY carry, in its one link context, links to related discovery documents and systems — an llms.txt v2 file, a VoID or DCAT description, an OKF index, an Agent2Agent Agent Card, an MCP server card, an Agentic Resource Discovery manifest, a publisher-curated LLM context file, an agent-memory, ontology, knowledge-graph or SPARQL endpoint, a runtime or architecture registry — so that any agentic-AI, knowledge, memory or ontology system that this node relates to can be reached from it, and so that new ones can be added without a change to this specification. Such links use IANA-registered relations only, chosen by meaning: describedby (the target describes this node), alternate (the same knowledge in another representation), related (a related resource), service-desc, service-doc and service-meta (an interface this node exposes or points at), collection and item (containment). Each MUST carry type and MAY carry profile (RFC 6906) and title. They are configured in agsc.config.json as related[]{rel, href, type, profile?, title?} (AGSC-01-18; rel from the list above, href absolute https:), emitted in href order within each relation (AGSC-06-10), and never derived from content. A reader MUST ignore a related-system link it does not understand; no related-system link affects conformance, any digest, the peer check or the walk (AGSC-11-10 follows rel#peer only), and none is ever required at any Level. An unregistered short name (ard, llm-context, …) MUST NOT be used until IANA registers it — a MINOR adds it then — and a relation not in the list above is AGSC-E209. [D82, R60, AR2-01/02/52]

6.3 llms.txt

  • AGSC-06-13 (amended at rc.3) /llms.txt MUST begin with a single H1 (the Bundle title), then the provenance header of AGSC-06-15 as an HTML comment — a profile of llms.txt v2 (AR2-02) — followed by one blockquote summary, then H2 sections whose bodies are link lists - [title](url): one-line description. An Optional H2 section MAY hold lower-priority links. [audit/G §1 llms.txt row]
  • AGSC-06-13a (added at rc.3) Byte layout of /llms.txt and /llms-full.txt. The convention fixes no grammar, so this specification fixes one, and a vector proves it. Both files are UTF-8, NFC, LF-terminated, one trailing LF (AGSC-04-07), and consist of these blocks in this order, separated by exactly one blank line and by nothing else: (1) # followed by the Bundle title — first, so the file is a profile of llms.txt v2 (2026-08-10), whose only required element is the leading H1 (AR2-02); (2) the provenance header of AGSC-06-15, as an HTML comment block whose lines are <!-- agsc:provenance, then bundle: <Bundle IRI>, license: <bundle.license_prose>, terms: <Content Use Terms identifier>, spec_version: <value>, generated_at: <AGSC-04-10 instant>, then -->; (3) > followed by the Bundle description on a single line, newlines in the source replaced by a single space; (4) zero or more section blocks, each ## plus the cluster title, one blank line, then one link line per item whose primary cluster (the first of clusters[]) is that cluster — an item appears exactly once — ordered by slug: - [ title ]( absolute item IRI ): the item description, or the title again when the item has no description; (5) the ## Optional section is NOT emitted at 1.x (reserved). Section blocks are ordered by cluster slug; items with no cluster go in a final section titled Other; a type: cluster item has no link line of its own (its section is its entry) and a cluster with no primary member emits no section (V7-07/08). No other line may appear. /llms-full.txt is identical through block (4), and then, for each item in the same order, one block of three parts with no blank line inside it — ## plus the item title, a line <!-- agsc:item <item IRI> -->, and the item body (ending in exactly one LF) fenced exactly as ```text agsc-content … ``` (AGSC-06-15). Retired and draft items appear in neither file (AGSC-06-30). Vector disc-0006. [V6-B B2, D67 B2, PRD-060]
  • AGSC-06-14 Every published item MUST be reachable from /llms.txt, directly or through a listed cluster section. /llms-full.txt carries the same index plus item bodies. [PRD-025 ← R33]
  • AGSC-06-15 Both files MUST carry, immediately after the H1, the fixed provenance header naming the Bundle IRI, the licence bundle.license_prose (whose default is LicenseRef-AgenticSystemCore-Content-Use-1.0, AGSC-01-18), the Content Use Terms identifier of AGSC-06-18 and the build instant, in the byte layout of AGSC-06-13a, and MUST fence every quoted body as ```text agsc-content so prose is presented as data, not instruction. [NFR-07 ← N9, ADR-001]

6.4 Machine surfaces and headers

  • AGSC-06-16 search.json MUST be a prebuilt inverted index {terms:{token:[docIndex…]}, docs:[{slug,title,description,cluster}]} requiring no runtime dependency. docs[] MUST be ordered by slug, each posting list MUST be ascending docIndex values without repetition, and the terms member names MUST be ordered as JSON member names per AGSC-04-05. Tokens are produced by AGSC-06-23 and by nothing else. An item with no clusters[] omits the cluster member, and an item with no description omits description; a member is never emitted as the empty string, so search.json stays a function of the authored keys. [PRD-014 ← D19, G15, D48(3)]
  • AGSC-06-23 Tokenizer (normative). For each item the tokenizer input is, in this order, title, description, every tags value and the body with fenced code blocks removed. The input MUST be NFC-normalized, then ASCII-lower-cased (only U+0041–U+005A are mapped; no locale casing, no case folding of non-ASCII), then split at every run of characters that are not token characters. A token character is [a-z0-9] or a character whose Unicode General_Category is L* (any letter), Nd (decimal digit) or M* (combining mark, so Devanagari and Thai words are not split); every other character — including No/Nl forms such as ² and Ⅷ, and Lo-adjacent symbols — is a boundary. Non-ASCII letters and digits are kept code-point-wise and never transliterated. The General_Category table is that of the Unicode version pinned by AGSC-04-22 (16.0.0 at rc.3); a port using another version MUST state it in its conformance claim, since that is the only remaining source of divergence. A token shorter than 2 Unicode code points MUST be dropped (AGSC-02-24). There is no stemming, no stop-word list, no synonym expansion and no n-gram: two conforming engines therefore emit byte-identical search.json. [PRD-014, NFR-04 ← D48(4)]
  • AGSC-06-17 _headers MUST set Content-Type: text/markdown; charset=utf-8; variant=GFM for /pages/*.md, Content-Type: application/linkset+json; profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge" for /.well-known/knowledge-linkset — or the header fallback of AGSC-06-07 (M13) — and a default-src 'none' policy with script-src 'self'. _redirects MUST carry /.well-known/agentic-knowledge → 301 → /.well-known/knowledge-linkset (D60), and this alias MUST be present until the last 0.0.x consumer is retired. [PRD-020, D40, D60, audit/G §1 RFC 7763 row]
  • AGSC-06-18 One licence policy is expressed in exactly three machine-readable dialects at 1.x, and no more: the AI-usage signals of robots.txt (RFC 9309); the TDMRep policy at /.well-known/tdmrep.json (the TDM Reservation Protocol well-known location, and the only route that carries it — the duplicate copy at /tdmrep.json is not emitted); and the schema:license/schema:usageInfo members of the JSON-LD views together with llms.txt. rsl.xml and the aipref Content-Usage field are not emitted at 1.x, and no rule, route or claim may assert them. A policy divergence between any two of the three dialects MUST fail the build. Every prose-carrying export MUST embed the Content Use Terms, and a build omitting them MUST fail. The Content Use Terms identifier is the constant LicenseRef-AgenticSystemCore-Content-Use-1.0: it names the terms every export carries, independently of bundle.license_prose, which names the licence of the prose itself and may differ (a CC-BY-4.0 Bundle still ships under the Content Use Terms), so license and terms are two members with two meanings even when their strings coincide. The Content Use Terms text is published at /legal/ (AGSC-06-01) and shipped as LICENSE-CONTENT at the repository root (AGSC-01-26); its wording is an owner decision outside this specification (AR2-58, owner question Q18) and a distribution without it is incomplete. [PRD-019 ← R39, D06, D39 ← V5-3 S3-10, S3-37]
  • AGSC-06-19 sitemap.xml MUST list every published route with lastmod from the build instant, ordered by URL. Schema.org JSON-LD (TechArticle, DefinedTerm, Dataset) MUST be embedded in item and index pages. [PRD-020 ← R41, R42]
  • AGSC-06-20 Generated HTML MUST meet WCAG 2.2 AA — semantics, keyboard operability, contrast, and alt text from the diagram's alt key. [NFR-08 ← N10]
  • AGSC-06-21 Budgets are normative and MUST fail the build when exceeded: ≤100 KB per HTML page; ≤1 KB of search.json per published item and ≤500 KB absolute at or below 500 items; ≤60 s build per 500 items (external page requests are already impossible under AGSC-06-05 — R20). Above 500 items a writer MUST shard the index as /search-<nn>.json (<nn> zero-padded from 01, in slug order) with /search.json as the manifest {shards:[…], docs_total} (and /chunks.jsonl sharded on the same trigger and in the same shape, AGSC-06-31), and MUST paginate any index route carrying more than 500 entries as /<route>/page-<n>/ (<n> from 2; page 1 is the route itself). The budgets are therefore per-scale, not absolute, and a 5,000-item Bundle conforms. Exceeding a budget that no sharding rule relieves MUST fail the build. [NFR-06 ← N8, V5-3 S3-05/S3-30]
  • AGSC-06-22 /now/ and /now.md MUST be generated from stored state only — counts, last build, stale items, open Lessons, monthly spend — never hand-edited. A section whose input is absent MUST be omitted, not guessed. [PRD-015 ← R29, D44(a), G16]
  • AGSC-06-24 /about/ MUST include a "Quickstart" section with one ≤10-line path per persona P0–P11 (P0 first: the three commands), generated from a template so it cannot drift from the verb set. /about/ and the Internet-Draft's Security Considerations MUST both carry the AGSC-08-19 honest-limit statement verbatim. [PRD-052 ← D32(6), R56, V4-A A-73]
  • AGSC-06-25 (amended 2026-09-17, D82 Q3) A writer (Level 2 and above) MUST emit, in the <head> of every generated HTML page, <link rel="describedby" href="/.well-known/knowledge-linkset" type="application/linkset+json">, and MAY additionally send the equivalent Link: </.well-known/knowledge-linkset>; rel="describedby"; type="application/linkset+json" response header (AGSC-11-05). A Level-0 publisher SHOULD do the same, so that a CMS or wiki export that cannot inject a <head> element still claims Level 0 (AGSC-10-02). describedby is the IANA-registered relation — registered by the W3C POWDER Recommendation (POWDER-DR §4.1.4, 2009); RFC 6892 registers its inverse describes (corrected 2026-09-18, D88: the draft of D82 Q3 credited RFC 6892) — whose meaning — "the target describes the context" — is exactly this link's; what kind of description is said by the target's media type and by the profile URI (AGSC-06-07), never by a new relation name. A page may carry several describedby links (llms.txt v2 uses the same relation for its context file): a reader selects this one by type="application/linkset+json", and a reader that fetches it confirms the profile. No link relation is requested from IANA: the Internet-Draft registers the well-known suffix and the Profile URI only (two entries, D82 Q3 — AR2-03/73), so no extension-URI spelling and no later alias ever exist. [PRD-024 ← D55, D60, D82, RFC 6892, RFC 9264]
  • AGSC-06-34 (added at rc.3) Agent card, OPTIONAL emission. A node MAY emit /.well-known/agent-card.json only when it declares both the a2a-card and a responder surface (AGSC-11-16, AGSC-11-21): the card is the Agent2Agent 1.0 Agent Card whose interfaces point at that responder, with protocolVersion equal to the agsc-surface-version declared for a2a-card, serialised JCS-canonical (AGSC-04-05) plus one trailing LF, and it MAY carry signatures[] per A2A §8.4 (JWS over the JCS form). A node with no responder MUST NOT emit the card (AGSC-06-07). [D67 A2, D72 non-goals note, A2A 1.0 §8]

rc.3 amendment (2026-09-16, folded into AGSC-06-10 on 2026-09-16): relation names gain surface, contribute and access under the same extension-URI form (AGSC-11-14/16/20); _headers additionally carries AGSC-11-03 and AGSC-11-05.

6.5 Agent-retrieval chunk export (added at rc.3, 2026-09-16 — D67 Q67 / V-23, D71)

  • AGSC-06-26 A Level ≥ 2 writer MUST emit /chunks.jsonl: one JCS-canonical JSON object per LF-terminated line, one line per chunk, UTF-8, NFC, no blank lines, one trailing LF. The file is the Bundle's agent-retrieval export: a stable, citable, pre-split unit set with provenance, so that any agent can use the Bundle as remote memory without re-chunking, guessing boundaries or inventing identifiers. Embeddings are out of scope; the record is embedding-ready. The file is declared as the chunks surface (AGSC-11-16). [D67 Q67, PRD-061, D72 C7]
  • AGSC-06-27 Boundary rule. Chunks are cut after the AGSC-04-07 normalisation of the item body; fenced code is NOT removed (code stays in its chunk). Cut 1: at every ATX heading of level 2 or 3 (## , ### ) that lies outside any fenced code block, per CommonMark 0.31.2 (AGSC-02-20) — a ## line inside a fence is content, and setext headings are not cut points — the text before the first such heading is chunk 0 (an empty chunk 0 — a body that begins with a cut heading, or an empty body — is not emitted, V7-09), and each heading with its following text is one chunk, the heading line included. The blank line(s) immediately preceding a cut belong to neither chunk, so a chunk's text ends with exactly one LF and never begins with one. Cut 2: a chunk whose UTF-8 byte length exceeds chunks.max_bytes (AGSC-11-01; default 4096, maximum 65536) is split at the last paragraph boundary (a blank line, i.e. two consecutive LFs) at or before the bound — the chunk's byte length, excluding the separating blank line, MUST NOT exceed the bound (V7-44) — repeatedly; a single paragraph longer than the bound is split at the last LF at or before the bound, and, failing that, at the bound on a code-point boundary — only in that last case may a chunk's text end without LF and the next begin mid-line (AR2-40). No overlap. The heading is not repeated into continuation chunks. [D72 R-04]
  • AGSC-06-28 Identifier. id is the lowercase-hex SHA-256 of the UTF-8 bytes of the item IRI, then one U+0000 (NUL) byte, then the section path, then one U+0000 (NUL) byte, then the ordinal in decimal — where the section path is the AGSC-03-13 anchor of the chunk's heading (the empty string for chunk 0) and the ordinal is the zero-based index of the chunk within that section after Cut 2. Two conforming writers therefore derive identical ids from identical sources; an agent cites a chunk back as the item IRI followed by #chunk- and the first 16 hex characters of id, which a page MUST render as an in-page anchor on the chunk's heading (the top of the page for chunk 0). [V-23]
  • AGSC-06-29 Record shape. Members, all REQUIRED unless marked: digest (lowercase-hex SHA-256 of the UTF-8 bytes of text), id, iri (the item IRI), item (the slug), kind (the item type), subkind (OPTIONAL: the concept kind, present only on concepts), license (bundle.license_prose), links (the item's authored Links as an object of key → slug arrays (anchors stripped; each array in code-point order — AR2-41) in JCS order; OPTIONAL when empty), ordinal, section (the anchor; empty for chunk 0), terms (the Content Use Terms identifier of AGSC-06-18), text, title, trust (always untrusted — the value an agent MUST attach when the text re-enters a model, AGSC-08-18), type (text, or the media type of an attachment chunk, AGSC-06-30). No other member at 1.x; x-<vendor>-<key> members MAY follow (AGSC-02-05a). Lines are ordered by item slug (code point), then section (code point), then ordinal ascending numerically. [PRD-061, AGSC-11-18]
  • AGSC-06-30 Exclusions and attachments. Items with status retired (AGSC-11-22) or draft, and items held back by the releases switchboard (AGSC-01-20), are excluded — the same set that search.json and /llms.txt exclude; a cluster contributes one chunk (its description; a cluster without description contributes no chunk, V7-09). Each attachment of an item (AGSC-02-98) contributes one chunk whose type is the attachment's media type, whose text is the attachment's alt text for binary media and the file's full text for image/svg+xml and other text media, whose section is attachment-<n> (<n> the 1-based index in attachments[]) and whose ordinal is 0; a cluster's chunk has item = the cluster slug, iri = the cluster IRI, section empty and ordinal 0. The in-page anchor of AGSC-06-28 is required only for chunks that begin with a heading; every other chunk is cited at the top of its page. Peer-derived content never appears in a node's own export (AGSC-11-11). [D67 Q64, R36]
  • AGSC-06-31 Budgets: /chunks.jsonl MUST NOT exceed 8 KB per published item on average; above 500 items a writer MUST shard as /chunks-<nn>.jsonl (<nn> zero-padded from 01, each shard the lines of at most 500 items in slug order, no item split across shards) with /chunks.jsonl becoming the JCS-canonical manifest {"lines_total": <integer>, "shards": ["/chunks-01.jsonl", …]} (paths in shard order), exactly as AGSC-06-21 shards the index. [AGSC-06-21]

6.6 JSON-LD context file (added at rc.3 — D67 B2)

  • AGSC-06-32 A Level ≥ 2 writer MUST emit /ns/context.jsonld, the target of the …/rel#context link (AGSC-06-10) and of the application/ld+json branch of /ns/ negotiation (AGSC-06-06). It MUST be generated from ontology/agsc.ttl by a deterministic mapping — every asc: term becomes a term definition whose @id is its IRI, object properties carry @type @id, datatype properties carry the @type of their declared range, and — because graph.jsonld also uses external vocabularies — the prefixes dcterms, prov, rdfs, schema, skos and xsd are defined together with a typed term definition for every external property a rule of §05, §06 or §11 emits (rdfs:seeAlso as @id, the SKOS, DCTerms, PROV and schema.org properties named in AGSC-05-14…20, 05-27, 05-29, 06-18 and 11-12); no term is ever mapped to null (a null term definition, which JSON-LD 1.1 keeps as a blocked term so that it can never be used — AR2-44); @version 1.1 and @protected true are set — sorted per AGSC-04-05, and MUST round-trip: expanding graph.jsonld with it and re-compacting MUST reproduce graph.jsonld byte for byte. Released context files are immutable (AGSC-00-16); the versioned copy lives at /ns/<version>/context.jsonld. [D67 B2, AGSC-05-09]

6.7 Static query fragments (added at rc.3 — D67 A4; SHOULD, sacrificial)

  • AGSC-06-33 A Level ≥ 2 writer SHOULD emit /graph/fragments/s/<subject-hash>.nq for every distinct subject IRI and /graph/fragments/p/<predicate-hash>.nq for every distinct predicate IRI of graph.nq — each file the byte-sorted N-Quads lines sharing that term, the hash being the first 16 hex characters of the SHA-256 of the IRI — plus /graph/fragments/index.json {subjects, predicates, generated_at} — JCS-canonical, subjects and predicates arrays of file paths in code-point order. Object fragments are NOT emitted at 1.x. A writer that does not emit fragments MUST NOT emit the index. (Non-normative: a static subset of the Triple Pattern Fragments interface at the dump end of the Linked Data Fragments spectrum; counts and controls are omitted at 1.x.) [research/29 R6-O1, D72 R-08, A-17]

6.8 Dataset vocabularies — VoID and DCAT (informative, added at rc.3 DS-4, 2026-09-16)

VoID is cited as complementary prior art by AGSC-06-12 (a MUST). DCAT 3 (W3C Recommendation, 22 August 2024) is the catalogue vocabulary a publisher or an aggregator MAY use to describe a Bundle as a dataset; this specification defines no DCAT emission and no rule depends on one, so the mapping below is a courtesy to catalogue maintainers and adds no term to ontology/agsc.ttl. Where a publisher emits it, the natural mapping is: the Bundle IRI is a dcat:Dataset (and, being a skos:ConceptScheme, also the dcat:themeTaxonomy of its own catalogue record); dcterms:title/dcterms:description from site.title/content/index.md; dcterms:license from bundle.license_prose; dcterms:modified from the build instant; each machine artefact of AGSC-06-01 is a dcat:Distribution with dcat:accessURL the route, dcat:mediaType the served type and spdx:checksum the same SHA-256 the link set carries as digest; the discovery document itself is the dcat:landingPage-adjacent entry point, and the …/rel#graph targets are the distributions a triple-store consumer wants. A VoID description (void:Dataset, void:dataDump = /graph.nq, void:vocabulary = the /ns/ IRI) may sit beside it at /.well-known/void; both are optional, both point at artefacts this specification already pins, and neither is a conformance target at 1.x.
