AGSC-04 — Canonicalization and determinism

SummaryWhy two builds anywhere give the same bytes: canonical JSON, NFC text, one time format, fixed sort orders and SHA-256.

Status of this document

Specification 1.0.0-rc.6, a draft release candidate, not yet tagged. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

In plain language

The promise. Build the same Bundle twice, on two machines, with two conforming tools: every machine artefact is byte-identical. HTML pages are identical within one tool.

How. JSON is written in the canonical form of RFC 8785 (members sorted by UTF-16 code unit, no whitespace, -0 written as 0). Text is NFC-normalised before anything is sorted or hashed. Time is one instant format in UTC, taken from SOURCE_DATE_EPOCH or the last commit. Every list has a stated sort order. Hashes are SHA-256, lowercase hex.

Unicode. The vectors were generated with Unicode 16.0.0; a tool states the version it uses. A run of more than 256 combining marks after one character is refused, so hostile input cannot exhaust memory.

Why it matters. Because outputs are deterministic, a digest in the discovery document is a real integrity check, two nodes can compare notes, and a reader can rebuild a site from its source and check that nothing changed.

4.1 The determinism obligation

  • AGSC-04-01 Two builds of the same Bundle content with the same SOURCE_DATE_EPOCH MUST produce byte-identical output on every operating system and every runtime. [PRD-004]
  • AGSC-04-02 Verification is a double build into two directories followed by a recursive byte comparison; any difference is error AGSC-E602. [PRD-004]
  • AGSC-04-03 A build MUST NOT read a wall clock, resolve the network, read environment locale, or depend on filesystem enumeration order. [design]

4.2 JSON (JCS, RFC 8785)

  • AGSC-04-04 Every emitted JSON artefact — graph.jsonld, per-item .jsonld, search.json, the well-known file, dist/gate.json, ledger.jsonl entries — MUST be JCS-canonical and MUST be followed by exactly one LF. Vector files are not emitted artefacts: they are governed by AGSC-09-06, which requires JCS member order but permits pretty-printing. This rule binds at Level 2 and above (AGSC-10-04). A Level-0 publisher's JSON artefacts MUST be valid I-JSON (RFC 7493) and SHOULD be JCS-canonical, and tools/validate-wellknown --level 0 MUST NOT require canonical bytes — UTF-16 member ordering and ECMA-262 number formatting are not something a CMS export produces by accident, and Level 0 exists precisely so that it need not. [AGSC-10-02]
  • AGSC-04-05 JCS here means: UTF-8 output; no whitespace between tokens; members sorted by UTF-16 code units of the member name; numbers per ECMA-262 §7.1.12.1 (Number#toString); input restricted to I-JSON. Locale and Unicode code-point sorting MUST NOT be used: they differ from UTF-16 order for astral-plane keys. A number MUST NOT serialise as -0: ECMA-262 §7.1.12.1 renders negative zero as 0, so a producer emits 0. (amended at rc.5: the earlier sentence cited RFC 8785 erratum 7920 as its authority. That erratum — Verified, reported 2024-05-02 — in fact recommends the opposite remedy, "a JSON parser following this specification SHOULD generate an error condition … when it encounters -0"; it notes that the serialisation is lossy and addresses the parser. This specification chooses the producer-side rule instead, because I-JSON input is a precondition of AGSC-04-05 and a Bundle never authors -0.) The UTF-16 rule governs JSON member names and nothing else — every other ordering in this specification is code-point (AGSC-04-12/13), and the two differ only for astral-plane text, which reaches member names through search.json tokens (AGSC-06-23) and nowhere else. A port MUST therefore sort member names by UTF-16 code units (comparing surrogate-aware, not by rune) even where its language's default string order is by code point; vector jcs-0003 proves it. [RFC 8785]
  • AGSC-04-06 A JSON artefact that is not JCS-canonical is error AGSC-E601. [PRD-004]

4.3 Text

  • AGSC-04-07 All emitted text MUST be UTF-8 without BOM, LF-terminated, NFC-normalized, with exactly one trailing LF. Non-NFC output is AGSC-E604. [design]
  • AGSC-04-08 Slugs, keys and IRIs stay ASCII; titles, descriptions and aliases MAY be any Unicode in NFC. [design]

4.4 Time

  • AGSC-04-09 The build instant MUST come from SOURCE_DATE_EPOCH (integer seconds since the Unix epoch), defaulting to the last commit time. Where no git history exists — the drop-in flow of PRD-053 runs before git init — the default MUST be 0 (1970-01-01T00:00:00Z) with warning AGSC-E606, so the instant is always defined. A malformed value MUST exit 2 (AGSC-E603, the configuration class of AGSC-09-08); the variable MUST NOT be unset for child processes. [design]
  • AGSC-04-10 Every embedded timestamp MUST be rendered from that instant as YYYY-MM-DDTHH:MM:SSZ — UTC, seconds precision, never milliseconds, never a local offset. [design]
  • AGSC-04-11 Staleness, "last build" and NOW counts MUST all derive from the same instant (amended at rc.5: "feed dates" removed with /feed.xml). Only the refresh verb MAY read a real clock, and a clock it reads MUST NOT reach any emitted artefact: ledger ts values derive from the committer times of the git-log file (AGSC-08-20a) and from SOURCE_DATE_EPOCH for the single trailing build entry, never from a wall clock, so a refresh observation can only open an issue. [PRD-015, PRD-017]

4.5 Ordering

  • AGSC-04-12 All ordering — except the JSON member-name ordering of AGSC-04-05, which is UTF-16 code units by deliberate exception — MUST be code-point comparison of the sort key. Locale collation, case-insensitive collation and Intl comparators MUST NOT be used. [design]
  • AGSC-04-13 Explicit sort keys: items by slug; links by (key, target); tags by code point; cluster members by (order, slug) with absent order sorting last; search tokens as JSON member names per AGSC-04-05 (UTF-16 code units), never by code point; sitemap entries by URL; N-Quads lines by their serialized bytes; RDF subjects, then predicates, then objects by IRI or lexical form; JSON object members by AGSC-04-05. [design]
  • AGSC-04-14 Arrays authored by a human (tags, clusters, aliases, Link arrays) MUST retain author order in the source file and MUST be sorted only in derived artefacts, so that lint --fix never reorders meaning-bearing first entries such as the primary cluster. [design]

4.6 Hashes and the canonical RDF form

  • AGSC-04-15 graph.nq — canonical N-Quads, code-point ordered, each quad terminated by a single LF — is the hashed form of the graph. Every line of it is a quad whose fourth term, the graph name, is the Bundle IRI (AGSC-05-03): the file is one named graph, and no statement is written in the default graph. bundle.hash MUST be the lowercase hex SHA-256 of its bytes. (amended at rc.6, 2026-09-23: no rule named the graph term, and the released vectors stated both readings — graph-0001, graph-0002, graph-0004, graph-0006 and graph-0020 wrote triples in the default graph, while graph-0015 to graph-0018 and bnd-0008 wrote quads named by the Bundle IRI — so two conforming writers could emit different bytes, and therefore different bundle.hash values, for one Bundle. The newer form is pinned: it is the one the reference engine's build has always emitted, so no published fingerprint changes, and it lets a consumer load several nodes' dumps into one store without losing which node stated what. The five vectors of the other form are withdrawn and superseded by graph-0021 to graph-0025, which state the same cases with the graph term added.) [design]
  • AGSC-04-16 Because exports are blank-node-free (§05), RDFC-1.0 canonicalization degenerates to this sort. An implementation MUST scope any conformance claim to "canonical N-Quads equal to RDFC-1.0 output for blank-node-free datasets" and MUST NOT claim full RDFC-1.0. [design]
  • AGSC-04-17 Content hashes elsewhere (per-item Markdown, ontology files, skill packs) MUST be lowercase hex SHA-256 over the canonical bytes. A CIDv1 (raw, sha2-256, base32 b…) MAY additionally be emitted for graph.nq; when emitted it MUST be computed over the same canonical bytes. [design]
  • AGSC-04-18 (amended at rc.5: feed.xml removed, because no 1.0 rule pins its bytes and AGSC-06-01 no longer emits it) search.json, sitemap.xml and the well-known file MUST be reproducible from content/, agsc.config.json (every URL derives from site.base, every switch from build{}) and SOURCE_DATE_EPOCH, plus — for the well-known file's agsc-ledger-head attribute alone — the git-log file of AGSC-08-02/08-20a. No other input exists — four inputs in all. [design]

4.7 Normalization on write

  • AGSC-04-19 lint --fix MUST be idempotent: applying it twice MUST produce the same bytes as applying it once. Its normalizations are limited to line endings, NFC, trailing newline, frontmatter key order (schema order = the top-level properties order of schema/item.schema.json, then the matching oneOf branch's properties order, then unknown keys in code-point order — including inside a nested mapping, where the order is that $def's properties order — the order AGSC-02-90 emits, so lint --fix never rewrites an adopted file), and wikilink rewriting. The emitted YAML profile is fixed: block style only, two-space indentation, sequence items indented two spaces under their key, plain scalars unless the value would re-parse as another type or begins with an indicator character (then double-quoted with \ and " escapes only), one space after every :, no document markers, no trailing spaces. What it changed — and, where it only reports, what it would change — MUST be reported as a finding: a line-ending, BOM, NFC or trailing-newline normalisation under AGSC-E108 (the encoding rule that obliges it, AGSC-01-14), every other normalisation of this rule under AGSC-E506. Both are warnings, so no exit code depends on the choice; without this sentence two conforming engines reported the same file under different codes (added at rc.5: four rules oblige lint --fix and no rule said which registered code its report carries). [PRD-003, AGSC-03-12]
  • AGSC-04-20 lint --fix MUST NOT change prose, reorder authored arrays, or add, remove or infer any key. [design]

4.8 Normalization order, Unicode version and the cross-implementation obligation (added at rc.3, 2026-09-16)

  • AGSC-04-21 Order. Normalization and canonicalization do not commute, so the order is fixed: text is NFC-normalized first (AGSC-04-07), then canonicalized (AGSC-04-05). Every JSON member name MUST be NFC-normalized before it is sorted; a producer that sorts first and normalizes afterwards emits different bytes for the same input and is non-conforming. The same order governs every derived artefact: normalize, then sort, then serialize. [design]
  • AGSC-04-22 Unicode version. The vectors of tests/vectors/** were generated against Unicode 16.0.0; NFC, the General_Category classes of the tokenizer (AGSC-06-23) and the case mapping of AGSC-03-13 are those of that version. The vector set is version-stable: every character in it has identical NFC, General_Category and case-mapping properties from Unicode 15.0 through 18.0.0 (verified 2026-09-17 by recomputation and the Unicode stability policy), so a runtime on any of those versions passes the set and the pin names the generation version, not a runtime requirement. A conforming implementation MUST state the Unicode version of its runtime in its conformance claim (AGSC-09-01). A divergence that arises only from a different Unicode version, on input outside the vector set, is a documented divergence and not a conformance failure; a divergence on the vector set is a failure. [design]
  • AGSC-04-23 Combining-sequence bound. NFC is computed per starter-delimited segment, so a segment must be buffered before any of it is emitted. A conforming implementation MUST NOT buffer without bound: a starter followed by more than 256 combining marks is AGSC-E607 (a lint error naming the file and offset), never a silent truncation and never unbounded memory. [design]
  • AGSC-04-24 Cross-implementation obligation. Byte-identity across implementations is claimed for the machine artefacts — graph.jsonld, graph.ttl, graph.nq, per-item .jsonld, search.json and its shards, chunks.jsonl and its shards, ledger.jsonl, /.well-known/knowledge-linkset, /llms.txt, /llms-full.txt and the board exports — and is discharged by the expected-byte vectors that name them. The seven Harness file kinds of AGSC-07-12 carry the same obligation, discharged when the harness/ vector area is populated; until then no conformance claim may assert cross-implementation byte-identity for a Harness. (amended at rc.5: the earlier text named "the seven Harness files" as already discharged, while tests/vectors/harness/ is a declared-but-empty area and the two compose/ vectors assert harness_emitted: false only; AGSC-07-12 also defines seven file kinds, two of them one file per selected item, so "seven files" was never literally seven.) Generated HTML is byte-identical within one implementation (AGSC-04-01) and is NOT part of the cross-implementation vector set: no rule pins a Markdown renderer's output. A conformance claim MUST NOT assert cross-implementation byte-identity for HTML. [PRD-060]

4.9 The content version (added at rc.6, 2026-09-22)

  • AGSC-04-25 The content version. A Bundle has one content version, bundle_version: a short, human-readable name for the state a build published or a consumer saved, so that a reader, a citation and an imported item can all say which version of this node's content they mean. It is derived at build, never authored, never stored and never incremented by the engine — a static build keeps no state between runs, so a counter of its own could not be reproduced. Its inputs are the two the derived ledger already uses, and it therefore adds no input to a build: the git-log file of AGSC-08-20b and the build instant of AGSC-04-09.

    Derivation — the first branch that applies, where the built commit is the last element of the git-log file: 1. the tag of the built commit, when it carries one; 2. otherwise <tag>+<n>.g<hash>, where <tag> is the tag of the newest earlier element that carries one, <n> is the number of elements after that element up to and including the built commit, and <hash> is the first twelve lowercase-hexadecimal characters of the built commit's sha — a fixed width, because git's own abbreviation length depends on the clone and would make the string unreproducible; 3. otherwise, when no element carries a tag, 0.0.0+<n>.g<hash> with <n> the number of elements in the git-log file; 4. otherwise, with no git history at all — the drop-in flow AGSC-04-09 names — 0.0.0+<instant>, where <instant> is the build instant written YYYYMMDDThhmmssZ, AGSC-04-10's form with its separators removed so that the whole value stays inside the grammar below.

    The grammar is ^[A-Za-z0-9][A-Za-z0-9._+-]{0,63}$ — one line, ASCII, and safe unescaped inside a JSON string, an HTML comment and a link-set attribute value. A tag that does not match it is not a content version: the built commit is treated as untagged for this rule alone, the derivation falls to the next branch, the ledger still takes kind: release from that tag (AGSC-08-20a), and the verbs that derive the version — those that EMIT — report the value-was-defaulted warning AGSC-E506 naming the tag they could not use; lint, which reads no build fact, reports nothing here (AGSC-04-09, AGSC-04-11). (amended at rc.6, 2026-09-22: the sentence said lint reported it. lint reads no clock and no git history by design — the same decision that keeps AGSC-04-09's AGSC-E606 out of it — so a lint that reported this warning would have to start a process and read the checkout, and its output would then depend on the clone rather than on the Bundle, which is the opposite of what lint is for. The obligation moves to the verbs that already derive the version, so it stays testable and nothing is lost.)

    The version is stamped in exactly these places, and adding one is a MINOR:

    every agent-facing digestthe bundle_version: line of the provenance header (AGSC-06-13a, AGSC-06-15), which carries it into /llms.txt, /llms-full.txt, the language-model context export, every export --steer target and every AGENTS.md and SKILL.md a Harness emits (AGSC-01-29)

    (the table was amended at rc.6, 2026-09-22: it was closed at nine rows and the content-version decision asks the Harness archive name to carry the content version, which no row admitted — so a conforming engine could not do what the decision asks, and the two documents disagreed. The tenth row is that name. No published artefact gains a byte: a file name is not content, and the archive's entries are unchanged.)

    An import records where each written item came from: prov.source_version = the source's content version and prov.source_hash = the source's bundle hash, each omitted when the source publishes neither (AGSC-01-22, AGSC-08-01).

    The content version is not an input to any digest. bundle.hash is the hash of graph.nq (AGSC-04-15) and nothing here adds to it, so re-tagging unchanged content changes the published version and not the fingerprint, and changing content changes the fingerprint whether or not anyone re-tags — which is what makes the two worth publishing together. Vectors build-0014, disc-0013, disc-0015, imp-0002, compose-0016 (the archive name). [PRD-008, PRD-024, AGSC-04-09, AGSC-08-20b]
