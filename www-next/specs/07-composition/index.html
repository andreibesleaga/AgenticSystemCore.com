AGSC-07 — Composition: the closure algebra and the Harness

SummaryHow a selection of items becomes a verdict and a Harness: the five steps in their fixed order, the seven Harness files, skill packs, ports and saved architectures.

Status of this document

Specification 1.0.0-rc.6, a draft release candidate, not yet tagged. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

In plain language

Pick items, get a harness. You select items (by slug, or by re-running a saved architecture). The combiner runs five steps in a fixed order: pull in everything requires reaches (breadth-first), hide what is superseded, refuse any surviving excludes pair, warn on contradicts and missing uses, then wire ports — matching what one item produces to what another consumes.

The verdict. Valid or not, with the hidden items, the conflicts and the warnings listed. Step 5 never changes the verdict; it only adds wiring.

The Harness. A valid composition yields exactly seven kinds of file — a JSON-LD record of the selection, an AGENTS.md context file, a Structurizr model, a Mermaid diagram, an arc42 skeleton, one decision record per selected Concept and one SKILL.md per selected Procedure — byte-identical whether produced by the CLI or in the browser, and named after the selection. A runtime emitter, which is a plugin, may render those seven files for one runtime without changing them; renderings for named runtimes are planned for version 1.1. (Corrected 2026-09-24 against AGSC-07-12 and AGSC-07-18.)

Skill packs. Procedures export to SKILL.md files that can be installed into agent tool trees and imported back.

This box explains; the rules below decide. New to the notation? See how to read the specification.

7.1 Inputs

  • AGSC-07-01 A composition takes an ordered selection of item slugs and the resolved graph, and produces a verdict plus a Harness file map. It MUST NOT require a network, a key or a server. [PRD-038]
  • AGSC-07-02 (retired at rc.3, 2026-09-17: the same byte-identity claim, now stated once — merged into AGSC-07-13; the id is reserved under AGSC-00-16 and never reused.)
  • AGSC-07-03 A slug not present in the graph is AGSC-E802. A selection MUST be de-duplicated preserving first-occurrence order. [PRD-036]

7.2 The algebra, in this order

  • AGSC-07-04 Step 1 — closure. Compute the transitive closure of requires over the selection. Each added item MUST record an explanation path — the chain of (source, key, target) steps that pulled it in. The traversal MUST be breadth-first from the de-duplicated selection, expanding each frontier in code-point slug order and each item's requires targets in code-point order; the path recorded for an item is the first one discovered by that traversal (a shortest path, ties broken by the lexicographically least slug sequence). Depth-first traversal is non-conforming: it records different path[] chains for the same input, and path[] is byte-compared (PRD-038). [PRD-036]
  • AGSC-07-05 Step 2 — hiding. Remove from the result any item that a member of the result supersedes, whether that item was selected directly or added by Step 1 (formerly AGSC-03-17). A superseded item MUST NOT be re-added by a later step, appears in hidden[], and MUST NOT appear in added[] even when Step 1 had added it. [PRD-036, AGSC-03-17] (trace corrected at rc.5: the bracket cited this rule itself.)
  • AGSC-07-05a Step 2, hard-dependency guard. When an item removed by Step 2 is the requires target of an item that survives Step 2, the composition is invalid with AGSC-E802 — message form "required item superseded — select <superseding>" — naming the requiring item, the hidden target and the superseding item. Closure MUST NOT be re-run and the superseding item MUST NOT be substituted: the selection is the author's, and a hard dependency is never silently dropped. [PRD-036]
  • AGSC-07-06 Step 3 — mutex. Evaluate excludes over the surviving set. One or more surviving excludes pairs make the composition invalid; the verdict MUST name every violating pair and the explanation path of each side (AGSC-E801). [PRD-036]
  • AGSC-07-07 Step 4 — warnings. Emit the warning AGSC-E803 for every contradicts pair inside the result, and for every uses target that is not in the result (the code was registered against this rule and named by no sentence until rc.5). Warnings MUST NOT invalidate a composition. [PRD-036]
  • AGSC-07-08 (amended at rc.3) Steps MUST run exactly once each, in the order 1→5 — closure, then supersedes hiding (with the AGSC-07-05a guard), then excludes mutex, then warnings, then port wiring (AGSC-07-23). Step 5 is verdict-neutral: it reads the surviving set and writes only wiring[] and warnings, so every verdict member of AGSC-07-09 other than warnings[] is byte-identical whether or not any item carries a port, and warnings[] differs only by its AGSC-E804 entries. Closure MUST NOT be re-run after hiding, and mutex MUST NOT be evaluated before hiding: evaluating excludes over a set that still contains superseded items reverses verdicts (an item hidden at Step 2 can be one half of an excludes pair). [PRD-036]
  • AGSC-07-09 The verdict object MUST be JCS-canonical with members added[], conflicts[], warnings[], hidden[], selection[] and valid (boolean). selection[] is the surviving post-Step-2 set — the closed selection minus the hidden items — in code-point slug order; hidden[] is code-point ordered; added[] is ordered by slug; conflicts[] sort element-wise over the internally sorted pair, then by code; warnings[] sort element-wise over (source, target), then by code and key; every comparison is code-point. Each added entry carries slug and path[]; each conflicts[] entry carries code, key and pair (plus superseding for AGSC-E802); each warnings[] entry carries code, key, source and target. Input order therefore never reaches the verdict, which is why order-independence holds (formerly AGSC-07-11). [AGSC-04-04]
  • AGSC-07-10 related, broader, narrower, derived-from and mentions MUST NOT affect any step. [AGSC-03-18]
  • AGSC-07-11 (retired at rc.3, 2026-09-17: derivable: AGSC-07-09 fixes every order and says so, AGSC-07-04 fixes iteration order — merged into AGSC-07-09; the id is reserved under AGSC-00-16 and never reused.)

7.3 The Harness

  • AGSC-07-12 A valid composition MUST emit exactly these seven file kinds, and no others (two of them one file per selected item), under dist/harness/<name>/ — never under content/ (formerly AGSC-01-09) — or as an equivalent in-memory map for download, as the table below lists. [PRD-037]
FileContent
harness.jsonldselection, closure with explanation paths, links, verdict, and the content version bundle_version of the Bundle composed from (AGSC-04-25, added at rc.6) — JCS-canonical
AGENTS.mditem summaries and constraints, as context only
workspace.dslStructurizr: one container per selected Concept, relationships from Links
diagram.mmdMermaid flowchart of the same relationships, emitted as text
arc42.mdarc42 skeleton seeded from the selection
decisions/0001-<slug>.mdone MADR record per selected Concept, numbered in selection order
skills/<slug>/SKILL.mdone skill file per selected Procedure

decisions/NNNN-<slug>.md is numbered in the de-duplicated first-occurrence input order of AGSC-07-03 restricted to the survivors — the one place where input order is still meaningful; the verdict itself is order-free (AGSC-07-09). harness.jsonld is a JSON document in JCS form, not an RDF export: AGSC-05-08 and AGSC-E605 do not apply to its nested selection/closure/links/verdict objects, which carry no @id. [design]

<name> is the first sixteen lowercase-hex characters of the selection digest: the SHA-256 of the JCS form (AGSC-04-05) of the verdict's selection[] — the surviving set in code-point order (AGSC-07-09) — so a Harness is addressed by its member set alone, two different selections never share a directory, and the input order of AGSC-07-03 does not reach the name. That same digest is the selection digest the emitted files carry under AGSC-07-16. A writer MUST derive <name> from that digest and from nothing else — never from a path, a clock or a host — because the digest reaches the emitted bytes, and a name one host could compute and another could not would make AGSC-07-13's byte-identity unattainable; the directory the files are actually written into is compose --out's (AGSC-09-09) and MUST NOT reach any emitted byte. Vector compose-0015. (stated at rc.5: neither <name> nor the digest was defined by any rule of §7.3, while AGSC-07-13 requires both to be computable in a browser that has no path at all.)

  • AGSC-07-13 The algorithm MUST be identical in every host: Harness output computed in a browser MUST be byte-identical to the equivalent CLI invocation and MUST be reproducible from the graph plus the selection plus SOURCE_DATE_EPOCH. [PRD-037, PRD-038]

  • AGSC-07-13a A writer that offers the archive of AGSC-09-09's --zip MUST emit it as a ZIP container (APPNOTE.TXT 6.3.10) in the STORE profile, so that every byte of the archive is a function of the entry names, the entry bytes and the build instant, with no encoder's choices in between:

    • Entries. One entry per file and no directory entry, in code-point order of the entry name — AGSC-07-09's ordering, which is this specification's only ordering. An entry name is the file's path relative to the directory the archive packages: UTF-8, no leading /, no drive or device letter, no backslash and no .. segment (APPNOTE.TXT §4.4.17.1); a writer holding site-absolute paths drops the leading / when it forms the name. A name that is still not relative in that sense MUST be refused with AGSC-E902; a name stored twice, an entry above 4,294,967,295 bytes, a total above 4,294,967,295 bytes, or more than 65,535 entries MUST be refused with AGSC-E903 (AGSC-01-16). ZIP64 is never emitted.
    • No compression. The compression method is 0 (stored) in every local file header and every central-directory record, and the compressed size equals the uncompressed size.
    • Time. Every entry's modification time is the build instant of AGSC-04-09 expressed in UTC, written into the MS-DOS date and time fields of APPNOTE.TXT §4.4.6 from the digits of that instant's AGSC-04-10 rendering and from no clock and no zone: date = ((YYYY - 1980) << 9) | (MM << 5) | DD and time = (hh << 11) | (mm << 5) | (ss >> 1), each an unsigned 16-bit field. Those fields are local time by the format's own definition and carry no zone, which is why the digits are used directly and never a broken-down local time — a writer that used one would emit different bytes on two machines differing only in TZ. An instant before 1980-01-01T00:00:00Z — which AGSC-04-09's own default of 0 produces — is written as 1980-01-01T00:00:00 (date = 0x0021, time = 0x0000), and an instant after 2107-12-31 as 2107-12-31T23:59:58, the format representing no other year; both clamps are stated here so that two writers clamp alike.
    • Header fields. In every local file header and every central-directory record: version needed to extract = 20; the general-purpose bit flag = 0x0800 and nothing else (APPNOTE.TXT §4.4.4 bit 11, "the filename and comment fields for this file MUST be encoded using UTF-8"); the CRC-32/ISO-HDLC of the entry's bytes; the file-name length; and an extra-field length of 0. In every central-directory record additionally: version made by = 20 with an upper byte of 0 (MS-DOS attribute semantics, so no attributes are stored), file-comment length 0, disk-number-start 0, internal file attributes 0, external file attributes 0, and the byte offset of that entry's local file header. The end-of-central-directory record carries disk number 0, central-directory-start disk 0, the entry count twice (this disk and total), the central directory's size and its offset, and an archive-comment length of 0. Every multi-byte field is little-endian (APPNOTE.TXT §4.4).
    • Nothing else. No extra field, no file comment, no archive comment, no data descriptor, no directory entry, no external attribute and no ZIP64 record is written, so the archive carries the file set and no host's traces.

    The archive is then byte-identical in every host and across time zones, exactly as the files it carries already are (AGSC-07-13), and the SHA-256 a page shows beside a download link is a statement about the content and not about the writer. The archive MUST NOT be written inside dist/harness/<name>/, whose file kinds AGSC-07-12 closes at seven "and no others", and MUST NOT be read as an input (AGSC-01-16). Its file name is AGSC-04-25's tenth stamping place. Vector compose-0016. (added at rc.6, 2026-09-22: AGSC-09-09's --zip writes an archive whose bytes no rule defined, so two conforming engines could emit different bytes for the same file set and neither would be wrong — while the "download all" archive's SHA-256 is shown beside the download link, which invites exactly the comparison the missing rule would have made meaningless.) [AGSC-09-09, AGSC-04-09, AGSC-01-16, AGSC-07-13]

  • AGSC-07-14 (retired at rc.3, 2026-09-17: strictly implied by the general rule AGSC-01-29, which now names the Harness files — merged into AGSC-01-29; the id is reserved under AGSC-00-16 and never reused.)
  • AGSC-07-15 A Harness MUST NOT contain scripts, executables, symlinks, an allowed-tools key (the seven-file closure is AGSC-07-12's); nor MUST a published skill pack (§7.4). A violation is AGSC-E407 (the code was registered against this rule and named by no sentence until rc.5). [PRD-035]
  • AGSC-07-16 Harness structure is CC0 to the user; the prose it quotes travels under the Content Use Terms. Both facts MUST be stated in the emitted files. [NFR-10]
  • AGSC-07-17 An invalid composition MUST NOT emit a Harness. The verdict alone is returned, with exit code 1 from the CLI. [PRD-036, AGSC-09-08] (trace corrected at rc.5: the bracket cited AGSC-09-06, which governs vector-file encoding; exit codes are AGSC-09-08.)
  • AGSC-07-18 Runtime emitters (GABBE, kaiban-distributed, CrewAI, LangGraph, ADK/MS-AF, n8n) are target renderings of the seven files of AGSC-07-12, selected by compose --emit <target> and written outside dist/harness/<name>/; adding one MUST NOT change the seven files, MUST NOT add a file inside the Harness directory, and MUST be a single template plus a registry row. [design]

7.4 Skill packs

The packs of this section are the published packs of the route set (AGSC-06-01), one per Cluster. They are a different artefact from the per-Procedure skills/<slug>/SKILL.md files inside a Harness (AGSC-07-12), which are never published and never installed; both are correct, both are needed, and no rule of §7.3 and §7.4 refers to the other's artefact.

  • AGSC-07-19 One skill pack MUST be emitted per Cluster, plus /skills/index.json, whose object carries the member bundle_version, the content version of AGSC-04-25 (added at rc.6, 2026-09-22), beside its pack entries. Each pack's directory name MUST equal its name field and MUST satisfy the slug grammar including the no--- rule; description MUST be ≤1024 characters. [PRD-032]
  • AGSC-07-20 Each pack MUST declare its licence and MUST be accompanied by a SHA-256 lockfile over its files, carried as the lock member of that pack's entry in /skills/index.json — AGSC-06-01 emits no other route for one, so a separate file would have nowhere to be published and the two rules would be jointly unsatisfiable (stated at rc.6, 2026-09-22); an install MUST verify the lockfile and MUST show a diff on update. [PRD-035]
  • AGSC-07-21 Install targets are .claude/skills, .agents/skills and .github/skills; installation MUST be idempotent. [PRD-033]
  • AGSC-07-22 skills import MUST map a SKILL.md to a procedure item, round-tripping without loss of the declared fields. [PRD-034]

7.5 Step 5 — ports and wiring; saved architectures (added at rc.3, 2026-09-16)

  • AGSC-07-23 Step 5 — wiring. After Step 4, over the surviving set only: for every survivor and every name in its consumes[], the producers are the survivors whose produces[] contains that name, in code-point slug order. Emit wiring[] into harness.jsonld as objects {consumer, port, producers} sorted by (consumer, port); emit one Structurizr relationship per producer–consumer pair, labelled produces <name>, into workspace.dsl, and the equivalent edge into diagram.mmd, both ordered by (producer, consumer, port) with every comparison by code point. A name with no producer among the survivors is a warning appended to warnings[] in the AGSC-07-09 shape — {code: "AGSC-E804", key: "consumes", source: <consumer slug>, target: <port name>}; it MUST NOT invalidate the composition. Verdict-neutrality and ordering are stated once, in AGSC-07-08. [PRD-057]
  • AGSC-07-24 compose --from <slug> MUST take the selection from the yaml agsc-selection block of a kind: architecture item (AGSC-02-97) and run Steps 1–5 exactly as for an explicit selection; the item page MUST expose the same composition through /compose/?from=<slug> and the page tools. When the item carries verdict_digest and the recomputed JCS verdict's SHA-256 differs, lint reports AGSC-E805 (warning) and the page shows the stored and current verdicts. The seven-file rule (AGSC-07-12/15) is unchanged: wiring lives inside harness.jsonld, workspace.dsl and diagram.mmd. [design]
