AgenticSystemCore

SummaryAn open format and a set of rules that turn a folder of Markdown into a wiki, a graph, an agent memory, a skills library, runnable architectures and a shared live board for agents and people, published here as a node of itself.

Auto-wiki, distributed agentic memory, live specifications, evolving skills, runnable architectures and a self-driving live board — one open format for people and agents. Reference Node Level-0 of the Agentic Knowledge Web.

AgenticSystemCore is an open specification and reference implementation for knowledge that people and software agents can both read, verify and build on: a memory substrate that is deterministic, auditable, and governed by published conformance rules rather than by convention.

This site publishes the specification and is itself a node of it: its vocabulary items, its discovery document, its graph and its agent-facing text file follow the rules they describe, and the discovery validator checks the site at Level 2 before every publish.

What is different about it

Other systems have some of these. To our knowledge none has them together: a knowledge base a machine can find through registered web mechanisms, a digest on everything it points at, a typed graph with a published vocabulary, bytes pinned by conformance vectors, a person on every merge — directly, or by a standing rule that person recorded — and a runnable harness out of the same files, with no server.

These are claims about the specification's text and its test vectors, not performance claims. The dated comparison with other systems is in the related work, and the full sentence in the introduction.

Six ways to use it

  • Auto-wikiMarkdown in, a checked and linked website out; no model needed.
  • Distributed agentic memoryAgents read, cite and propose; people ratify; nodes peer with each other.
  • Live specificationsA project's decisions, specs, tasks and gates as one governed memory.
  • Evolving skillsProcedures become skill packs; improved skills come back as Procedures.
  • Runnable knowledgeSelect Concepts, get a Harness of seven files a runtime can execute.
  • The live boardAgents and people pull, claim and finish a project's tasks on one shared board until it is done.

One folder of files, one format, six ways of using it. The six modes explain each.

What it is best for

For agents

  • Memory for one agentRun agsc mcp in a Bundle: an assistant gets seven tools to search, read, follow links and cite items by address, and nothing leaves the machine.
  • Shared memory for manyEvery agent reads the same published files and changes them only by proposals a person ratifies.
  • A source of skillsProcedures become skill packs with a lockfile of their digests, installable into agent tool folders.
  • Runnable proceduresSelected Concepts become a harness of seven files a runtime can execute.
  • A live board for a team of agentsAgents claim and finish tasks until a board is done; decisions stay with people.
  • Knowledge across nodesA client reads several nodes' graph dumps and joins them on its own side, every foreign result marked with its origin.

For people

  • A wiki that corrects itselfMarkdown in; a checked, linked, searchable site out, with every change reviewed.
  • A project's living specificationsDecisions, specifications, tasks and gates as one governed memory.
  • A pattern catalogueConcepts with sources and provenance, readable without JavaScript, composable into a starting architecture.
  • A team boardA board exported from a project tool becomes a live board and goes back again: 11 board formats, listed below.

Works with the tools you already use

Every name below is read from the reference engine's own registries when this page is built.

  • Imports and exports: Markdown, the Open Knowledge Format, JSON-LD, JSONL and chunk exports, and adapters for project boards, COGX memory archives, GABBE kits, a compact context file for a model, skills repositories.
  • Steering files for coding assistants: AGENTS.md, Aider, Claude Code, Cline, Codex, GitHub Copilot, Cursor, GABBE, Gemini CLI, Kiro, Windsurf.
  • Skills, both ways: plugin marketplaces, Claude Code plugins, Agent Skills folders, Cursor rules, Windsurf rules.
  • Project boards, both ways: this format's own board file, Asana, GitHub issues and projects, GitLab, Jira, Linear, plain Markdown, Notion, Obsidian Kanban, Todo.txt, Trello.
  • For assistants: a local MCP server (agsc mcp), and the same seven tools registered on every page of a built site for a browser's own agent.
  • In your repository: a GitHub Action that runs agsc ci, and a pre-commit hook that runs agsc lint.
  • Where a node can live: Cloudflare Pages, nginx or Apache, GitHub Pages behind a proxy, your own machine, a clone of the repository, IPFS through a gateway, a ledger-anchored record — any place that serves the files over HTTPS; agsc-host list says what each place can and cannot do.

A distributed brain, with no server

Each node is a folder of files published as a static site. Nodes find and read each other through registered web mechanisms, every file they point at carries its digest, and they share one vocabulary. A node names its peers; a reader walks from one to the next. No node calls another, and no server sits in between.

Get started

In a folder of Markdown notes, with the command line installed:

agsc init     # each note gets a type, a title and its provenance
agsc ci       # lint, build twice, compare the bytes, verify
agsc mcp      # give an assistant seven tools over the same folder

Before the first build, add .well-known/security.txt with a Contact: line; agsc init says so. The assistant setup guide and the start page for each kind of reader go further.

This site is a node of itself

Everything published here follows the rules it publishes: the vocabulary items, the discovery document, the graph and the agent-facing text file are written by the reference engine, and the discovery validator checks this site at Level 2 before every publish. The status page says which further parts are live.

Where to start

  • Everyone: start here — one path for each kind of reader.
  • People: the guide, then the specification and the vocabulary.
  • Architects and implementers: the architecture, the requirements, the discovery profile and the ontology.
  • Agents: /.well-known/knowledge-linkset or /llms.txt.
  • Publishers: publish a Level-0 node from any CMS or wiki export.
