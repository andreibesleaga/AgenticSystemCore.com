    Guide

    • Guide: The plain-language layer of this site: what AgenticSystemCore is, the six ways it is used, how it works, and how to read the specification without being a standards expert.
    • Agent skill: One skill file that teaches a coding agent to use AgenticSystemCore: the six modes, the sixteen commands, how to write an item, how to propose a change, how to read and cite a node, and what an agent never does on its own. Download it into your agent's skills folder and the agent can pick up any mode at once.
    • Architecture: The architecture of the reference implementation in the arc42 and C4 forms: quality goals, constraints, the system in its context, containers, five bounded contexts and their ports, the runtime sequences, deployment, the decisions of record and the threat model.
    • Compliance and security: Where the standard, the reference software, the documentation and this site stand against the regulations and frameworks that could apply to them, what the security design proves and what it does not, and what this site does and does not do with your data.
    • Data model: Six kinds of item, one file shape, fourteen typed links, clusters for navigation, sources for evidence and a provenance record on everything: this is the whole vocabulary a node needs.
    • Demos: Every mode and every persona as a small demo you can run in under five minutes from an empty folder: the exact commands, the lines they print, and the one thing each proves. Every command is run by a test in the engine repository, so this page cannot drift from the engine.
    • Glossary: Every term of the specification's language and every term of the ontology, with its definition and the rule that defines it, generated from the sources so that it cannot drift from them.
    • Guides: Six short guides, one per mode: who each is for, what you get, the exact commands on files you write yourself, and the lines they print. Every command is run by a test in the engine repository.
    • Mode 0 guide: a folder of notes becomes a checked site: For a person with Markdown notes: install the package, adopt the notes, add a security contact, commit once, check and build the site, change a note as a proposal, and get it ready to publish.
    • Mode 1 guide: memory for an assistant, and nodes that check each other: For a developer connecting an AI assistant, and for two publishers: the local tool server and its seven tools, two nodes that name and check each other, and how to verify a published node by hand.
    • Mode 2 guide: a project's decisions, specifications, tasks and gates: For a team with coding assistants: the files for a decision, a specification, tasks and a gate; the board; the forge files a gate compiles to; one steering file for every assistant.
    • Mode 3 guide: procedures as installable skills: For a team with repeatable procedures: write a procedure, emit one skill pack per cluster with its lockfile, install it for an agent, publish it, and bring skills from elsewhere in.
    • Mode 4 guide: a selection becomes a starting harness: For an architect: compose a selection of items into a harness of seven kinds of file and an archive, try the opt-in run verb, and record a run that happened elsewhere.
    • Mode 5 guide: the live board: For people and agents sharing tasks: a board, an agent lane declared with its owner, budget and limits, a claim made as a proposal and accepted by a person, and the refusals that keep the board honest.
    • How it works: Files go in, every surface comes out, and nothing is published until a deterministic build has proved itself twice: this page walks through the build, the proposal lifecycle, discovery, import and export, and the safety rules.
    • How to use it: One page to pick up any of the six modes and use it now: what to install, the first commands for each kind of user — one person, one agent, or many people, agents and nodes together — the scenarios each mode covers, the switches in the configuration, and the hooks that connect agents and tools to a node.
    • Introduction: AgenticSystemCore turns a folder of Markdown files into a shared memory that people and software agents can both read, check, extend and run: a distributed brain whose meaning, form and rules are published, so any agent anywhere can use it, improve it and build systems from it.
    • The six modes: One folder of Markdown, one format, six ways of using it: an automatic wiki, a distributed memory for agents, live specifications for a software project, an evolving library of skills, knowledge that can be assembled into a running architecture, and a shared live board on which agents and people run a whole project until it is done.
    • Reading the specification: A key to the specification's notation: what the rule identifiers mean, how the key words MUST and SHOULD are used, what the small bracketed references at the end of each rule are, why some rules are marked reserved, and how error codes, vectors and Levels fit together.
    • Requirements: The product requirements document, frozen as the project's first baseline and published here for the specification version this site publishes: personas, functional requirements in EARS form with their acceptance criteria, non-functional requirements, non-goals and the definition of done.
    • Scenarios: The behaviour of the system written as scenarios, one feature file per persona, in the Given/When/Then form of behaviour-driven development. Each scenario names the requirement it proves.
    • Standards and references: Every standard this work stands on or defines, with its version and the date it was checked; its registrations — two with IANA, one of them registered, and one w3id.org namespace — and their current status; the related work it was compared against; and the publications that describe it.
    • Start here: One path through this site and its sources for each kind of reader: someone with a folder of notes, someone curious, a developer, an implementer in another language, and an agent. Each step is one page, in order.
    • Status: What is live today, what is in preparation, and what has not been requested or granted yet. This page changes at each step and never says a name is registered before a registry does.

    Vocabulary and items

    • Clusters: The groupings this node uses to organise its items.
    • Guides cluster: Procedures for publishing and reading a node, each step naming the rule or the check that proves it.
    • Project board cluster: The open work on the specification itself, kept as task items of this node, so the project's own plan is published the way the live board publishes any team's.
    • Vocabulary cluster: The terms of the specification's ubiquitous language: the six item types and the words that complete them.
    • Vocabulary: The twelve terms of the specification, each on its own page with the rules that define it.
    • Bundle: One directory tree of Markdown items plus exactly one agsc.config.json: the unit of publication and of conformance.
    • Cluster: A navigational grouping of items. Membership is authored on the item, and nesting is expressed as membership.
    • Concept: A unit of knowledge in a Bundle, qualified by kind: pattern, taxonomy, explainer, principle, decision, spec, task, term or architecture.
    • Episode: A recorded occurrence, such as a session, a run or an incident, with a start instant, an actor and an outcome.
    • Gate: A declared set of checks that a change must pass, at level L1 or L2. Its runs are recorded as episodes.
    • Harness: Generated output: the file map a valid composition of selected items produces. A Harness is never authored.
    • Item: One Markdown file with YAML frontmatter whose type is concept, episode, procedure, lesson, cluster or gate.
    • Lesson: Knowledge distilled from one or more episodes, carrying a severity of info, warn or block.
    • Link: A typed relation between two items of one Bundle, written as a frontmatter key whose values are slugs.
    • NOW: Generated context about the current state of a Bundle, such as counts and last build. NOW is never an item.
    • Procedure: A plan a reader can execute: a trigger, steps and checks. Procedures are published in skill packs, one pack per cluster.
    • Release version 1.0.0 of the specification: Apply the items recorded against the release candidate, run the whole vector set with the reference engine, and tag version 1.0.0, at which the reference engine may first claim a conformance Level.
    • Source: An external work cited by an item, written inline as a sources[] entry and published under a fragment IRI.
    • Procedures: Step-by-step procedures derived from the specification, each step naming the rule or the check that proves it.
    • Publish a Level-0 node: Turn an existing CMS, wiki or static-site export into a conforming Level-0 node without running an engine.
