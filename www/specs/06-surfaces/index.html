AGSC-06 — Published surfaces: routes, discovery files, llms.txt

SummaryEverything a node publishes: the fixed route set, the discovery document, llms.txt, the chunk export, the JSON-LD context, headers and budgets.

Status of this document

Specification 1.1.0, a draft of this version, not yet tagged. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

Part 1 of 2, 6.1 to 6.4. This section is published in two parts so that each page stays within the budget of AGSC-06-21; a rule's link names the part that carries it. Part 2 carries 6.4 (continued) to 6.10.

In plain language

Routes. A writer emits a fixed set of pages and files — item pages, clusters, tags, search, NOW, compose, skills, specs, the graph files, llms.txt, sitemap, robots, the ledger, the chunk export, the context file, boards when tasks exist — and nothing else.

The discovery file. /.well-known/knowledge-linkset is an RFC 9264 link set: one document that points at every machine artefact with its SHA-256 digest, the spec version, counts, the ledger head, peers, surfaces and contribution targets. Pages point at it with the standard describedby relation; the Internet-Draft asks for the well-known name, which is not registered, and the profile identifier is registered in the IANA Profile URIs registry. The file can also carry optional links to related systems — an llms.txt file, an agent card, a server card, a memory or ontology endpoint — using standard relations only.

llms.txt. The agent-facing text file has a fixed byte layout — a provenance header, the title, the description, one section per cluster with one line per item — so two tools produce the same file.

From 1.1, llms.txt follows v2 of the convention, and every page points at it. The title comes first and the description straight after it, so a reader of llms.txt v2 finds the summary; the provenance header follows them, and a [, ], ( or backslash in a title or description is escaped. Every page names /llms.txt in its head with the relation describedby and the type text/plain, beside the discovery file, and an item page names its Markdown copy /pages/<slug>.md with the relation alternate and the type text/markdown (AGSC-06-13a, AGSC-06-46).

The chunk export. /chunks.jsonl is the Bundle pre-split for agents: one line per chunk, cut at headings outside code fences and at a size bound, with a stable id, the text, provenance, licence and terms, and a digest. No embeddings.

From 1.1, the chunks can be checked as a set. Each chunk line also carries the item's own description (abstract) and a licence address that resolves (license_url); no chunk text begins with a blank line. The discovery document states the digest of /chunks.jsonl, the number of lines and one hash over all their ids, so a reader finds a line that was dropped or added. A node with at most 500 items also serves /chunks-index.toon, a compact table of the lines (AGSC-06-29, AGSC-06-37, AGSC-06-44, AGSC-06-45).

From 1.1, the graph is on the page. An item page shows its typed Links in both directions, the links back to it included, as a small figure and a table that says what each relation means; a cluster page maps its members; /clusters/ adds an overview of the links between clusters, a legend and an explorer that works from the keyboard. Where a node uses the domain layer, an item page also shows its domain type, role, warrant and domain links. Only published items are drawn.

From 1.1, /query/ answers questions in SPARQL. The page runs a query over the node's own graph in the browser, with the ten questions of the graph as examples, and offers the result as CSV or JSON; it calls no server and stores nothing. site.query_page: false leaves it out.

Headers. No third-party scripts, no beacons; strict security headers; public artefacts readable cross-origin.

This box explains; the rules below decide. New to the notation? See how to read the specification.

6.1 Route set

  • AGSC-06-01 A writer MUST emit exactly this route set into build.out (default www/) — the routes listed here together with the conditional routes the third paragraph below names, the conformance report, the agent card and the VoID description among them (Amended 2026-10-02 for 1.0.0: those three were named only among the conditional routes, against "exactly this route set"), and the optional routes /chunks-index.toon (AGSC-06-37), /query/ (AGSC-06-39), /.well-known/ard.json and /.well-known/ai-catalog.json (AGSC-06-42) (Amended 2026-10-29 for 1.1.0: the route set named no route that a node may leave out;     A writer targeting another host MUST emit the equivalent configuration for that host and MUST state which deployment profile it emitted in its conformance claim (AGSC-09-01); the normative content is the header set of AGSC-06-17, AGSC-11-03 and AGSC-11-05 and the redirect of AGSC-06-17, never the file format. This route set bounds what a writer MUST emit; it is not a bound on every file that may sit in the deployed directory, and the same-origin script assets a page of this set loads — /compose/ and every item page load them so that the page tools of AGSC-09-16 can be registered, and AGSC-06-17's script-src 'self' policy leaves a writer no inline alternative — are emitted as part of the page that names them and are not routes of their own. The same holds for the two presentation files every page of this set links, the stylesheet /assets/site.css and the theme-control script /assets/theme.js of AGSC-06-05: a Bundle that authors content/assets/site.css replaces the default stylesheet at that path whether or not a body references it, and /assets/theme.js is always the writer's own, and so is the one script the /search/ page loads to search /search.json in the page, /search/agsc-search.js, which MUST tokenize a query exactly as AGSC-06-23 tokenizes an item — a writer that ships that page MUST emit the script as part of it. The files under /query/ other than its index page (AGSC-06-39) — the page script, the query engine and its licence text — are page assets of that page in the same way. A page that registers the page tools of AGSC-09-16 MUST do so only through document.modelContext, feature-detected, the API of the WebMCP Draft Community Group Report of 27 October 2026 (a report of the Web Machine Learning Community Group, which is not a W3C Standard and is not on the W3C Standards Track; read 2026-10-29), and through no other object. (Amended 2026-10-29 for 1.1.0: the route set named no query page and said nothing of the API the page tools register through) (Rationale: _headers and _redirects are Cloudflare Pages configuration files whose grammar no rule pins, and holding a Level-2 writer on nginx, Apache, S3 + CloudFront or a Solid pod to them would make every Level-2 claim implicitly Cloudflare-shaped.)

The conditional routes are the shards and index pages of AGSC-06-21/06-31 (by size), /boards/** (by the presence of a task), /.well-known/agent-card.json (only when the node declares both a2a-card and a responder surface, AGSC-06-34), /chunks-index.toon (only at Level 2 and above, only when the published set holds at most 500 items, and only if the writer chooses to emit it, AGSC-06-37), /query/ and the files under it (unless site.query_page is false, and only when the node serves /graph.nq, AGSC-06-39), /.well-known/ard.json and /.well-known/ai-catalog.json (only when discovery.ai_catalog is true, AGSC-06-42), /legal/ (only when the Bundle root carries a LICENSE-CONTENT file, AGSC-06-18), /conformance/ (only when a claimant publishes the report AGSC-09-03 defines, which is a MAY), /.well-known/void (only when a publisher emits a VoID description independently, AGSC-06-12, which is a SHOULD-link and never an emission of this specification), /.well-known/security.txt (only when the Bundle root carries an authored .well-known/security.txt that states a Contact: field — AGSC-06-36), /assets/<path> (one route per authored asset file a published body references), /specs/, /specs/agentic-knowledge/ and /specs/mcp/ (only on the namespace document site, above), /about/ (only when the Bundle authors that page; its source and bytes are implementation-defined at 1.x), /changelog/ and /ledger.jsonl (only when the build is given the git-log file of AGSC-08-20b; a Level-2 claim requires both, AGSC-10-04) and the optional /graph/fragments/** (AGSC-06-33); no other route is conditional. /graph.rdf and /feed.xml are not emitted at 1.x, and build.rdfxml and build.feed are reserved names rejected with AGSC-E004 (feed is reserved because no 1.0 rule pins a feed's bytes, so the route cannot be derived and the switch has nothing to switch on).

    SECURITY.md, CODE_OF_CONDUCT.md, CITATION.cff, CONTRIBUTING.md, GOVERNANCE.md, CONTRIBUTOR-AGREEMENT (AGSC-08-06) and the REUSE layout are repository files, not routes (PRD-047); only security.txt is published, at its RFC 9116 location above, and what it carries is AGSC-06-36's. (Amended 2026-11-11 for 1.1.0: the files that the /clusters/ explorer loads are page assets of that page, as the files under /query/ are, and in general any .js or .css file that a page of the set loads from its own origin is one (build-0029). 6.2 The well-known file

  • AGSC-06-07 There MUST be exactly one discovery file, /.well-known/knowledge-linkset at the root of the node's origin — at 1.0 a node occupies a whole origin (AGSC-01-19) — served as application/linkset+json carrying the RFC 9264 §5 profile parameter profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge". Where the hosting platform cannot carry a parameter on Content-Type, the node MUST instead send the response header Link: <https://w3id.org/agentic-system-core/profile/agentic-knowledge>; rel="profile" (RFC 6906); at least one of the two MUST be present, and a reader MUST accept either. No vendor media type is defined, registered or served. Separate manifests MUST NOT be emitted — except the two catalogue files of AGSC-06-42, which are not discovery files of this specification but catalogue entries that point at this one document, are emitted only when discovery.ai_catalog is true, and which no reader of this specification needs (Amended 2026-10-29 for 1.1.0: "exactly one discovery file" and "separate manifests MUST NOT be emitted" now admit the opt-in catalogue files, and nothing else); a release MAY carry a copy named knowledge-linkset.json. agent-card.json MUST NOT be published unless the node declares it as the a2a-card surface and declares a responder surface it points at (AGSC-06-34, AGSC-11-16); a card without an endpoint is AGSC-E210. The well-known suffix knowledge-linkset is not registered: its registration under RFC 8615 is asked for in the Internet-Draft draft-besleaga-agentic-knowledge-wellknown, which is posted, and no request has been sent to the registry; the Profile URI is registered in the IANA Profile URIs registry under RFC 7284 (First Come First Served) (Amended 2026-10-02 for 1.0.0: "pending registration" said more than was true); the discovery link uses the already-registered relation describedby (AGSC-06-25), so no relation is requested. Until the suffix is granted, a node MAY additionally serve the same document at a path it controls, linked with describedby and the linkset media type — nothing in this specification says "registered" of the suffix before the registry does (Amended 2026-10-07 for 1.0.0: IANA has registered the Profile URI in the Profile URIs registry (RFC 7284). This rule said that its registration was "to be requested" and that nothing here says "registered" of the profile before the registry does; the registry now does. The well-known suffix is unchanged: not registered, and no request has been sent to the registry.). The suffix is a single point of substitution: the reference implementation holds it as one constant (WELLKNOWN_SUFFIX) from which the peers[] schema pattern, the _redirects alias of AGSC-06-17, the vector paths and the rule texts derive, so a refused registration substitutes the next candidate suffix by one MINOR and a regeneration: the new suffix is added and the present path keeps answering with a redirect to it, so no reader that knows only the present path breaks (AGSC-00-14) (Amended 2026-10-02 for 1.0.0: until 1.0.0-rc.6 this said "by one PATCH", but a new discovery address is an addition, which a MINOR makes). The profile URI carries no version: it names the same profile for every version of this specification with the same MAJOR, a discovery document states the version it follows in agsc-spec-version (AGSC-06-08), and a new MAJOR that changes what the profile fixes takes a new profile URI. [PRD-024, RFC 9264, RFC 9727 §7.3, RFC 6906]

  • AGSC-06-08 The document is a JSON object — JCS-canonical at Level ≥2 (AGSC-04-04), valid I-JSON at Level 0 (AGSC-06-08a, AGSC-10-02) — whose sole top-level member is linkset (RFC 9264 §4.2.1); the document MUST NOT carry any other top-level member; the linkset array holds exactly one link context object whose anchor is the Bundle IRI (AGSC-05-03), its relation-name members ordered as JSON member names (AGSC-04-05). The anchor is on the origin of the document. A reader MUST treat a document whose anchor is not on the origin of the URL it finally retrieved the document from, after redirects, as not being that node's discovery document (RFC 9264 §9, RFC 8615 §4.3): a validator reports AGSC-E907, and a federation walk and the mutual check of AGSC-10-12 skip it as unreadable; a document read from a file has no such origin and is not judged by this sentence. (Amended 2026-10-02 for 1.0.0: a copy of one node's document served by any other origin passed every check, and a reader would have attributed it to that node.) Integrity and bundle facts ride on the links as extension target attributes (RFC 9264 §4.2.4.3), whose values are ALWAYS arrays of strings. Every artefact link — a link whose row in the table below says yes under digest — MUST carry digest at Level 2 and above (AGSC-06-08a), a Dictionary with a single member whose key is the RFC 9530 algorithm name sha-256 and whose value is an RFC 9651 §3.3.5 Byte Sequence, serialised per RFC 9651 §4.1 as sha-256=:<base64>: and carried as one string in the attribute's array, over the canonical bytes of the target. Bundle-level facts ride on the anchor's describedby link to graph.jsonld and nowhere else: agsc-spec-version (one value), agsc-generated-at (one value, an AGSC-04-10 instant derived from SOURCE_DATE_EPOCH), agsc-counts (one "<type-plural>=<n>" string per item type, in code-point order of the type name, counted over the published set — release-gated, draft and retired items excluded, AGSC-06-30), agsc-bundle-hash (the AGSC-04 bundle hash, RFC 9530 syntax), and agsc-bundle-version (one value, the content version of AGSC-04-25: the hash says whether two nodes hold the same content and never what the publisher calls that content, so a reader that wants to cite or compare releases needs both). The ledger is the link https://w3id.org/agentic-system-core/rel#ledger, carrying digest and agsc-ledger-head (one value, the lowercase hex head of the derived ledger of §08). A node MAY carry one further link whose relation is https://w3id.org/agentic-system-core/rel#signature (AGSC-06-10) and whose target is a detached signature over the canonical bytes of this document. At 1.x no rule pins the signature format, no Level requires the link, it affects no digest, no claim and no walk, and a reader MUST ignore it if present. (Non-normative: the digests of this rule establish that the bytes are the bytes the publisher hashed; they establish nothing about who the publisher is. The trust anchor at 1.x is the origin's TLS certificate and DNS name, and a publisher who needs more publishes the optional signature. The nearest comparator, the Agent2Agent Agent Card, makes a signature over its canonical card optional ("Agent Cards MAY be digitally signed", A2A §8.4, read 2026-09-16 and quoted in docs/SECURITY-CONSIDERATIONS.md §2); this specification keeps its own optional for the same reason and one more — a static node has no key custody — and the reasoning is written here rather than left to inference. No IANA-registered relation exists for a signature — the registry was read on 2026-09-23 and holds none — so the link can only take this specification's own extension-URI form, and AGSC-06-35's registered-names-only list cannot admit it.) (Amended 2026-10-02 for 1.0.0: the table below names every link the document carries, when, and which of them carry digest; until then "artefact link" was not defined.)

The example is shown pretty-printed for review; the served bytes are JCS-canonical with exactly one trailing LF (AGSC-04-04).

  • AGSC-06-08a At Level 0 (AGSC-10-02) the document is the same link set with every digest and every agsc-* attribute of AGSC-06-08 (agsc-spec-version, agsc-generated-at, agsc-counts, agsc-bundle-hash, agsc-bundle-version and agsc-ledger-head, and from 1.1 agsc-chunk-count, agsc-chunk-set and agsc-ledger-length) omitted — the §11 attributes (agsc-surface, agsc-surface-version, agsc-access, agsc-visibility, agsc-contribute-mode, agsc-tombstone) are Level-independent — a CMS export has no ledger, no graph.nq and no build instant, and Level 0 does not ask for one. At Level 2 and above every digest REQUIRED by AGSC-06-08, and every agsc-* attribute on the describedby and rel#ledger links, MUST be present. There is no structural difference between the two: linkset is the sole member at every Level. [PRD-055]
  • AGSC-06-09 The linkset member MUST conform to RFC 9264: an array of link-context objects, each with anchor and relation-keyed arrays of objects carrying href and optionally type. A consumer that cannot obtain the discovery document at the well-known URL of AGSC-06-07 SHOULD try, in order, the home page's describedby link whose type is application/linkset+json (AGSC-06-25) — which names the copy a node MAY serve at a path it controls (AGSC-06-07) — and then /llms.txt (AGSC-06-13). This order is informative: a node is not obliged to be reachable by more than the well-known URL, and a reader that finds none of them reports AGSC-E901. (Rationale: the well-known name is one door among several, and a consumer meeting a 404 needs a second door.) [PRD-024, RFC 9264]
  • AGSC-06-10 Relation names MUST be either IANA-registered short names — the five this specification itself emits (describedby, alternate, license, service-doc, author) plus any relation AGSC-06-35 admits for a related-system link (related, service-desc, service-meta, collection, item and cite-as) — or extension URIs of the form https://w3id.org/agentic-system-core/rel#<name> with <name> ∈ graph, ontology, context, now, skills, ledger, peer, surface, contribute, access, signature and boards — of the first six, five have a route in AGSC-06-01 and ontology names the vocabulary document of the namespace document site (AGSC-06-06), which a content node does not serve: a node that does not serve it omits the link, and a node that does names its own copy; peer naming another node's well-known URL for the mutual-conformance test of AGSC-10-12; surface, contribute and access defined in AGSC-11-16, AGSC-11-14 and AGSC-11-20, whose targets are surfaces, contribution endpoints and credential pages and need not be routes of this node; signature defined in AGSC-06-08, whose target is a detached signature and need not be a route of this node (the IANA link-relation registry holds no relation for a signature, so this specification's own extension form is the only one available); boards defined in AGSC-10-13, whose target is /boards/index.json. shapes is NOT a 1.x relation: SHACL shapes stay in the development lane (AGSC-05-24), so no /ns/shapes.ttl is published and a relation with no target would be a dangling promise. Unregistered short names MUST NOT be used. Extension target attributes (RFC 9264 §4.2.4.3) MUST use the prefix agsc- (agsc-spec-version, agsc-generated-at, agsc-counts, agsc-bundle-hash, agsc-bundle-version, agsc-ledger-head, and from 1.1 agsc-chunk-count, agsc-chunk-set and agsc-ledger-length (AGSC-06-44); and the six attributes of the boundary rules that AGSC-06-08a lists) (Amended 2026-10-02 for 1.0.0: the list did not point to the boundary rules' six) so that they can never collide with the target attributes RFC 8288 §3.4 defines (hreflang, media, title, title*, type) or with those RFC 9264 §4.2.4 serialises — no Web-wide registry of target attributes exists, and the registry that RFC 9423 created is scoped to CoRE and holds no digest and no agsc- name (read 2026-10-10); digest is deliberately unprefixed: RFC 9530 supplies its algorithm token and RFC 9651 its value syntax, and the plain name keeps a generic link-set reader that knows RFC 9530 syntax able to read it (Amended 2026-10-02 for 1.0.0: the rule said "RFC 9727-style" consumers, and RFC 9727 says nothing of digests). Every extension target attribute value — digest, every agsc-* attribute, and profile where a related-system link carries it (AGSC-06-35) — is an array of strings (RFC 9264 §4.2.4.3); type, title and media are strings and hreflang is an array of strings (RFC 9264 §4.2.4.1). Within one relation's array, link objects are ordered by href (code point), and every href is absolute — the Bundle base plus the route. type values are advisory hints (RFC 9264 §4.2.4.1, "Target Attributes Defined by Web Linking", is where the type member is specified; RFC 8288 §3.4.1 is where the hint language is — "this is only a hint; for example, it does not override the Content-Type header field of a HTTP response obtained by actually following the link"); application/jsonl is used for /ledger.jsonl and is deliberately unregistered — a reader MUST NOT depend on it. (Amended 2026-10-10 for 1.0.0: the rule denied that any registry of target attributes exists; RFC 9423 created one, scoped to CoRE, which holds neither name.) [RFC 9264, RFC 8288, RFC 9530]
  • AGSC-06-11 digest values are defined once, in AGSC-06-08; agsc-ledger-head MUST be the lowercase hex hash of the last entry of the derived ledger of §08 — the head that verify --ledger recomputes and compares. A ledger always has at least the trailing build entry (AGSC-08-20a), so the head is never undefined where the attribute is required; a Level-0 node publishes no rel#ledger link and therefore no head (AGSC-06-08a). agsc-generated-at MUST derive from SOURCE_DATE_EPOCH.   • AGSC-06-12 VoID (/.well-known/void, registered 2011) is prior art for dataset discovery and is cited as complementary wherever this specification describes its discovery layer (an editorial commitment, not a conformance requirement). This specification emits no VoID description: graph.jsonld on the describedby link already carries the bundle-level facts (AGSC-06-08), AGSC-06-01's route set is closed, and a SHOULD-emit with no route would be unimplementable. A node that publishes a VoID description independently SHOULD link it from the link set as a second describedby link (AGSC-06-09 admits several; AGSC-06-08's "nowhere else" binds the agsc-* bundle-facts attributes to the graph.jsonld link, not the number of describedby targets). [design]
  • AGSC-06-35 Related-system links, OPTIONAL and extensible. The discovery document MAY carry, in its one link context, links to related discovery documents and systems — an llms.txt v2 file, a VoID or DCAT description, an OKF index, an Agent2Agent Agent Card, an MCP server card, an Agentic Resource Discovery manifest, a publisher-curated LLM context file, an agent-memory, ontology, knowledge-graph or SPARQL endpoint, a runtime or architecture registry — so that any agentic-AI, knowledge, memory or ontology system that this node relates to can be reached from it, and so that new ones can be added without a change to this specification. Such links use IANA-registered relations only, chosen by meaning: describedby (the target describes this node), alternate (the same knowledge in another representation), related (a related resource), service-desc, service-doc and service-meta (an interface this node exposes or points at), collection and item (containment), and cite-as (RFC 8574: the target is preferred over this node for the purpose of permanent citation — a concept DOI's landing page, for instance, configured with type: "text/html") (cite-as is IANA-registered, so this list's registered-names-only condition admits it, and it lets a node that has deposited a release say which identifier to cite). Each MUST carry type and MAY carry profile (RFC 6906) and title. They are configured in agsc.config.json as related[]{rel, href, type, profile?, title?} (AGSC-01-18; rel from the list above, href absolute https:), emitted in href order within each relation (AGSC-06-10), and never derived from content. A reader MUST ignore a related-system link it does not understand; no related-system link affects conformance, any digest, the peer check or the walk (AGSC-11-10 follows rel#peer only), and none is ever required at any Level. An unregistered short name (ard, llm-context, …) MUST NOT be used until IANA registers it — a MINOR adds it then — and a relation not in the list above is AGSC-E209. [design]

6.3 llms.txt

  • AGSC-06-13 /llms.txt MUST begin with a single H1 (the Bundle title), then one blockquote summary, then the provenance header of AGSC-06-15 as an HTML comment, then H2 sections whose bodies are link lists - [title](url): one-line description. The file follows llms.txt v2 (modified 2026-08-10, read 2026-10-29) in its order — the H1, which is that convention's one required element, then the blockquote summary, then the link sections — so that a v2 parser reads the summary; the provenance comment is a block of detail without a heading between the summary and the first section, which v2 allows. No Optional H2 section is emitted at 1.x (AGSC-06-13a) (Amended 2026-10-02 for 1.0.0: the rule allowed one, and AGSC-06-13a forbids it). (Amended 2026-10-10 for 1.0.0: the file was described as following llms.txt v2 as a whole; it follows v2's H1 only, and the rule now says that a v2 parser reads no summary.) (Amended 2026-10-29 for 1.1.0: the provenance comment moves from before the summary to after it, so a v2 parser reads the summary again; the bytes of /llms.txt and /llms-full.txt change for every node, and disc-0013 and disc-0014 are withdrawn for disc-0024 and disc-0025) [design]
  • AGSC-06-13a Byte layout of /llms.txt and /llms-full.txt. The convention fixes no grammar, so this specification fixes one, and a vector proves it. Both files are UTF-8, NFC, LF-terminated, one trailing LF (AGSC-04-07), and consist of these blocks in this order, separated by exactly one blank line and by nothing else: (1) # followed by the Bundle title — first, as llms.txt v2 (modified 2026-08-10, read 2026-10-29) asks of its one required element, the leading H1, with the summary of block (2) straight after it, as v2 orders them (AGSC-06-13); (2) > followed by the Bundle description on a single line, newlines in the source replaced by a single space; (3) the provenance header of AGSC-06-15, as an HTML comment block whose lines are <!-- agsc:provenance, then bundle: <Bundle IRI>, license: <bundle.license_prose>, terms: <Content Use Terms identifier>, spec_version: <value>, bundle_version: <the content version of AGSC-04-25> (a line that a restricted node, AGSC-11-20, leaves out, because the content version is commit activity by another name; its header then runs from spec_version: straight to generated_at:), generated_at: <AGSC-04-10 instant>, assistance: <the AI-assistance statement of AGSC-06-15, a constant of this specification>, then -->; no value interpolated into this block may carry the two-character sequence -->, which would close the comment early — a writer MUST replace every occurrence of it with --&gt;, and lint reports the authored value as AGSC-E204 (Rationale: license: carries bundle.license_prose, an authored string, and an unneutralised --> would make a reader that strips comments stop stripping at the wrong point; the bundle_version: line lets an agent reading only this file say which version of the node's content it read.); (4) zero or more section blocks, each ## plus the cluster title, one blank line, then one link line per item whose primary cluster (the first of clusters[]) is that cluster — an item appears exactly once — ordered by slug: - [ title ]( absolute item IRI ): the item description, or the title again when the item has no description — in the title and in the description each backslash, [, ] and ( is preceded by one backslash, the backslash first, so that no authored character ends the link text or opens a link of its own, and no other character is escaped; (5) the ## Optional section is NOT emitted at 1.x (reserved). Section blocks are ordered by cluster slug; items with no cluster go in a final section titled Other; a type: cluster item has no link line of its own (its section is its entry) and a cluster with no primary member emits no section. A writer MUST NOT emit any other line. /llms-full.txt is identical through block (4), and then, for each item in the same order, one block of three parts with no blank line inside it — ## plus the item title, a line <!-- agsc:item <item IRI> -->, and the item body (ending in exactly one LF) fenced exactly as ```text agsc-content … ``` (AGSC-06-15). Retired and draft items appear in neither file (AGSC-06-30). Vectors disc-0024 and disc-0025. (Amended 2026-10-10 for 1.0.0: "No other line may appear" written as a prohibition with its key word) (Amended 2026-10-10 for 1.0.0: the layout was described as following llms.txt v2 as a whole; block (1) now says that it follows v2's H1 only.) (Amended 2026-10-29 for 1.1.0: blocks (2) and (3) change places so that the summary follows the H1; in a link line the backslash and [, ] and ( of a title or a description are escaped; a restricted node omits the bundle_version: line; disc-0013 and disc-0014 are withdrawn for disc-0024 and disc-0025) [PRD-060]
  • AGSC-06-14 Every listed item MUST be reachable from /llms.txt, directly or through a listed cluster section. A retired item is published and not listed (AGSC-00-05), so it is not in the index (AGSC-06-13a). /llms-full.txt carries the same index plus item bodies. (Amended 2026-10-10 for 1.0.0: the rule said "every published item", a set that includes the retired items AGSC-06-13a leaves out.) [PRD-025]
  • AGSC-06-15 Both files MUST carry, immediately after the blockquote summary that follows the H1, the fixed provenance header naming the Bundle IRI, the licence bundle.license_prose (whose default is LicenseRef-AgenticSystemCore-Content-Use-1.0, AGSC-01-18), the Content Use Terms identifier of AGSC-06-18, the content version of AGSC-04-25 (on a node that is not restricted, AGSC-11-20), the build instant and the AI-assistance statement — the constant line assistance: content may be AI-assisted; each item states its origin in prov.origin and each accepted contribution carries an Assisted-by: trailer, which is a constant of this specification and never authored (so that a reader of an agent-facing export can tell that the prose may be AI-assisted and where each item records it); AGSC-02-07 makes its first clause true; its second clause names the optional line of AGSC-08-07, which an accepted contribution carries when its contributor writes one, as the contributor agreement asks; it is kept verbatim at 1.x so that every 1.x node and checker agree on the bytes — in the byte layout of AGSC-06-13a, and MUST fence every quoted body as ```text agsc-content so prose is presented as data, not instruction. (Amended 2026-10-12 for 1.0.0: the rule said that AGSC-02-07 and AGSC-08-07 make the statement true; the line of AGSC-08-07 is optional, so the rule now says what each clause rests on, and that the constant is kept byte for byte at 1.x; rewording the constant is planned for 1.1 (AGSC-00-20). No emitted byte changes.) (Amended 2026-10-29 for 1.1.0: the header sits after the summary (AGSC-06-13a) and a restricted node leaves out the content version; the rewording of the statement that the 1.0 note planned for 1.1 is not made, the constant stays byte for byte, and the rewording is planned for a later MINOR (AGSC-00-20)) [NFR-07, ADR-001]

6.4 Machine surfaces and headers

  • AGSC-06-16 search.json MUST be a prebuilt inverted index {terms:{token:[docIndex…]}, docs:[{slug,title,description,cluster}]} requiring no runtime dependency. docs[] MUST be ordered by slug, each posting list MUST be ascending docIndex values without repetition, and the terms member names MUST be ordered as JSON member names per AGSC-04-05. Tokens are produced by AGSC-06-23 and by nothing else. An item with no clusters[] omits the cluster member, and an item with no description omits description; a member is never emitted as the empty string, so search.json stays a function of the authored keys — unless AGSC-06-21 applies, in which case this document is the manifest that rule defines. [PRD-014]
  • AGSC-06-23 Tokenizer (normative). For each item the tokenizer input is, in this order, title, description, every tags value and the body with fenced code blocks removed. The input MUST be NFC-normalized, then ASCII-lower-cased (only U+0041–U+005A are mapped; no locale casing, no case folding of non-ASCII), then split at every run of characters that are not token characters. A token character is [a-z0-9] or a character whose Unicode General_Category is L* (any letter), Nd (decimal digit) or M* (combining mark, so Devanagari and Thai words are not split); every other character — including No/Nl forms such as ² and Ⅷ, and Lo-adjacent symbols — is a boundary. Non-ASCII letters and digits are kept code-point-wise and never transliterated. The General_Category table is that of the Unicode version pinned by AGSC-04-22. That pin is 16.0.0; a port using another version MUST state it in its conformance claim, since that is the only remaining source of divergence. A token shorter than 2 Unicode code points MUST be dropped (AGSC-02-24). There is no stemming, no stop-word list, no synonym expansion and no n-gram: two conforming engines therefore emit byte-identical search.json. [PRD-014, NFR-04]
  • AGSC-06-17 _headers MUST set Content-Type: text/markdown; charset=utf-8; variant=GFM for /pages/*.md, Content-Type: application/linkset+json; profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge" for /.well-known/knowledge-linkset — or the header fallback of AGSC-06-07 — and a Content-Security-Policy that contains at least default-src 'none', script-src 'self', style-src 'self', img-src 'self' and connect-src 'self' — the least the required pages need: the stylesheet every page links, the images it shows, and the search index and the page tools' reads, all from the node itself — and admits no inline script; a writer MAY add directives that only restrict further (base-uri 'none', form-action 'none', frame-ancestors 'none' in the reference engine), and a case on the policy asserts that it contains these directives, never the whole string. (Amended 2026-10-02 for 1.0.0: until 1.0.0-rc.6 the rule named default-src 'none' with script-src 'self' alone, a policy under which the pages the same chapter requires could not load their stylesheet or their search index.) In _headers each address pattern MUST be written once, as one block that carries every header the address takes — its content type, the cross-origin pair of AGSC-11-03 and its Link and Cache-Control values — because the reference host serves only one of two blocks written for the same pattern, and a header set split over two blocks loses one of them; the Link values of AGSC-06-40 and the Cache-Control value of AGSC-06-06 are written into those blocks and into no second block, and the address /query/ and the files under it carry exactly one Content-Security-Policy (AGSC-06-39). (Amended 2026-10-06 for 1.0.0: the sentence was missing; the reference engine wrote the cross-origin pair and the content type of fourteen addresses in two blocks each, and the host served the discovery document and the other thirteen without Access-Control-Expose-Headers.) For a restricted node (AGSC-11-20 (b)) the block of every address other than the discovery document MUST leave the cross-origin pair of AGSC-11-03 out, and a profile for a host that adds Access-Control-Allow-Origin by default MUST say how the host's default is removed: on Cloudflare Pages a header that a more pervasive rule or the host sets is detached by a line that begins with an exclamation mark and a space before the header name, ! Access-Control-Allow-Origin (Cloudflare Pages documentation, "Headers", "Detach a header", last updated 25 August 2026, https://developers.cloudflare.com/pages/configuration/headers/, read 2026-10-29). _redirects SHOULD carry /.well-known/agentic-knowledge → 301 → /.well-known/knowledge-linkset, for a reader that still asks for the older name. agentic-knowledge is a legacy name: RFC 8615 §3 asks that a new well-known name be registered, and this specification will not request it, so it will not be registered, and a reader asks for knowledge-linkset. A writer MAY additionally emit, for each machine artefact of AGSC-06-01, a served Repr-Digest: sha-256=:<base64>: header whose value is the base64 of the same SHA-256 the discovery document carries as that link's digest (AGSC-06-08) — only on a response served without a content coding: under Content-Encoding the field is computed over the encoded bytes (RFC 9530 Appendix B.4), which a static header cannot follow, so a host that compresses MUST NOT send it from a static value. (Amended 2026-10-02 for 1.0.0: the restriction to uncoded responses was missing.) The field is RFC 9530's, a Structured Fields Dictionary whose value is a Byte Sequence (RFC 9651) and whose algorithm token is sha-256; a writer that emits it MUST derive it from the emitted bytes and never from a separate computation. It is a MAY and no Level requires it, so the required header set of this rule and the bytes build-0012 pins are unchanged. (Amended 2026-10-29 for 1.1.0: the Link and Cache-Control values of 1.1 join the one block of their address, and /query/ may extend the policy by one source; Content-Digest is sent for the export manifest only (AGSC-09-17), and Repr-Digest stays a MAY for responses without a content coding) (Rationale: a reader holding one fetched file can check it without a second fetch of the discovery document.) (Amended 2026-10-10 for 1.0.0: the redirect was a MUST bounded by a condition no one can test, which named a version line older than this one; that clause is removed, the redirect is a SHOULD, and the rule says that the legacy name will not be registered. The reference engine still writes the redirect, so no emitted byte changes.) (Amended 2026-10-29 for 1.1.0: a restricted node sends no wildcard origin on any address but the discovery document, AGSC-11-20 (b), and the way a header is detached on the reference host is stated) [PRD-020, RFC 7763, RFC 9530]
  • AGSC-06-18 One licence policy is expressed in exactly three machine-readable dialects at 1.x, and no more: the per-crawler User-agent/Disallow groups of robots.txt (RFC 9309); the TDMRep policy at /.well-known/tdmrep.json (the TDM Reservation Protocol well-known location, and the only route that carries it — the duplicate copy at /tdmrep.json is not emitted); and the schema:license/schema:usageInfo members of the JSON-LD views together with llms.txt. rsl.xml and the aipref Content-Usage field are not emitted at 1.x, and no rule, route or claim may assert them. A Content-Signal line in a robots.txt group — the reference engine writes one in every group — is an optional "other record" of RFC 9309 §2.2.4, which a crawler may interpret or ignore: it restates the same policy for the crawlers that read it, is not counted as a dialect and is compared with nothing. The three dialects express one policy at three levels of precision, and only what is comparable is compared: a TDMRep tdm-reservation of 1 MUST be accompanied by a robots.txt group User-agent: <token> with Disallow: / for every product token (RFC 9309 §2.2.1) of site.tdm_crawlers[] (AGSC-01-18), and by a schema:usageInfo naming the Content Use Terms; a disagreement on those three comparable facts — a token of the list with no such group, or a reservation with no such schema:usageInfo — MUST fail the build with AGSC-E202, and nothing else is compared. site.tdm_crawlers[] is the publisher's own, maintained list of the product tokens whose operators state that they collect content in order to train a machine-learning model; it is configuration and never a constant of this specification, because vendors rename tokens and add them and a list frozen into a standard goes stale where it matters most. A writer MUST emit one such group per token, in the order the configuration states them and before the User-agent: * group, and MUST NOT emit a Disallow for any token the list does not name — a fetch made on a person's behalf, and a search crawler, stay invited, which is what keeps a node readable by the agents it exists for. An empty site.tdm_crawlers[] on a node that publishes tdm-reservation: 1 is AGSC-E202 at build, because the Content Use Terms text this rule pins by hash tells the reader that the reservation is stated machine-readably by the TDM reservation file and the robots signals of this node: with no token named, those signals carry no reservation and the node's own prose is false. (Rationale: with no token named, the Disallow conjunct would be vacuously true, and the one machine-checkable link between the strongest dialect and the weakest could never fail.) robots.txt expresses crawler access, not licence: RFC 9309 defines only User-Agent, Allow and Disallow and says of them "These rules are not a form of access authorization" (read 2026-09-19). (Rationale: no rule defines a mapping between the three dialects, and RFC 9309 has no vocabulary in which a TDM reservation or a schema:license can be expressed at all, so only the comparable facts are compared.) The Content Use Terms identifier is the constant LicenseRef-AgenticSystemCore-Content-Use-1.0. The Content Use Terms accompany the prose only where the publisher adopts them — bundle.license_prose is that identifier, or is absent and defaults to it (AGSC-01-18) — and every prose-carrying export of such a node MUST embed the identifier; a build omitting it MUST fail with AGSC-E202. A Bundle whose prose carries another licence MUST NOT be presented under terms narrower than that licence: wherever this specification places the Content Use Terms identifier — the terms: line of AGSC-06-13a, the terms member of a chunk line (AGSC-06-26), a skill pack or a Harness (AGSC-07-16), schema:usageInfo (AGSC-05-26) — such a node places the value of bundle.license_prose; it publishes tdm-reservation: 0 and no crawler group, and its pages name its own licence and not the Content Use Terms. license and terms are two members with two meanings even when their strings coincide. (Rationale: the Content Use Terms reserve model training, and a licence that grants more may forbid adding restrictions to it.) The Content Use Terms text is shipped as LICENSE-CONTENT at the Bundle root (AGSC-01-26); a distribution without it is incomplete. The text the identifier names is the file LICENSE-CONTENT at the root of this specification's distribution, whose SHA-256 over its bytes is b2e8da62e6a41886296d2d2358fb4642cc7418e806eb4a29ada12b588ac32857 (2133 bytes). A distribution that ships different text MUST use a different identifier: the identifier names terms, not a file name, and reusing it over other wording would make every terms: line of AGSC-06-13a and every schema:usageInfo of AGSC-05-26 unverifiable. A reader MAY check the hash; nothing requires a node to publish it, because the terms are the same terms for every node that carries the identifier. A writer MUST emit /legal/ from that LICENSE-CONTENT file when the Bundle root carries one, and MUST NOT emit the Content Use Terms link on any page when it does not; /about/ remains authored and optional, and /changelog/ is derived from the git-log file and emitted when the build is given it (AGSC-06-01) (Amended 2026-10-02 for 1.0.0: /changelog/ was called authored and optional). The /legal/ page MUST also carry, each only where the Bundle supplies its input: the publisher's privacy notice and retention statement, from an authored PRIVACY.md in the Bundle root, rendered unchanged; an identification of the operator, derived from site.author and bundle.operator (AGSC-01-18, AGSC-01-25); and the AI-assistance statement of AGSC-06-15, in the same words the provenance header of every agent-facing export carries. A writer MUST NOT invent any of them — a privacy notice that is not the publisher's own words is worse than none — and an absent input omits that section and is the warning AGSC-E406, naming what is missing. (Rationale: PRD-019 asks this page for the Content Use Terms, a privacy notice, the operator and a retention statement.) A second identifier, LicenseRef-AgenticSystemCore-Content-Use-1.1, is RESERVED for a revised text of the Content Use Terms: it names no text until a later amendment of this rule pins one by SHA-256 and byte length, as this rule does for the 1.0 text; until then no distribution MAY ship a LICENSE-CONTENT under it and no node MAY set bundle.license_prose to it. When it is pinned it is opt-in through bundle.license_prose alone, the default stays the identifier above, a node that does not choose it keeps its bytes, and an item published under the 1.0 terms keeps them. The resolvable licence URL that chunks, the Link header of / and the Dataset block carry is defined once, in AGSC-06-44. (Amended 2026-10-29 for 1.1.0: the second identifier is reserved and its text is not yet published; no emitted byte changes) (Amended 2026-10-10 for 1.0.0: robots.txt was credited with signals about the use of content by AI that RFC 9309 does not define; the Content-Signal line every reference robots.txt carries was named nowhere; and the two build failures named no code.) [PRD-019]
