AGSC-06 — Published surfaces: routes, discovery files, llms.txt

SummaryEverything a node publishes: the fixed route set, the discovery document, llms.txt, the chunk export, the JSON-LD context, headers and budgets.

Status of this document

Specification 1.0.0-rc.7, a release candidate tagged on 2026-10-08. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

Part 1 of 2, 6.1 to 6.3. This section is published in two parts so that each page stays within the budget of AGSC-06-21; a rule's link names the part that carries it. Part 2 carries 6.4 to 6.8.

In plain language

Routes. A writer emits a fixed set of pages and files — item pages, clusters, tags, search, NOW, compose, skills, specs, the graph files, llms.txt, sitemap, robots, the ledger, the chunk export, the context file, boards when tasks exist — and nothing else.

The discovery file. /.well-known/knowledge-linkset is an RFC 9264 link set: one document that points at every machine artefact with its SHA-256 digest, the spec version, counts, the ledger head, peers, surfaces and contribution targets. Pages point at it with the standard describedby relation; the Internet-Draft asks for the well-known name, which is not registered, and the profile identifier is registered in the IANA Profile URIs registry. The file can also carry optional links to related systems — an llms.txt file, an agent card, a server card, a memory or ontology endpoint — using standard relations only.

llms.txt. The agent-facing text file has a fixed byte layout — a provenance header, the title, the description, one section per cluster with one line per item — so two tools produce the same file.

The chunk export. /chunks.jsonl is the Bundle pre-split for agents: one line per chunk, cut at headings outside code fences and at a size bound, with a stable id, the text, provenance, licence and terms, and a digest. No embeddings.

Headers. No third-party scripts, no beacons; strict security headers; public artefacts readable cross-origin.

This box explains; the rules below decide. New to the notation? See how to read the specification.

6.1 Route set

  • AGSC-06-01 A writer MUST emit exactly this route set into build.out (default www/) — the routes listed here together with the conditional routes the third paragraph below names, the conformance report, the agent card and the VoID description among them (amended 2026-10-02 for 1.0.0: those three were named only among the conditional routes, against "exactly this route set") — /; /concepts/ and /concepts/<slug>/, plus /<type-plural>/<slug>/<lang>/ for every language variant (AGSC-01-13, reserved to 1.1 — none at 1.0); /procedures/, /lessons/, /episodes/, /gates/ with their item pages; /clusters/ and /clusters/<slug>/; /tags/<tag>/; /search/ with /search.json, plus /search-<nn>.json shards and /<route>/page-<n>/ index pages above the bounds of AGSC-06-21; /now/ and /now.md; /compose/; /skills/, /skills/index.json, /skills/<cluster>/SKILL.md; /specs/, /specs/agentic-knowledge/ and /specs/mcp/ — on the namespace document site only, which is what the w3id rules of AGSC-06-06 resolve to; a content node does not emit them and links the specification there (amended 2026-10-02 for 1.0.0: these routes stood in this list as if every node emitted them, and again below as the namespace site's only) — (the published specification of the AGSC-06-07 profile URI, the 303 target of the w3id profile/agentic-knowledge rule, which MUST carry an anchor #link-relations and one anchor named exactly as the fragment of the relation URI — #graph, #ontology, #context, #now, #skills, #ledger, #peer, #surface, #contribute, #access, #signature, #boards — per AGSC-06-10 extension relation, so that a client that does follow an extension relation URI lands on that relation's documentation; RFC 8288 §2.1.2 permits that but discourages it, saying "clients SHOULD NOT automatically access that resource to avoid overburdening its server"); /ns/context.jsonld and /ns/<ontology-version>/context.jsonld (AGSC-06-32, AGSC-05-09), which are the only /ns/ routes a content node emits — the vocabulary documents /ns/agsc.ttl, /ns/agsc.rdf and the /ns/ HTML index, and the three JSON Schemas at their $id URLs /ns/schema/{bundle,config,item}.schema.json (so that each $id resolves), are published by the namespace document site alone, which is what the w3id negotiation of AGSC-06-06 resolves to; /about/; /legal/; /changelog/; /graph.jsonld, /graph.ttl and /graph.nq; /pages/<slug>.md and /pages/<slug>.jsonld; /attachments/<slug>/<file> for every attachment an item names (AGSC-02-98; the served bytes are the hashed bytes of AGSC-05-29); /assets/<path> for every file under content/assets/ that a published item's body references (AGSC-03-11), <path> being that file's path relative to content/assets/ and the served bytes being the authored file's bytes (AGSC-03-11 admits a body image or link into content/assets/ and AGSC-02-95 creates such files during adoption, byte for byte; this route is what such a reference resolves to.); /llms.txt and /llms-full.txt; /sitemap.xml; /robots.txt; /.well-known/tdmrep.json; /ledger.jsonl; /chunks.jsonl and its /chunks-<nn>.jsonl shards (AGSC-06-26/31); /boards/index.json, /boards/<cluster-slug>.json and /boards/<cluster-slug>/ (the human view of the same board) when the Bundle holds at least one task item (AGSC-10-13); optionally /graph/fragments/** with /graph/fragments/index.json (AGSC-06-33); /.well-known/knowledge-linkset; /.well-known/security.txt; /404.html; and, for the Cloudflare Pages deployment profile, _headers and _redirects (AGSC-06-17).

    A writer targeting another host MUST emit the equivalent configuration for that host and MUST state which deployment profile it emitted in its conformance claim (AGSC-09-01); the normative content is the header set of AGSC-06-17, AGSC-11-03 and AGSC-11-05 and the redirect of AGSC-06-17, never the file format. This route set bounds what a writer MUST emit; it is not a bound on every file that may sit in the deployed directory, and the same-origin script assets a page of this set loads — /compose/ and every item page load them so that the page tools of AGSC-09-16 can be registered, and AGSC-06-17's script-src 'self' policy leaves a writer no inline alternative — are emitted as part of the page that names them and are not routes of their own. The same holds for the two presentation files every page of this set links, the stylesheet /assets/site.css and the theme-control script /assets/theme.js of AGSC-06-05: a Bundle that authors content/assets/site.css replaces the default stylesheet at that path whether or not a body references it, and /assets/theme.js is always the writer's own, and so is the one script the /search/ page loads to search /search.json in the page, /search/agsc-search.js, which MUST tokenize a query exactly as AGSC-06-23 tokenizes an item — a writer that ships that page MUST emit the script as part of it. (Rationale: _headers and _redirects are Cloudflare Pages configuration files whose grammar no rule pins, and holding a Level-2 writer on nginx, Apache, S3 + CloudFront or a Solid pod to them would make every Level-2 claim implicitly Cloudflare-shaped.)

    /ledger.jsonl is the derived ledger of §08, published so that a reader can recompute the chain offline (AGSC-08-23) and so that the rel#ledger link of AGSC-06-10 has a target. /search/ and /search.json are unconditional (AGSC-06-16 MUSTs the index). The conditional routes are the shards and index pages of AGSC-06-21/06-31 (by size), /boards/** (by the presence of a task), /.well-known/agent-card.json (only under AGSC-06-34), /legal/ (only when the Bundle root carries a LICENSE-CONTENT file, AGSC-06-18), /conformance/ (only when a claimant publishes the report AGSC-09-03 defines, which is a MAY), /.well-known/void (only when a publisher emits a VoID description independently, AGSC-06-12, which is a SHOULD-link and never an emission of this specification), /.well-known/security.txt (only when the Bundle root carries an authored .well-known/security.txt that states a Contact: field — AGSC-06-36), /assets/<path> (one route per authored asset file a published body references), /specs/, /specs/agentic-knowledge/ and /specs/mcp/ (only on the namespace document site, above), /about/ (only when the Bundle authors that page; its source and bytes are implementation-defined at 1.x), /changelog/ and /ledger.jsonl (only when the build is given the git-log file of AGSC-08-20b; a Level-2 claim requires both, AGSC-10-04) and the optional /graph/fragments/** (AGSC-06-33); no other route is conditional. /graph.rdf and /feed.xml are not emitted at 1.x, and build.rdfxml and build.feed are reserved names rejected with AGSC-E004 (feed is reserved because no 1.0 rule pins a feed's bytes, so the route cannot be derived and the switch has nothing to switch on).

    SECURITY.md, CODE_OF_CONDUCT.md, CITATION.cff, CONTRIBUTING.md, GOVERNANCE.md, CONTRIBUTOR-AGREEMENT (AGSC-08-06) and the REUSE layout are repository files, not routes (PRD-047); only security.txt is published, at its RFC 9116 location above, and what it carries is AGSC-06-36's. [PRD-011]

[PRD-018, PRD-020]

It MUST write the key only when the visitor chooses a theme and remove it when the visitor chooses the system theme, MUST NOT read, write or send any other stored value, and every page MUST render and work when storage is empty or unavailable; the privacy section of /legal/ (AGSC-06-18), where the node publishes one, SHOULD say that the choice is kept in the browser, is never sent, and is cleared with the site's data. 6.2 The well-known file

  • AGSC-06-07 There MUST be exactly one discovery file, /.well-known/knowledge-linkset at the root of the node's origin — at 1.0 a node occupies a whole origin (AGSC-01-19) — served as application/linkset+json carrying the RFC 9264 §5 profile parameter profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge". Where the hosting platform cannot carry a parameter on Content-Type, the node MUST instead send the response header Link: <https://w3id.org/agentic-system-core/profile/agentic-knowledge>; rel="profile" (RFC 6906); at least one of the two MUST be present, and a reader MUST accept either. No vendor media type is defined, registered or served. Separate manifests MUST NOT be emitted; a release MAY carry a copy named knowledge-linkset.json. agent-card.json MUST NOT be published unless the node declares it as the a2a-card surface and declares a responder surface it points at (AGSC-06-34, AGSC-11-16); a card without an endpoint is AGSC-E210. The well-known suffix knowledge-linkset is not registered: its registration under RFC 8615 is asked for in the Internet-Draft draft-besleaga-agentic-knowledge-wellknown, which is posted, and no request has been sent to the registry; the Profile URI is registered in the IANA Profile URIs registry under RFC 7284 (First Come First Served) (amended 2026-10-02 for 1.0.0: "pending registration" said more than was true); the discovery link uses the already-registered relation describedby (AGSC-06-25), so no relation is requested. Until the suffix is granted, a node MAY additionally serve the same document at a path it controls, linked with describedby and the linkset media type — nothing in this specification says "registered" of the suffix before the registry does (Amended 2026-10-07 for 1.0.0: IANA has registered the Profile URI in the Profile URIs registry (RFC 7284). This rule said that its registration was "to be requested" and that nothing here says "registered" of the profile before the registry does; the registry now does. The well-known suffix is unchanged: not registered, and no request has been sent to the registry.). The suffix is a single point of substitution: the reference implementation holds it as one constant (WELLKNOWN_SUFFIX) from which the peers[] schema pattern, the _redirects alias of AGSC-06-17, the vector paths and the rule texts derive, so a refused registration substitutes the next candidate suffix by one MINOR and a regeneration: the new suffix is added and the present path keeps answering with a redirect to it, so no reader that knows only the present path breaks (AGSC-00-14) (amended 2026-10-02 for 1.0.0: until 1.0.0-rc.6 this said "by one PATCH", but a new discovery address is an addition, which a MINOR makes). The profile URI carries no version: it names the same profile for every version of this specification with the same MAJOR, a discovery document states the version it follows in agsc-spec-version (AGSC-06-08), and a new MAJOR that changes what the profile fixes takes a new profile URI. [PRD-024, RFC 9264, RFC 9727 §7.3, RFC 6906]

  • AGSC-06-08 The document is a JSON object — JCS-canonical at Level ≥2 (AGSC-04-04), valid I-JSON at Level 0 (AGSC-06-08a, AGSC-10-02) — whose sole top-level member is linkset (RFC 9264 §4.2.1); no other top-level member may be present; the linkset array holds exactly one link context object whose anchor is the Bundle IRI (AGSC-05-03), its relation-name members ordered as JSON member names (AGSC-04-05). The anchor is on the origin of the document. A reader MUST treat a document whose anchor is not on the origin of the URL it finally retrieved the document from, after redirects, as not being that node's discovery document (RFC 9264 §9, RFC 8615 §4.3): a validator reports AGSC-E907, and a federation walk and the mutual check of AGSC-10-12 skip it as unreadable; a document read from a file has no such origin and is not judged by this sentence. (Amended 2026-10-02 for 1.0.0: a copy of one node's document served by any other origin passed every check, and a reader would have attributed it to that node.) Integrity and bundle facts ride on the links as extension target attributes (RFC 9264 §4.2.4.3), whose values are ALWAYS arrays of strings. Every artefact link — a link whose row in the table below says yes under digest — MUST carry digest at Level 2 and above (AGSC-06-08a), a Dictionary with a single member whose key is the RFC 9530 algorithm name sha-256 and whose value is an RFC 9651 §3.3.5 Byte Sequence, serialised per RFC 9651 §4.1 as sha-256=:<base64>: and carried as one string in the attribute's array, over the canonical bytes of the target. Bundle-level facts ride on the anchor's describedby link to graph.jsonld and nowhere else: agsc-spec-version (one value), agsc-generated-at (one value, an AGSC-04-10 instant derived from SOURCE_DATE_EPOCH), agsc-counts (one "<type-plural>=<n>" string per item type, in code-point order of the type name, counted over the published set — release-gated, draft and retired items excluded, AGSC-06-30), agsc-bundle-hash (the AGSC-04 bundle hash, RFC 9530 syntax), and agsc-bundle-version (one value, the content version of AGSC-04-25: the hash says whether two nodes hold the same content and never what the publisher calls that content, so a reader that wants to cite or compare releases needs both). The ledger is the link https://w3id.org/agentic-system-core/rel#ledger, carrying digest and agsc-ledger-head (one value, the lowercase hex head of the derived ledger of §08). A node MAY carry one further link whose relation is https://w3id.org/agentic-system-core/rel#signature (AGSC-06-10) and whose target is a detached signature over the canonical bytes of this document. At 1.x no rule pins the signature format, no Level requires the link, it affects no digest, no claim and no walk, and a reader MUST ignore it if present. (Non-normative: the digests of this rule establish that the bytes are the bytes the publisher hashed; they establish nothing about who the publisher is. The trust anchor at 1.x is the origin's TLS certificate and DNS name, and a publisher who needs more publishes the optional signature. The nearest comparator, the Agent2Agent Agent Card, makes a signature over its canonical card optional ("Agent Cards MAY be digitally signed", A2A §8.4, read 2026-09-16 and quoted in docs/SECURITY-CONSIDERATIONS.md §2); this specification keeps its own optional for the same reason and one more — a static node has no key custody — and the reasoning is written here rather than left to inference. No IANA-registered relation exists for a signature — the registry was read on 2026-09-23 and holds none — so the link can only take this specification's own extension-URI form, and AGSC-06-35's registered-names-only list cannot admit it.) [PRD-024, RFC 9264, RFC 9530, RFC 9651] (Amended 2026-10-02 for 1.0.0: the table below names every link the document carries, when, and which of them carry digest; until then "artefact link" was not defined.)

  • AGSC-06-08a At Level 0 (AGSC-10-02) the document is the same link set with every digest and every agsc-* attribute of AGSC-06-08 (agsc-spec-version, agsc-generated-at, agsc-counts, agsc-bundle-hash, agsc-bundle-version and agsc-ledger-head) omitted — the §11 attributes (agsc-surface, agsc-surface-version, agsc-access, agsc-visibility, agsc-contribute-mode, agsc-tombstone) are Level-independent — a CMS export has no ledger, no graph.nq and no build instant, and Level 0 does not ask for one. At Level 2 and above every digest REQUIRED by AGSC-06-08, and every agsc-* attribute on the describedby and rel#ledger links, MUST be present. There is no structural difference between the two: linkset is the sole member at every Level. [PRD-055]
  • AGSC-06-09 The linkset member MUST conform to RFC 9264: an array of link-context objects, each with anchor and relation-keyed arrays of objects carrying href and optionally type. A consumer that cannot obtain the discovery document at the well-known URL of AGSC-06-07 SHOULD try, in order, the home page's describedby link whose type is application/linkset+json (AGSC-06-25) — which names the copy a node MAY serve at a path it controls (AGSC-06-07) — and then /llms.txt (AGSC-06-13). This order is informative: a node is not obliged to be reachable by more than the well-known URL, and a reader that finds none of them reports AGSC-E901. (Rationale: the well-known name is one door among several, and a consumer meeting a 404 needs a second door.) [PRD-024, RFC 9264]
  • AGSC-06-10 Relation names MUST be either IANA-registered short names — the five this specification itself emits (describedby, alternate, license, service-doc, author) plus any relation AGSC-06-35 admits for a related-system link (related, service-desc, service-meta, collection, item and cite-as) — or extension URIs of the form https://w3id.org/agentic-system-core/rel#<name> with <name> ∈ graph, ontology, context, now, skills, ledger, peer, surface, contribute, access, signature and boards — of the first six, five have a route in AGSC-06-01 and ontology names the vocabulary document of the namespace document site (AGSC-06-06), which a content node does not serve: a node that does not serve it omits the link, and a node that does names its own copy; peer naming another node's well-known URL for the mutual-conformance test of AGSC-10-12; surface, contribute and access defined in AGSC-11-16, AGSC-11-14 and AGSC-11-20, whose targets are surfaces, contribution endpoints and credential pages and need not be routes of this node; signature defined in AGSC-06-08, whose target is a detached signature and need not be a route of this node (the IANA link-relation registry holds no relation for a signature, so this specification's own extension form is the only one available); boards defined in AGSC-10-13, whose target is /boards/index.json. shapes is NOT a 1.x relation: SHACL shapes stay in the development lane (AGSC-05-24), so no /ns/shapes.ttl is published and a relation with no target would be a dangling promise. Unregistered short names MUST NOT be used. Extension target attributes (RFC 9264 §4.2.4.3) MUST use the prefix agsc- (agsc-spec-version, agsc-generated-at, agsc-counts, agsc-bundle-hash, agsc-bundle-version, agsc-ledger-head; and the six attributes of the boundary rules that AGSC-06-08a lists) (amended 2026-10-02 for 1.0.0: the list did not point to the boundary rules' six) so that they can never collide with the target attributes RFC 8288 §3.4 defines (hreflang, media, title, title*, type) or with those RFC 9264 §4.2.4 serialises — no registry of target attributes exists; digest is deliberately unprefixed: RFC 9530 supplies its algorithm token and RFC 9651 its value syntax, and the plain name keeps a generic link-set reader that knows RFC 9530 syntax able to read it (amended 2026-10-02 for 1.0.0: the rule said "RFC 9727-style" consumers, and RFC 9727 says nothing of digests). Every extension target attribute value — digest, every agsc-* attribute, and profile where a related-system link carries it (AGSC-06-35) — is an array of strings (RFC 9264 §4.2.4.3); type, title and media are strings and hreflang is an array of strings (RFC 9264 §4.2.4.1). Within one relation's array, link objects are ordered by href (code point), and every href is absolute — the Bundle base plus the route. type values are advisory hints (RFC 9264 §4.2.4.1, "Target Attributes Defined by Web Linking", is where the type member is specified; RFC 8288 §3.4.1 is where the hint language is — "this is only a hint; for example, it does not override the Content-Type header field of a HTTP response obtained by actually following the link"); application/jsonl is used for /ledger.jsonl and is deliberately unregistered — a reader MUST NOT depend on it. [RFC 9264, RFC 8288, RFC 9530]
  • AGSC-06-11 digest values are defined once, in AGSC-06-08; agsc-ledger-head MUST be the lowercase hex hash of the last entry of the derived ledger of §08 — the head that verify --ledger recomputes and compares. A ledger always has at least the trailing build entry (AGSC-08-20a), so the head is never undefined where the attribute is required; a Level-0 node publishes no rel#ledger link and therefore no head (AGSC-06-08a). agsc-generated-at MUST derive from SOURCE_DATE_EPOCH. [PRD-005, PRD-024]
  • AGSC-06-12 VoID (/.well-known/void, registered 2011) is prior art for dataset discovery and is cited as complementary wherever this specification describes its discovery layer (an editorial commitment, not a conformance requirement). This specification emits no VoID description: graph.jsonld on the describedby link already carries the bundle-level facts (AGSC-06-08), AGSC-06-01's route set is closed, and a SHOULD-emit with no route would be unimplementable. A node that publishes a VoID description independently SHOULD link it from the link set as a second describedby link (AGSC-06-09 admits several; AGSC-06-08's "nowhere else" binds the agsc-* bundle-facts attributes to the graph.jsonld link, not the number of describedby targets). [design]
  • AGSC-06-35 Related-system links, OPTIONAL and extensible. The discovery document MAY carry, in its one link context, links to related discovery documents and systems — an llms.txt v2 file, a VoID or DCAT description, an OKF index, an Agent2Agent Agent Card, an MCP server card, an Agentic Resource Discovery manifest, a publisher-curated LLM context file, an agent-memory, ontology, knowledge-graph or SPARQL endpoint, a runtime or architecture registry — so that any agentic-AI, knowledge, memory or ontology system that this node relates to can be reached from it, and so that new ones can be added without a change to this specification. Such links use IANA-registered relations only, chosen by meaning: describedby (the target describes this node), alternate (the same knowledge in another representation), related (a related resource), service-desc, service-doc and service-meta (an interface this node exposes or points at), collection and item (containment), and cite-as (RFC 8574: the target is preferred over this node for the purpose of permanent citation — a concept DOI's landing page, for instance, configured with type: "text/html") (cite-as is IANA-registered, so this list's registered-names-only condition admits it, and it lets a node that has deposited a release say which identifier to cite). Each MUST carry type and MAY carry profile (RFC 6906) and title. They are configured in agsc.config.json as related[]{rel, href, type, profile?, title?} (AGSC-01-18; rel from the list above, href absolute https:), emitted in href order within each relation (AGSC-06-10), and never derived from content. A reader MUST ignore a related-system link it does not understand; no related-system link affects conformance, any digest, the peer check or the walk (AGSC-11-10 follows rel#peer only), and none is ever required at any Level. An unregistered short name (ard, llm-context, …) MUST NOT be used until IANA registers it — a MINOR adds it then — and a relation not in the list above is AGSC-E209. [design]

6.3 llms.txt

  • AGSC-06-13 /llms.txt MUST begin with a single H1 (the Bundle title), then the provenance header of AGSC-06-15 as an HTML comment — a profile of llms.txt v2 — followed by one blockquote summary, then H2 sections whose bodies are link lists - [title](url): one-line description. No Optional H2 section is emitted at 1.x (AGSC-06-13a) (amended 2026-10-02 for 1.0.0: the rule allowed one, and AGSC-06-13a forbids it). [design]
  • AGSC-06-13a Byte layout of /llms.txt and /llms-full.txt. The convention fixes no grammar, so this specification fixes one, and a vector proves it. Both files are UTF-8, NFC, LF-terminated, one trailing LF (AGSC-04-07), and consist of these blocks in this order, separated by exactly one blank line and by nothing else: (1) # followed by the Bundle title — first, so the file is a profile of llms.txt v2 (2026-08-10), whose only required element is the leading H1; (2) the provenance header of AGSC-06-15, as an HTML comment block whose lines are <!-- agsc:provenance, then bundle: <Bundle IRI>, license: <bundle.license_prose>, terms: <Content Use Terms identifier>, spec_version: <value>, bundle_version: <the content version of AGSC-04-25>, generated_at: <AGSC-04-10 instant>, assistance: <the AI-assistance statement of AGSC-06-15, a constant of this specification>, then -->; no value interpolated into this block may carry the two-character sequence -->, which would close the comment early — a writer MUST replace every occurrence of it with --&gt;, and lint reports the authored value as AGSC-E204 (Rationale: license: carries bundle.license_prose, an authored string, and an unneutralised --> would make a reader that strips comments stop stripping at the wrong point; the bundle_version: line lets an agent reading only this file say which version of the node's content it read.); (3) > followed by the Bundle description on a single line, newlines in the source replaced by a single space; (4) zero or more section blocks, each ## plus the cluster title, one blank line, then one link line per item whose primary cluster (the first of clusters[]) is that cluster — an item appears exactly once — ordered by slug: - [ title ]( absolute item IRI ): the item description, or the title again when the item has no description; (5) the ## Optional section is NOT emitted at 1.x (reserved). Section blocks are ordered by cluster slug; items with no cluster go in a final section titled Other; a type: cluster item has no link line of its own (its section is its entry) and a cluster with no primary member emits no section. No other line may appear. /llms-full.txt is identical through block (4), and then, for each item in the same order, one block of three parts with no blank line inside it — ## plus the item title, a line <!-- agsc:item <item IRI> -->, and the item body (ending in exactly one LF) fenced exactly as ```text agsc-content … ``` (AGSC-06-15). Retired and draft items appear in neither file (AGSC-06-30). Vectors disc-0013 and disc-0014. [PRD-060]
  • AGSC-06-14 Every published item MUST be reachable from /llms.txt, directly or through a listed cluster section. /llms-full.txt carries the same index plus item bodies. [PRD-025]
  • AGSC-06-15 Both files MUST carry, immediately after the H1, the fixed provenance header naming the Bundle IRI, the licence bundle.license_prose (whose default is LicenseRef-AgenticSystemCore-Content-Use-1.0, AGSC-01-18), the Content Use Terms identifier of AGSC-06-18, the content version of AGSC-04-25, the build instant and the AI-assistance statement — the constant line assistance: content may be AI-assisted; each item states its origin in prov.origin and each accepted contribution carries an Assisted-by: trailer, which is a constant of this specification and never authored, and which AGSC-02-07 and AGSC-08-07 are the rules that make true (so that a reader of an agent-facing export can tell that the prose may be AI-assisted and where each item records it) — in the byte layout of AGSC-06-13a, and MUST fence every quoted body as ```text agsc-content so prose is presented as data, not instruction. [NFR-07, ADR-001]
