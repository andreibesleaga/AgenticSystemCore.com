AGSC-06 — Published surfaces: routes, discovery files, llms.txt

SummaryEverything a node publishes: the fixed route set, the discovery document, llms.txt, the chunk export, the JSON-LD context, headers and budgets.

Status of this document

Specification 1.1.0, released and tagged on 2026-11-13. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

Part 2 of 2, 6.4 (continued) to 6.10. This section is published in two parts so that each page stays within the budget of AGSC-06-21; a rule's link names the part that carries it. Part 1 carries 6.1 to 6.4.

In plain language

Routes. A writer emits a fixed set of pages and files — item pages, clusters, tags, search, NOW, compose, skills, specs, the graph files, llms.txt, sitemap, robots, the ledger, the chunk export, the context file, boards when tasks exist — and nothing else.

The discovery file. /.well-known/knowledge-linkset is an RFC 9264 link set: one document that points at every machine artefact with its SHA-256 digest, the spec version, counts, the ledger head, peers, surfaces and contribution targets. Pages point at it with the standard describedby relation; the Internet-Draft asks for the well-known name, which is not registered, and the profile identifier is registered in the IANA Profile URIs registry. The file can also carry optional links to related systems — an llms.txt file, an agent card, a server card, a memory or ontology endpoint — using standard relations only.

llms.txt. The agent-facing text file has a fixed byte layout — a provenance header, the title, the description, one section per cluster with one line per item — so two tools produce the same file.

From 1.1, llms.txt follows v2 of the convention, and every page points at it. The title comes first and the description straight after it, so a reader of llms.txt v2 finds the summary; the provenance header follows them, and a [, ], ( or backslash in a title or description is escaped. Every page names /llms.txt in its head with the relation describedby and the type text/plain, beside the discovery file, and an item page names its Markdown copy /pages/<slug>.md with the relation alternate and the type text/markdown (AGSC-06-13a, AGSC-06-46).

The chunk export. /chunks.jsonl is the Bundle pre-split for agents: one line per chunk, cut at headings outside code fences and at a size bound, with a stable id, the text, provenance, licence and terms, and a digest. No embeddings.

From 1.1, the chunks can be checked as a set. Each chunk line also carries the item's own description (abstract) and a licence address that resolves (license_url); no chunk text begins with a blank line. The discovery document states the digest of /chunks.jsonl, the number of lines and one hash over all their ids, so a reader finds a line that was dropped or added. A node with at most 500 items also serves /chunks-index.toon, a compact table of the lines (AGSC-06-29, AGSC-06-37, AGSC-06-44, AGSC-06-45).

From 1.1, the graph is on the page. An item page shows its typed Links in both directions, the links back to it included, as a small figure and a table that says what each relation means; a cluster page maps its members; /clusters/ adds an overview of the links between clusters, a legend and an explorer that works from the keyboard. Where a node uses the domain layer, an item page also shows its domain type, role, warrant and domain links. Only published items are drawn.

From 1.1, /query/ answers questions in SPARQL. The page runs a query over the node's own graph in the browser, with the ten questions of the graph as examples, and offers the result as CSV or JSON; it calls no server and stores nothing. site.query_page: false leaves it out.

Headers. No third-party scripts, no beacons; strict security headers; public artefacts readable cross-origin.

This box explains; the rules below decide. New to the notation? See how to read the specification.

6.4 Machine surfaces and headers (continued)

  • AGSC-06-19 sitemap.xml MUST list every published route with lastmod from the build instant, ordered by URL. A published route is every route of AGSC-06-01 that the build emits as an HTML page — the home page, every item page, every index page (/<type-plural>/, /clusters/, /clusters/<slug>/, /tags/<tag>/, /<route>/page-<n>/), /now/, /compose/, /search/, /query/ where it is emitted (AGSC-06-39), /skills/ and, where the build emits them, /about/, /legal/, /changelog/, /conformance/, /boards/<cluster-slug>/ and /specs/** — and never /404.html or a machine file. Schema.org JSON-LD (TechArticle, DefinedTerm, Dataset) MUST be embedded in item and index pages. (Amended 2026-10-29 for 1.1.0: /query/ joins the published routes when AGSC-06-39 emits it, and /sitemap.xml gains its entry) [PRD-020]
  • AGSC-06-20 Generated HTML MUST meet WCAG 2.2 AA — semantics, keyboard operability, contrast, and alt text from the diagram's alt key. (Amended 2026-11-11 for 1.1.0: noted, not changed: the cluster page of 1.0 writes <h2 id="members">Members</h2>, and a body heading ## Members receives the same anchor, so that the id repeats on such a page. HTML pages are not byte-pinned (AGSC-04-24), but a fix would change the cluster page of every node, so it stays as it is in 1.1.) [NFR-08]
  • AGSC-06-21 Budgets are normative and MUST fail the build when exceeded: ≤100 KB per HTML page; ≤1 MB per index document — /search.json at or below 500 items, and each /search-<nn>.json shard above it, every shard carrying the docs of at most 500 items (AGSC-06-31 already describes this rule's sharding that way); ≤60 s build per 500 items, which is advisory from 1.1: no build measures time (AGSC-04-03), so no tool can fail a build on it, and a conforming build is never refused for being slow (external page requests are already impossible under AGSC-06-05). KB and MB are the decimal prefixes — 1,000 and 1,000,000 UTF-8 bytes of the emitted document — and AGSC-01-16 writes MiB where it means the binary prefix. (Rationale: AGSC-06-23 puts each item's body into the index, so the index costs what the prose costs, and per-item bytes fall as a Bundle grows, because the vocabulary amortises, and rise with body length; the budget is therefore stated once, on the artefact a reader actually downloads. At a full 500-item shard this bound is 2 KB of index per published item; how much one item can contribute to a page is already bounded by the 100 KB page budget of this rule.) Above 500 items a writer MUST shard the index as /search-<nn>.json (<nn> zero-padded from 01, in slug order) with /search.json as the manifest {shards:[…], docs_total} (and /chunks.jsonl sharded on the same trigger and in the same shape, AGSC-06-31), and MUST paginate any index route carrying more than 500 entries as /<route>/page-<n>/ (<n> from 2; page 1 is the route itself). The index routes are exactly these and no others: /; each /<type-plural>/ — /concepts/, /procedures/, /lessons/, /episodes/, /gates/, /clusters/; each /tags/<tag>/; and /search/. An item page, /now/, /compose/, /about/, /legal/, /changelog/, /specs/**, /ns/** and /skills/** are not index routes and are never paginated. A cluster's item page therefore lists at most 500 of its members, in the published order; above that it states how many members there are and says where the full list is — the search index and the graph, in which every member names the cluster (Amended 2026-10-02 for 1.0.0: the bound the reference writer applies was not stated). Each /search-<nn>.json shard is a complete AGSC-06-16 index over the items of its own slice: its docs[] is the contiguous run of the slug order that the shard carries, and its posting values are indices into its own docs[], counted from zero. A reader reconstructs the whole index by concatenating the shards' docs[] in manifest order and adding, to every posting of a shard, the number of documents the earlier shards carry. A reader that cannot obtain every shard the manifest names MUST report AGSC-E901 rather than answer over the part it holds. (Rationale: the other reading of a shard's docIndex answers wrongly and silently on every shard but the first.) The budgets are therefore per-scale, not absolute, and a 5,000-item Bundle conforms: it publishes ten index shards, each under the bound. Exceeding a budget that no sharding rule relieves MUST fail the build, with AGSC-E904 (the code of the size caps of AGSC-01-16 and AGSC-01-34). (Amended 2026-10-29 for 1.1.0: the build-time budget cannot be checked by a deterministic build and is advisory, as AGSC-04-03 says; the size budgets stay normative) [NFR-06]
  • AGSC-06-22 /now/ and /now.md MUST be generated from stored state only — counts, last build, stale items, open Lessons, monthly spend — never hand-edited. A section whose input is absent MUST be omitted, not guessed. Both MUST carry, as one line and its own paragraph, content version <bundle_version>, built at <instant>, fingerprint <bundle-hash>, specification <spec_version> — the four values of AGSC-04-25, AGSC-04-09, AGSC-04-15 and AGSC-00-17, in that order and with those separators — so that a reader who opens one file learns which content, built when, hashing to what, against which version of this specification; on a restricted node (AGSC-11-20) the line carries only built at <instant>, specification <spec_version>, because the content version and the fingerprint are facts that AGSC-11-20 keeps out of the discovery document and no file that anyone may read can carry them; the rest of the page's layout is implementation-defined and no rule pins a byte of it. (Amended 2026-10-29 for 1.1.0: a restricted node leaves the content version and the fingerprint out of /now/ and /now.md) [PRD-015]
  • AGSC-06-24 /about/ MUST include a "Quickstart" section with one ≤10-line path per persona P0–P12 (P0 first: init, then the security contact of AGSC-06-36, then one commit or a set SOURCE_DATE_EPOCH so that the build has an instant (AGSC-04-09), then ci), generated from a template so it cannot drift from the verb set. /about/ MUST carry the AGSC-08-19 honest-limit statement verbatim: both of its sentences, the second with its key word. AGSC-08-19 is where this specification itself states that limit, and this rule binds no other document. When a Bundle authors /about/ itself (AGSC-06-01), the writer MUST still insert the generated Quickstart section and the AGSC-08-19 statement into that page; a node that emits no /about/ — the route is conditional — has no obligation under this rule. (Amended 2026-10-06 for 1.0.0: P0's path read "the three commands"; it now names the two steps between init and a passing ci that AGSC-02-94 and AGSC-04-09 already require, the publisher's security contact and a build instant. A clarification: no path and no byte changes.) (Amended 2026-10-10 for 1.0.0: the rule also bound the security considerations of another document, which this specification cannot bind, and did not say which words the statement is.) (Amended 2026-11-10 for 1.1.0: the quickstart covers P0–P12; P12, the self-driving team on a live board (Mode 5, AGSC-10-17), was a persona of the requirements that the rule did not list, and the main site already carried its path) [PRD-052]
  • AGSC-06-25 A writer (Level 2 and above) MUST emit, in the <head> of every generated HTML page, <link rel="describedby" href="/.well-known/knowledge-linkset" type="application/linkset+json">, and SHOULD send the equivalent Link: </.well-known/knowledge-linkset>; rel="describedby"; type="application/linkset+json" response header on / and MAY send it on any other page (AGSC-11-05). A Level-0 publisher SHOULD do the same, so that a CMS or wiki export that cannot inject a <head> element still claims Level 0 (AGSC-10-02). describedby is the IANA-registered relation — registered by the W3C POWDER Recommendation (POWDER-DR Appendix D, used in §4.1.4, 2009); RFC 6892 registers its inverse describes — whose meaning — "the target describes the context" — is exactly this link's; what kind of description is said by the target's media type and by the profile URI (AGSC-06-07), never by a new relation name. A page may carry several describedby links (llms.txt v2 uses the same relation for its context file): a reader selects this one by type="application/linkset+json", and a reader that fetches it confirms the profile. No link relation is requested from IANA: the Internet-Draft requests registration of the well-known suffix only, and the Profile URI is registered in the IANA Profile URIs registry under RFC 7284 (AGSC-06-07), so no extension-URI spelling and no later alias ever exist. (Amended 2026-10-07 for 1.0.0: the sentence said that the registration of the Profile URI "is requested separately"; IANA has registered it. The Internet-Draft's part is unchanged.) [PRD-024, RFC 6892, RFC 9264]
  • AGSC-06-34 Agent card, OPTIONAL emission. A node MAY emit /.well-known/agent-card.json only when it declares both the a2a-card and a responder surface (AGSC-11-16, AGSC-11-21); otherwise it MUST NOT emit it (AGSC-06-07). The card is the Agent2Agent 1.0 Agent Card (a2a-protocol.org/latest/specification, version 1.0.0, read 2026-10-29), at the well-known URI agent-card.json, which the IANA registry lists as permanent since 2025-08-01 (read 2026-10-29). It carries every member that version requires of a card — name (site.title), description (the Bundle description, else site.tagline, else site.title), supportedInterfaces, version (the content version of AGSC-04-25; on a restricted node the specification version, AGSC-11-20), capabilities (the empty object), defaultInputModes (["text/plain"]), defaultOutputModes (["application/json"]) and skills — and no member that version does not define. supportedInterfaces holds one interface for each responder entry of surfaces[], in that order, with url the entry's target, protocolBinding the entry's binding (AGSC-01-18; default JSONRPC) and protocolVersion equal to the agsc-surface-version declared for a2a-card. skills holds one skill for each pack of /skills/index.json, in index order, with id and name the pack's name, description the pack's description and tags — which A2A 1.0 requires of every skill, so a skill without them is not emitted — ["knowledge","skill-pack"]; a node with no pack has skills []. The card also carries securitySchemes and securityRequirements, members A2A 1.0 defines as OPTIONAL, when a responder entry states security_schemes or security_requirements (AGSC-01-18): the schemes of the entries in their order, a name that two entries give taken from the first, and the requirements of the entries in their order, each written as A2A's JSON form writes it, so that a member A2A does not define is not carried; a responder declared with the access class credential whose entry states no security_schemes is the warning AGSC-E210, since an A2A client reads a card without them as open (disc-0038). The card is serialised JCS-canonical (AGSC-04-05) plus one trailing LF, and it MAY carry signatures[] per A2A §8.4 (JWS over the JCS form). A read-only local MCP tool server is not an A2A endpoint and does not make a node eligible for a card. The card is written only when every responder entry is an A2A one (version a2a:<version>, AGSC-11-21) and the version declared for a2a-card is a bare A2A version such as 1.0, which protocolVersion carries; otherwise no card is written, the warning AGSC-E210 says why, and the discovery document does not declare a2a-card (AGSC-11-16), whose target the node would not serve (disc-0035). (Amended 2026-10-29 for 1.1.0: the card is emitted as an A2A 1.0 card with its required members, among them the skill tags, at the registered well-known URI; until this amendment the rule named the card and left its members to the external specification, and no 1.0 writer emitted one) (Amended 2026-11-10 for 1.1.0: the interfaces are those of A2A responders, protocolVersion is a bare A2A version, and a card that cannot be written is not declared either; until this note the engine left the declaration in the discovery document and tools/validate-wellknown warned about it; and the card carries the security members a responder states, A2A's way to tell a client how to authenticate, so that a card for a credential responder is no longer read as open — the card of a node that sets them changes, and no 1.0 byte) [A2A 1.0 §8]
  • AGSC-06-36 The security contact file. /.well-known/security.txt (AGSC-06-01) MUST be a conforming RFC 9116 file, and its fields are the publisher's rather than the writer's: they are authored in the Bundle root's .well-known/security.txt and published verbatim, in the authored order, one Name: value line each with the field name in the registry's case and every value neutralised to a single line (AGSC-02-24). A writer MUST NOT emit the route, and MUST report AGSC-E901, where the Bundle root carries no such file; it MUST NOT emit the route, and MUST report AGSC-E202, where the authored file states no Contact: field — RFC 9116 §2.5.3: "This field MUST always be present in a 'security.txt' file". A Contact: value that is not a URI — a scheme, : and no white space, the RFC 3986 syntax §2.5.3 requires ("This means that 'mailto' and 'tel' URI schemes must be used when specifying email addresses and telephone numbers") — or that is an http: address ("If this field indicates a web URI, then it MUST begin with 'https://'") is AGSC-E204, and the route is not emitted (Amended 2026-10-06 for 1.0.0: a bare e-mail address was published unchanged, so the file the writer emitted was not the conforming RFC 9116 file this rule requires). A line that is neither blank, a comment nor a name: value field is AGSC-E204, and so is a second Expires field (§2.5.5: "This field MUST always be present and MUST NOT appear more than once"), an Expires value that is not an instant of AGSC-04-10, and an Expires that is not after the build instant; an Expires more than one year after the build instant is a warning under the same code (§2.5.5: "It is RECOMMENDED that the value of this field be less than a year into the future to avoid staleness"). Where the authored file states none, and only then, the writer derives Expires as the build instant plus 364 days, Canonical as the absolute URL of this route, and Policy as the absolute URL of the disclosure page that site.security_policy declares (AGSC-01-18, an absolute https: URL) or, where none is declared, of /legal/ — the last only where that route is emitted, because a Policy naming a route the same build does not produce is worse than no Policy. A writer MUST NOT derive an Expires from a build instant that is the AGSC-04-09 default of 0: it MUST report AGSC-E204, emit nothing for this route, and say that the publisher must commit the Bundle once or set SOURCE_DATE_EPOCH — 364 days after epoch 0 is a security contact that expired decades before it was published. Nothing in this rule reads a clock: every derived value is a function of the build instant, so the file stays byte-reproducible (AGSC-04-02). (Amended 2026-10-29 for 1.1.0: Policy follows a declared disclosure page; a node that declares none keeps the /legal/ of 1.0 and its bytes) [PRD-047, PRD-011]

6.5 Agent-retrieval chunk export

  • AGSC-06-26 A Level ≥ 2 writer MUST emit /chunks.jsonl: one JCS-canonical JSON object per LF-terminated line, one line per chunk, UTF-8, NFC, no blank lines, one trailing LF. The file is the Bundle's agent-retrieval export: a stable, citable, pre-split unit set with provenance, so that any agent can use the Bundle as remote memory without re-chunking, guessing boundaries or inventing identifiers. Embeddings are out of scope; the record is embedding-ready. The file is declared as the chunks surface (AGSC-11-16). This shape holds unless AGSC-06-31 applies, in which case this document is the manifest that rule defines. [PRD-061]
  • AGSC-06-27 Boundary rule. Chunks are cut after the AGSC-04-07 normalisation of the item body; fenced code is NOT removed (code stays in its chunk). Cut 1: at every ATX heading of level 2 or 3 (## , ### ) that lies outside any fenced code block, per CommonMark 0.31.2 (AGSC-02-20) — a ## line inside a fence is content, and setext headings are not cut points — the text before the first such heading is chunk 0 (an empty chunk 0 — a body that begins with a cut heading, or an empty body — is not emitted), and each heading with its following text is one chunk, the heading line included. The blank line(s) immediately preceding a cut belong to neither chunk, so a chunk's text ends with exactly one LF and never begins with one. Cut 2: a chunk whose UTF-8 byte length exceeds chunks.max_bytes (AGSC-11-01; default 4096, maximum 65536) is split at the last paragraph boundary (a blank line, i.e. two consecutive LFs) at or before the bound — the chunk's byte length, excluding the separating blank line, MUST NOT exceed the bound — repeatedly; a single paragraph longer than the bound is split at the last LF at or before the bound, and, failing that, at the bound on a code-point boundary — only in that last case may a chunk's text end without LF and the next begin mid-line. No overlap. The heading is not repeated into continuation chunks. [design]
  • AGSC-06-28 Identifier. id is the lowercase-hex SHA-256 of the UTF-8 bytes of the item IRI, then one U+0000 (NUL) byte, then the section path, then one U+0000 (NUL) byte, then the ordinal in decimal — where the section path is the AGSC-03-13 anchor of the chunk's heading (the empty string for chunk 0) and the ordinal is the zero-based index of the chunk within that section after Cut 2. Two conforming writers therefore derive identical ids from identical sources; an agent cites a chunk back as the item IRI followed by #chunk- and the first 16 hex characters of id, which a page MUST render as an in-page anchor on the chunk's heading (the top of the page for chunk 0). [design]
  • AGSC-06-29 Record shape. Members, all REQUIRED unless marked: digest (lowercase-hex SHA-256, FIPS 180-4, of the UTF-8 bytes of the decoded text string exactly as the text member states it — not of the JSON-escaped line, not of the record and not of any other member), id, iri (the item IRI), item (the slug), kind (the item type), subkind (OPTIONAL: the concept kind, present only on concepts), license (bundle.license_prose), links (the item's authored Links as an object of key → slug arrays (anchors stripped; each array in code-point order) in JCS order; a target naming an item excluded by AGSC-06-30 is dropped from its array and a key emptied by that drop is omitted (the exclusion every other surface applies); OPTIONAL when empty), ordinal, section (the anchor; empty for chunk 0), terms (the Content Use Terms identifier of AGSC-06-18), text, title, trust (always untrusted — the value an agent MUST attach when the text re-enters a model, AGSC-08-18), type (text, or the media type of an attachment chunk, AGSC-06-30). A 1.0 writer emits no other member; from 1.1 a writer also emits, each only under its condition: abstract (the item's own description, copied unchanged, never written by a model, present whenever the item has a non-empty description and omitted otherwise; every chunk of the item carries it, a cluster's chunk included, whose text already is the description; its bytes count toward the budget of AGSC-06-31), license_url (the licence URL of AGSC-06-44, omitted when the node has none) and content_digest (OPTIONAL, present only when chunks.content_digest is true, default false: the SHA-256 of the same bytes as digest in the RFC 9530 form sha-256=:<base64>: (the standard base64 alphabet with = padding), a Byte Sequence of RFC 9651, so that a client with an RFC 9530 library needs no conversion; it never replaces digest and the two MUST name the same hash); x-<vendor>-<key> members MAY follow (AGSC-02-05a), a later MINOR may add members, and a reader MUST ignore a member it does not know (AGSC-00-21). Lines are ordered by item slug (code point), then section (code point), then ordinal ascending numerically. (Amended 2026-10-29 for 1.1.0: the algorithm and the covered bytes of digest are named, and abstract, license_url and content_digest are added as optional members, which a 1.0 reader ignores (AGSC-00-21); for an item with a description every chunk line of that item changes by the abstract member) [PRD-061, AGSC-11-18]
  • AGSC-06-30 Exclusions and attachments. Items with status retired (AGSC-11-22) or draft, and items held back by the releases switchboard (AGSC-01-20), are excluded — the same set that search.json and /llms.txt exclude; a cluster contributes one chunk (its description; a cluster without description contributes no chunk). Each attachment of an item (AGSC-02-98) contributes one chunk whose type is the attachment's media type, whose text is the attachment's alt text for binary media and the file's full text for image/svg+xml and other text media, whose section is attachment-<n> (<n> the 1-based index in attachments[]) and whose ordinal is 0; a cluster's chunk has item = the cluster slug, iri = the cluster IRI, section empty and ordinal 0. The in-page anchor of AGSC-06-28 is required only for chunks that begin with a heading; every other chunk is cited at the top of its page. Peer-derived content never appears in a node's own export (AGSC-11-11). [design]
  • AGSC-06-31 Budgets: /chunks.jsonl SHOULD NOT exceed 8 KB per published item on average (a bound that a valid input can exceed, since a long item body is chunked whole, is advisory from 1.1: a build reports no finding for it, and the sharding below is what bounds the size of one file); above 500 items a writer MUST shard as /chunks-<nn>.jsonl (<nn> zero-padded from 01, each shard the lines of at most 500 items in slug order, no item split across shards) with /chunks.jsonl becoming the JCS-canonical manifest {"bundle_version": <string>, "lines_total": <integer>, "shards": ["/chunks-01.jsonl", …]} (paths in shard order; bundle_version is the content version of AGSC-04-25, and a chunk line does not carry it, its member set being closed by AGSC-06-29), exactly as AGSC-06-21 shards the index. A chunk line carries no index into any other line, so AGSC-06-21's shard-reading rule has no counterpart here: a reader concatenates the shards in manifest order and needs nothing else (so that a reader of the two sharding rules does not look for a rule that is deliberately absent). The digest, the count and the chunk-set commitment of AGSC-06-44 are those of the lines of all shards read in manifest order, and the digest is that of the manifest file when the export is sharded. (Amended 2026-10-29 for 1.1.0: the manifest is the file the surface digest covers when the export is sharded) (Amended 2026-10-29 for 1.1.0: the average budget is advisory, as AGSC-04-03 says, because an item body of any admitted length produces its chunks) [AGSC-06-21]
  • AGSC-06-37 Tabular chunk index. A Level ≥ 2 writer MAY emit /chunks-index.toon, a tabular index of /chunks.jsonl in the TOON format (@toon-format/toon 4.1.1, specification 4.1, the tabular form of its §9.3). The file is UTF-8, NFC, LF-terminated, with one trailing LF (AGSC-04-07), and consists of the header chunks[<n>]{id,item,kind,section,ordinal,title,digest}: — <n> the number of chunk lines — followed by one row for each chunk line of /chunks.jsonl, in the same order, whose columns are id and digest cut to their first 16 hexadecimal characters, and item, kind, section, ordinal and title as the record states them. Each row is indented by two spaces and its values are joined by ,; a value is written bare unless the quoting rule of TOON specification 4.1 requires quotes, in which case it is written in double quotes with \" and \\ escaped — an empty string is "", and a string that contains ,, :, " or \, a control character, a leading or trailing space, or that reads as a number, true, false or null, is quoted; ordinal is written in decimal without leading zeros (the case chk-0010 shows rows). A Bundle with no chunk line gets the header with <n> of 0 and no row, never an empty file. The index is regenerated with /chunks.jsonl, never differs from it in rows or in order, and carries no member that the records lack. It is emitted only when the published set holds at most 500 items: above that the file is not emitted, because /chunks.jsonl is itself sharded (AGSC-06-31) and the index has no shard of its own. It is announced, if at all, by a related[] link (AGSC-06-35) and by no surface name and no rel# relation, so the closed lists of AGSC-11-16 and AGSC-06-10 gain nothing, and its absence is never a fault at any Level (AGSC-10-04). The cut digest is a locator only: a reader that cites a chunk checks the full digest of the record (AGSC-06-29). The file is served as text/toon; charset=utf-8, the provisional media type that the TOON specification names (specification 4.4, §17, read 2026-11-10), which is not a registered media type (AGSC-06-17). (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: the export adapter llm-context wrote this file beside the node and the main site served it under /exports/; the route, the header row and the size condition are fixed here) (Amended 2026-11-10 for 1.1.0: the media type the engine serves the file with is named; no served byte changes) (Amended 2026-11-11 for 1.1.0: the format is read at the pinned @toon-format/toon 4.4.0 and TOON specification 4.4 (Working Draft of 8 October 2026), the current version, where the rule above names 4.1.1 and 4.1; the header, the rows and the quoting rule of the chunk index are the same under both, as chk-0010 passes on 4.4.0. A factual note: no emitted byte changes.) [design]
  • AGSC-06-44 Chunk integrity: the digest on the surface link, the chunk-set commitment, the licence URL and the freshness of the ledger. From 1.1 a Level ≥ 2 writer, on a node that is not restricted (AGSC-11-20), MUST give the rel#surface link whose agsc-surface is chunks (AGSC-11-16): a digest of the form of AGSC-06-08 over the canonical bytes of /chunks.jsonl, which is the manifest file when the export is sharded (AGSC-06-31); agsc-chunk-count, one value, the decimal number of chunk lines across all shards; and agsc-chunk-set, one value in the form of digest, the SHA-256 over the concatenation, in file order and in shard order, of the id of every chunk line, each written as its 64 lowercase hexadecimal characters followed by one LF (0x0A) — for an export with no line, the SHA-256 of the empty byte string. A consumer that holds the lines recomputes the count and the commitment and so finds a chunk that was dropped or added; the digest of each record finds a text that was changed (AGSC-06-29); none of the three says who published the file (AGSC-06-08). validate-wellknown at --level 2 and above recomputes the three over the fetched file and requires them of a document whose agsc-spec-version is 1.1.0 or later; it accepts their absence in an earlier document. The rel#ledger link MAY carry agsc-ledger-length, one value, the decimal number of entries of the derived ledger (AGSC-08-20a), beside agsc-ledger-head. The licence URL of a node is, in this order: bundle.license_url when configured (AGSC-01-18; a URL that names a specific version of the licence, such as the address of version 4.0 of a Creative Commons licence and not the address that names the licence without a version); else, when bundle.license_prose is the Content Use Terms identifier or is absent and the node emits /legal/ (AGSC-06-18), the absolute URL of /legal/; else none. Every chunk of a node that has one carries it as license_url (AGSC-06-29), and the same URL is the license link of AGSC-06-40 and the license of AGSC-06-41; license and terms are unchanged. A consumer SHOULD verify the digest of a chunk, and its id, before it hands the chunk's text to a model, and a consumer that keeps the last agsc-ledger-head it accepted SHOULD accept a later discovery document only when that head is still the hash of an entry of the ledger it then fetches (AGSC-08-23) — a ledger that no longer holds it was rolled back or rewritten — and MAY compare agsc-ledger-length first. (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: a chunk could be altered, dropped or served stale without a statement that a reader could check; these four additions give the surface link, the set, the licence and the ledger a checkable form) [design, RFC 9530, RFC 9651]
  • AGSC-06-45 A chunk's text begins with a line that is not blank. No chunk's text begins with a line feed: the text of chunk 0 (the text before the first heading that Cut 1 of AGSC-06-27 cuts at) starts at the first line that is not blank, and so does the text of every other chunk, the pieces that Cut 2 produces included; a line is blank when it is empty or holds only U+0020 and U+0009. Blank lines inside a text are kept, and nothing else of AGSC-06-27 changes: a text still ends with exactly one line feed, except where one paragraph is split in the middle of a line. AGSC-06-27 has said since 1.0 that a chunk never begins with a line feed, and a 1.0 writer kept the blank lines that began a body in chunk 0; so for an item whose body begins with a blank line the text and the digest of chunk 0 in 1.1 differ from those of 1.0, and its id does not (AGSC-06-28). A body that begins with a heading that Cut 1 cuts at, or with a non-blank line, gives the same chunks as in 1.0. (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: stated as a rule of its own, and not as a correction, so that the one change of chunk-0 digests that 1.1 makes to a Bundle of 1.0 is named here and in the change log) (Amended 2026-11-11 for 1.1.0: the last sentence reads "gives the same chunks as in 1.0, except a piece of Cut 2 that began on a blank line in 1.0", for such a piece loses that line. A clarification: no emitted byte changes.) [design, AGSC-06-27]

6.6 JSON-LD context file

  • AGSC-06-32 A Level ≥ 2 writer MUST emit /ns/context.jsonld, the target of the …/rel#context link (AGSC-06-10) and of the application/ld+json branch of /ns/ negotiation (AGSC-06-06). It MUST be generated from the vocabulary file of the context version (ontology/agsc.ttl as it stood at version 1.0.0, AGSC-05-09; a term the file gained later, such as asc:warrant, is not in it) by a deterministic mapping — every asc: term of that file becomes a term definition whose @id is its IRI, object properties carry @type @id, datatype properties carry the @type of their declared range, and — because graph.jsonld also uses external vocabularies — the prefixes dcterms, prov, rdfs, schema, skos and xsd are defined together with a term definition for every external property a rule of §05, §06 or §11 emits (rdfs:seeAlso as @id, the SKOS, DCTerms, PROV and schema.org properties named in AGSC-05-14…20, 05-27, 05-29, 06-18 and 11-12); no term is ever mapped to null (a null term definition, which JSON-LD 1.1 keeps as a blocked term so that it can never be used); @version 1.1 and @protected true are set — sorted per AGSC-04-05, and MUST round-trip: expanding graph.jsonld with it and re-compacting MUST reproduce graph.jsonld as a value, and MUST reproduce it byte for byte once the compacted result is serialised in the canonical form of AGSC-04-05 (JCS over NFC strings), which is the form graph.jsonld is written in — a JSON-LD processor fixes no member order, so the canonical serialisation is the step that makes the comparison a byte comparison. The term name of an asc: term is its local name; the term name of an external property is its local name, or its compact IRI (<prefix>:<local>) where that local name is also an asc: term name or is shared by two external properties. The full context file is therefore a constant of this specification, derived from the vocabulary file of the context version and from nothing about a node, and a node's /ns/context.jsonld MUST equal it byte for byte (AGSC-05-09). (Rationale: the member names of graph.jsonld are these term names, and AGSC-04-24 claims byte-identity for graph.jsonld across implementations; the vector graph-0011 uses the bare local name.) Released context files are immutable (AGSC-00-16); the versioned copy lives at /ns/<context-version>/context.jsonld, <context-version> being the context version of AGSC-05-09 — 1.0.0 at every version 1.x of this specification, and not the ontology version, which moves with the vocabulary file — and the constant that a node's /ns/context.jsonld MUST equal is the context file of that version. (Amended 2026-10-29 for 1.1.0: the address names the context version and not the ontology version, so that the @context address and the bytes of a graph.jsonld of 1.0 do not change when the vocabulary file gains annotations or terms (AGSC-05-09, case graph-0043)) (Amended 2026-10-10 for 1.0.0: the word "typed" is dropped; not every external term definition carries an @type.) (Amended 2026-11-11 for 1.1.0: a graph of one node is compacted by a JSON-LD processor without @graph, the members of the node standing at the top level, while graph.jsonld always has the member @graph; the round trip therefore puts @graph back, as an array of that one node, before it compares. A clarification: no emitted byte changes.) [AGSC-05-09]

6.7 Static query fragments (SHOULD, sacrificial)

  • AGSC-06-33 A Level ≥ 2 writer SHOULD emit /graph/fragments/s/<subject-hash>.nq for every distinct subject IRI and /graph/fragments/p/<predicate-hash>.nq for every distinct predicate IRI of graph.nq — each file the byte-sorted N-Quads lines sharing that term, the hash being the first 16 hex characters of the SHA-256 of the IRI — plus /graph/fragments/index.json {subjects, predicates, generated_at} — JCS-canonical, subjects and predicates arrays of file paths in code-point order. Object fragments are NOT emitted at 1.x. A writer that does not emit fragments MUST NOT emit the index. (Non-normative: a static subset of the Triple Pattern Fragments interface at the dump end of the Linked Data Fragments spectrum; counts and controls are omitted at 1.x.) [design]

6.8 Dataset vocabularies — VoID and DCAT (informative)

VoID is cited as complementary prior art by AGSC-06-12, a requirement. DCAT 3 (W3C Recommendation, 22 August 2024) is the catalogue vocabulary a publisher or an aggregator may use to describe a Bundle as a dataset; this specification defines no DCAT emission beyond the opt-in catalogue block of AGSC-06-41 and no rule depends on one, so the mapping below is a courtesy to catalogue maintainers and adds no term to ontology/agsc.ttl. Where a publisher emits it, the natural mapping is: the Bundle IRI is a dcat:Dataset (and, being a skos:ConceptScheme, also the dcat:themeTaxonomy of its own catalogue record); dcterms:title/dcterms:description from site.title/content/index.md; dcterms:license from bundle.license_prose; dcterms:modified from the build instant; each machine artefact of AGSC-06-01 is a dcat:Distribution with dcat:accessURL the route, dcat:mediaType the served type and spdx:checksum the same SHA-256 the link set carries as digest; the discovery document itself is the dcat:landingPage-adjacent entry point, and the …/rel#graph targets are the distributions a triple-store consumer wants. A VoID description (void:Dataset, void:dataDump = /graph.nq, void:vocabulary = the /ns/ IRI) may sit beside it at /.well-known/void; both are optional, both point at artefacts this specification already pins, and neither is a conformance target at 1.x.

6.9 Graph view and query page (1.1)

  • AGSC-06-38 Graph view, relations table and backlinks. An item page and a cluster page SHOULD show the neighbourhood of the item or the cluster as an inline SVG figure, drawn from published items only, with a relations table beside it as its text equivalent (AGSC-06-20). The table has one row for each relation key that links the item and another item, in either direction, and each row gives the key, its direction (outgoing or incoming), the other item's title as a link to its page, and the plain meaning of the key, taken from the Meaning column of the table of AGSC-03-01. The incoming rows are the backlinks of the item: every published item that links to it by one of the fourteen keys; a link written inside a body is not a backlink. The figure draws at most 24 neighbours, the first 24 rows of the relations table in its order, and the table says how many more there are. Published means that AGSC-06-30 does not exclude the item: an item that is a draft, retired or held back by the releases switchboard is neither drawn nor named, and a link to it is neither a row nor a backlink. A writer that draws the figure MUST also write the table, and MUST keep the figure inside the SVG rules of AGSC-02-13 and AGSC-01-07 and the page inside the budget of AGSC-06-21; a relation filter needs no script, and no route is added. A cluster page draws its members and the links among them the same way, and /clusters/ carries the overview of all clusters and a legend of the fourteen keys with their meanings. On a node that uses the domain layer (AGSC-01-41: a site vocabulary file is present), for the items that carry the keys domain_type, domain_role, domain_context or warrant (AGSC-02-25, AGSC-05-40), the relations table of an item page MUST also show, in each row, the other item's domain type and context, and the page MUST show the item's own domain type, role, context and warrant in a definition list under the table, each with the label that the site vocabulary gives it; a node that does not use the layer shows none of these, and its pages differ from those of 1.0 only by the figure, the table and the backlinks. HTML pages are not byte-pinned (AGSC-04-24), and the figure and the table are views added to the page, not changes to a machine file. (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: the 1.0 page listed the links of an item and nothing of what links to it; the figure, the table with the meanings of the keys and the backlinks are added, and the domain-layer parts are written with the layer itself) (Amended 2026-11-11 for 1.1.0: the table lists the same first 24 rows as the figure draws and says how many more there are and where all of them are (the graph), because a page that listed every backlink of a hub would pass the 100 KB of AGSC-06-21. The rows are the outgoing ones, then the incoming ones, each group in the order of the keys in AGSC-03-01 and then of the slug of the other item in code-point order. The page of a retired item has no relations section. A symmetric key (related, excludes, contradicts) that both items state is one relation: one row on each page, the outgoing one, and one link and one count in a cluster map and in the overview. A cluster map draws at most 24 members and 24 links among them, those the links join first, and says what it left out. On a node that uses the domain layer the two columns are written when the other item of at least one row has a domain type or a context, so that no table has two empty columns; the definition list is written on the page of a listed item that has any of the four parts. The label of a domain type is the rdfs:label of its class in the site vocabulary (the first in code-point order), else the local name as written; the vocabulary gives no term to a role or a context, so a role is shown as its words ("aggregate root") and a context as the title of its cluster, linked when that page is published; a warrant is shown as <type>: <source>, the source linked when it is an http or https address. A clarification: no machine file changes.) (Amended 2026-11-11 for 1.1.0: the trace bracket names PRD-077, the requirement of the graph view.) [design, AGSC-06-30, PRD-077]
  • AGSC-06-39 Query page. Unless site.query_page is false (AGSC-01-18; the default is true), a writer that serves /graph.nq MUST emit /query/, a page on which a visitor writes a query in SPARQL 1.1 (W3C Recommendation of 21 March 2013) and runs it against the node's own published graph, in the visitor's browser and nowhere else; no server takes part. The page MUST: (a) load /graph.nq of the same node into an in-browser RDF store, answer SELECT, ASK, CONSTRUCT and DESCRIBE, refuse an update and a SERVICE clause, and request no address outside the origin of the node; (b) offer, as named examples that fill the editor, the ten questions that the graph must answer (AGSC-05-34), each with the query by which the question is defined, and, on a node that declares competency questions of its own (AGSC-05-41), those too; (c) show a result as a table, and a CONSTRUCT, DESCRIBE or three-column result also as a graph picture; (d) offer the result for download as CSV and as JSON, in the formats of the W3C Recommendations "SPARQL 1.1 Query Results CSV and TSV Formats" and "SPARQL 1.1 Query Results JSON Format" (both of 21 March 2013); (e) make each query shareable as a link whose fragment (the part after #) holds the query text, so that no request to any server carries it, and put the query of such a link into the editor, running it only when the visitor asks; (f) carry a vocabulary explorer that lists the classes and the fourteen relation keys with their plain meaning (the Meaning column of AGSC-03-01) and, on a node with a site vocabulary (AGSC-05-38), its classes and relations. The page keeps AGSC-06-05 — it stores nothing, not even the last query, and sends nothing — and AGSC-06-20 (WCAG 2.2 AA, every control operable from the keyboard). The HTML of /query/ keeps the page budget of AGSC-06-21; the query engine and its licence text are same-origin page assets of the page (AGSC-06-01), outside that budget, and are the files of one release of an engine whose licence allows their redistribution; this specification names no engine, and the conformance case checks the rules (a) to (f) through the page's markup and the content security policy of AGSC-06-17 only (build-0030), not the engine. The content security policy of /query/ and of the files under it is the policy of AGSC-06-17; a writer whose engine is compiled to WebAssembly MAY add 'wasm-unsafe-eval' to its script-src, and MUST NOT add 'unsafe-eval', 'unsafe-inline', a host source, or any loosening of default-src, style-src, img-src or connect-src. A node with site.query_page set to false emits no /query/, no file under it and no link to it. A Bundle of 1.0 built by a 1.1 writer with the default gains /query/ and its assets, an entry for it in /sitemap.xml (AGSC-06-19), a navigation link on every generated page, and the _headers block of the page; no other file changes. (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: a visitor can ask the published graph a question without installing anything and without a server; the switch lets a node keep the file set of 1.0, and a Bundle that sets it SHOULD declare a spec_version of 1.1.0 or later (AGSC-01-18)) (Amended 2026-11-11 for 1.1.0: the trace bracket names PRD-078, the requirement of the query page.) [design, AGSC-06-17, PRD-078]

6.10 Signposting, dataset fields, catalogue files and page relations (1.1)

  • AGSC-06-40 FAIR Signposting links on the home page. A Level ≥ 2 writer MUST send, in the Link header of /, the typed links that FAIR Signposting (signposting.org/FAIR, read 2026-10-29) asks of a landing page at its Level 1, so that a client that reads only headers finds the identifier, the licence, the metadata and the content files: cite-as, exactly one, whose target is the href of the first related[] link of relation cite-as in href order (AGSC-06-35) or, without one, the Bundle IRI; type, two, https://schema.org/Dataset and then https://schema.org/AboutPage; describedby, the discovery document with type="application/linkset+json" (AGSC-06-25) and /graph.jsonld with type="application/ld+json"; item, /graph.nq, /graph.ttl and, where the node serves it, /chunks.jsonl, each with its type; license, the licence URL of AGSC-06-44 when the node has one; and linkset, the discovery document with type="application/linkset+json". The targets on the node itself are root-relative, as in AGSC-06-25, while the targets of cite-as and license are absolute URLs, and the values are written into the one _headers block of / (AGSC-06-17), as one Link field with comma-separated values or as one field for each. A restricted node (AGSC-11-20) sends cite-as, type, describedby, linkset and license, and no item. This rule claims the landing-page half of Signposting Level 1 (section 2.1.1) and the linkset link; the collection and describes links that section 2.1.2 asks for on the content and metadata files themselves are not sent, and the discovery document does not carry every landing-page link that Level 2 asks for. Informative example of one value: </.well-known/knowledge-linkset>; rel="describedby"; type="application/linkset+json"; the case disc-0026 compares the links as a set and does not pin their order or the spacing. validate-wellknown, given a URL, reads the Link header of / and checks that it carries the describedby link of AGSC-06-25 whose target is the discovery document; its absence is reported as a warning under AGSC-E202, because AGSC-06-25 makes the header a SHOULD. (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: FAIR Signposting asks for typed links in the headers of a landing page; the discovery document already exists and is named by linkset, and the checker did not look at the header) [design, RFC 8288, RFC 9264]
  • AGSC-06-41 Dataset fields of the home page. The Dataset JSON-LD block of the home page (AGSC-06-19) carries from 1.1, besides name, description and url: license, the licence URL of AGSC-06-44, omitted when the node has none; creator, a Person with a name and, where an ORCID iD is configured, a sameAs that holds https://orcid.org/ followed by the iD — taken from bundle.creator (name and OPTIONAL orcid), else from site.author with site.author_orcid (AGSC-01-18) — omitted when neither is configured; isAccessibleForFree, true on a node that is not restricted; and distribution, one DataDownload for each of /graph.jsonld, /graph.ttl, /graph.nq, /chunks.jsonl (its manifest when sharded) and /.well-known/knowledge-linkset that the node serves, in that order, with an absolute contentUrl and an encodingFormat (the type the file is served with, and application/jsonl for the chunks). The block names the PROV-O vocabulary (W3C Recommendation of 30 April 2013) with the prefix prov in its @context and carries prov:generatedAtTime, the build instant (AGSC-04-09), and prov:wasAttributedTo, the same Person object as creator; these two terms appear in this block and in no other place — not in graph.jsonld, graph.ttl or graph.nq, not in pages/*.jsonld, and not in the block of any other page — so that the graph files and the @context address of 1.0 do not change. The block of a restricted node holds no distribution, its files being gated. The block is the node @id = the Bundle IRI (site.base), and the creator Person is the node @id = its ORCID iD URL, else <site.base>#creator, which prov:wasAttributedTo names by @id alone, so that a JSON-LD reader finds the Bundle and one Person (disc-0037). A node whose configuration sets discovery.dcat to true (AGSC-01-18; the default is false) carries in the same script, after the Dataset block, a DCAT 3 catalogue block (W3C Recommendation, 22 August 2024): a dcat:Catalog <site.base>#catalog with dcterms:title site.title and dcat:dataset the Bundle IRI as a dcat:Dataset with dcterms:title, dcterms:description, dcterms:license and dcterms:creator (each where the Dataset block has it, by @id), dcterms:modified (the build instant) and, on a node that is not restricted, one dcat:Distribution for each DataDownload of the Dataset block, in its order, with dcat:downloadURL its contentUrl and dcat:mediaType the IANA media type IRI of its type without parameters, or dcterms:format for the chunks, whose type is not registered; the two blocks are then a JSON array. The fields follow the recommendations of the Google Search Central guide for datasets (last updated 2026-09-08, read 2026-10-29): a license URL that names a specific version of the licence and an ORCID iD for a person; a description shorter than 50 characters, which Google ignores, is reported as the warning AGSC-E202; the encodingFormat application/jsonl of the chunks is not a registered media type (AGSC-06-17); no other index page changes. (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: Dataset search reads the license, the creator and the distribution; the 1.0 block held a name, a description and a URL only. The PROV-O terms are confined to this block so that the graph bytes stay those of 1.0) (Amended 2026-11-10 for 1.1.0: the block and its creator are named by @id (the block wrote the creator twice, as two unlinked Persons on blank nodes; disc-0037 supersedes disc-0027), and the opt-in DCAT 3 catalogue block is added; /index.html changes on every node, by the @id members, and by the DCAT block only on a node that sets the switch) [design, schema.org]
  • AGSC-06-42 AI-catalogue files (opt-in; both formats are proposals). A node whose configuration sets discovery.ai_catalog to true (AGSC-01-18; the default is false) MUST emit /.well-known/ard.json and /.well-known/ai-catalog.json, and a node that leaves it false MUST NOT emit either. Both formats are proposals, not standards: the Agentic Resource Discovery manifest, version 0.91, status "Proposal", dated 26 August 2026 (agenticresourcediscovery.org/spec), and the AI Catalog draft, specVersion "1.0", undated (ai-catalog.io/spec), both read 2026-10-29; neither suffix is in the IANA registry of well-known URIs (read 2026-10-29). Each file is a JCS-canonical (AGSC-04-05) JSON document with one trailing LF, served as a public artefact with the headers of AGSC-11-03 and the media type application/ai-catalog+json for ai-catalog.json and application/json for ard.json. ard.json is {"entries":[…]} and ai-catalog.json is {"entries":[…],"specVersion":"1.0"}. The entries are, in identifier order, one for the discovery document of AGSC-06-07 and, when AGSC-06-34 emits a card, one for the card. An entry has: identifier, urn:air:<host>:knowledge:<bundle.id> for the discovery document and urn:air:<host>:a2a:<bundle.id> for the card, <host> being the host name of site.base in lower case and without a port, which for this switch MUST be a fully qualified domain name (it contains at least one ., is not an IP literal and does not end in .local; the form is that of ARD §4.2, urn:air:<publisher>:[<namespace>:]<agent-name>); displayName, site.title; type, for the discovery document the media type that AGSC-06-17 serves it with, parameter included (application/linkset+json; profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge"), and for the card application/a2a-agent-card+json; url, the absolute URL of the file; description, the Bundle description when there is one; and the SHA-256 of the exact bytes served at url, written sha256: and 64 lowercase hexadecimal characters, as the member digest in ai-catalog.json (the AI Catalog draft's form) and as the member metadata.digest in ard.json, which defines no digest member on an entry. A writer MUST NOT write representativeQueries, which ARD asks of an entry and which would have to be invented; a validator of ARD reports their absence as a warning, and this rule accepts it. The link relations ard and ai-catalog are not emitted, because AGSC-06-35 admits registered relation names only. A reader of this specification never needs either file. A switch set on a node whose site.base host is not a fully qualified domain name is rejected at build and reported as AGSC-E209, and a switch set on a node with no bundle.id is rejected as AGSC-E202; in both no file is written. (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: catalogue crawlers look for these two well-known names; one entry that points at the discovery document, with its digest, lets them find the node without a second format of our own) (Amended 2026-11-11 for 1.1.0: the entry type application/a2a-agent-card+json of the card is the string that both drafts use (read 2026-11-07); it is not a registered media type. A factual note: no emitted byte changes.) [design, ARD v0.91, AI Catalog draft]
  • AGSC-06-46 The link relations of llms.txt v2 on generated pages. Every generated HTML page MUST carry in its <head> <link rel="describedby" type="text/plain" href="/llms.txt">, and every item page MUST also carry <link rel="alternate" type="text/markdown" href="/pages/<slug>.md">: the two relations that llms.txt v2 (modified 2026-08-10, llmstxt.org, read 2026-10-29) defines for a page, describedby for the llms.txt file that covers it and alternate with the type text/markdown for the Markdown version of the page. A page may carry several describedby links, and a reader selects the discovery document by its type (AGSC-06-25). /llms.txt and /llms-full.txt are not changed by this rule. (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: llms.txt v2 defines page-level relations as well as the file; 1.0 pages linked the Markdown copy (AGSC-06-02) without saying which relation it was) [design, llms.txt v2]
