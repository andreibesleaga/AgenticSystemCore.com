AGSC-06 — Published surfaces: routes, discovery files, llms.txt

SummaryEverything a node publishes: the fixed route set, the discovery document, llms.txt, the chunk export, the JSON-LD context, headers and budgets.

Status of this document

Specification 1.0.0-rc.7, a release candidate tagged on 2026-10-08. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

Part 2 of 2, 6.4 to 6.8. This section is published in two parts so that each page stays within the budget of AGSC-06-21; a rule's link names the part that carries it. Part 1 carries 6.1 to 6.3.

In plain language

Routes. A writer emits a fixed set of pages and files — item pages, clusters, tags, search, NOW, compose, skills, specs, the graph files, llms.txt, sitemap, robots, the ledger, the chunk export, the context file, boards when tasks exist — and nothing else.

The discovery file. /.well-known/knowledge-linkset is an RFC 9264 link set: one document that points at every machine artefact with its SHA-256 digest, the spec version, counts, the ledger head, peers, surfaces and contribution targets. Pages point at it with the standard describedby relation; the Internet-Draft asks for the well-known name, which is not registered, and the profile identifier is registered in the IANA Profile URIs registry. The file can also carry optional links to related systems — an llms.txt file, an agent card, a server card, a memory or ontology endpoint — using standard relations only.

llms.txt. The agent-facing text file has a fixed byte layout — a provenance header, the title, the description, one section per cluster with one line per item — so two tools produce the same file.

The chunk export. /chunks.jsonl is the Bundle pre-split for agents: one line per chunk, cut at headings outside code fences and at a size bound, with a stable id, the text, provenance, licence and terms, and a digest. No embeddings.

Headers. No third-party scripts, no beacons; strict security headers; public artefacts readable cross-origin.

This box explains; the rules below decide. New to the notation? See how to read the specification.

6.4 Machine surfaces and headers

  • AGSC-06-16 search.json MUST be a prebuilt inverted index {terms:{token:[docIndex…]}, docs:[{slug,title,description,cluster}]} requiring no runtime dependency. docs[] MUST be ordered by slug, each posting list MUST be ascending docIndex values without repetition, and the terms member names MUST be ordered as JSON member names per AGSC-04-05. Tokens are produced by AGSC-06-23 and by nothing else. An item with no clusters[] omits the cluster member, and an item with no description omits description; a member is never emitted as the empty string, so search.json stays a function of the authored keys — unless AGSC-06-21 applies, in which case this document is the manifest that rule defines. [PRD-014]
  • AGSC-06-23 Tokenizer (normative). For each item the tokenizer input is, in this order, title, description, every tags value and the body with fenced code blocks removed. The input MUST be NFC-normalized, then ASCII-lower-cased (only U+0041–U+005A are mapped; no locale casing, no case folding of non-ASCII), then split at every run of characters that are not token characters. A token character is [a-z0-9] or a character whose Unicode General_Category is L* (any letter), Nd (decimal digit) or M* (combining mark, so Devanagari and Thai words are not split); every other character — including No/Nl forms such as ² and Ⅷ, and Lo-adjacent symbols — is a boundary. Non-ASCII letters and digits are kept code-point-wise and never transliterated. The General_Category table is that of the Unicode version pinned by AGSC-04-22. That pin is 16.0.0; a port using another version MUST state it in its conformance claim, since that is the only remaining source of divergence. A token shorter than 2 Unicode code points MUST be dropped (AGSC-02-24). There is no stemming, no stop-word list, no synonym expansion and no n-gram: two conforming engines therefore emit byte-identical search.json. [PRD-014, NFR-04]
  • AGSC-06-17 _headers MUST set Content-Type: text/markdown; charset=utf-8; variant=GFM for /pages/*.md, Content-Type: application/linkset+json; profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge" for /.well-known/knowledge-linkset — or the header fallback of AGSC-06-07 — and a Content-Security-Policy that contains at least default-src 'none', script-src 'self', style-src 'self', img-src 'self' and connect-src 'self' — the least the required pages need: the stylesheet every page links, the images it shows, and the search index and the page tools' reads, all from the node itself — and admits no inline script; a writer MAY add directives that only restrict further (base-uri 'none', form-action 'none', frame-ancestors 'none' in the reference engine), and a case on the policy asserts that it contains these directives, never the whole string. (Amended 2026-10-02 for 1.0.0: until 1.0.0-rc.6 the rule named default-src 'none' with script-src 'self' alone, a policy under which the pages the same chapter requires could not load their stylesheet or their search index.) In _headers each address pattern MUST be written once, as one block that carries every header the address takes — its content type, the cross-origin pair of AGSC-11-03 and its Link and Cache-Control values — because the reference host serves only one of two blocks written for the same pattern, and a header set split over two blocks loses one of them. (Amended 2026-10-06 for 1.0.0: the sentence was missing; the reference engine wrote the cross-origin pair and the content type of fourteen addresses in two blocks each, and the host served the discovery document and the other thirteen without Access-Control-Expose-Headers.) _redirects MUST carry /.well-known/agentic-knowledge → 301 → /.well-known/knowledge-linkset, and this alias MUST be present until the last 0.0.x consumer is retired. A writer MAY additionally emit, for each machine artefact of AGSC-06-01, a served Repr-Digest: sha-256=:<base64>: header whose value is the base64 of the same SHA-256 the discovery document carries as that link's digest (AGSC-06-08) — only on a response served without a content coding: under Content-Encoding the field is computed over the encoded bytes (RFC 9530 Appendix B.4), which a static header cannot follow, so a host that compresses MUST NOT send it from a static value. (Amended 2026-10-02 for 1.0.0: the restriction to uncoded responses was missing.) The field is RFC 9530's, a Structured Fields Dictionary whose value is a Byte Sequence (RFC 9651) and whose algorithm token is sha-256; a writer that emits it MUST derive it from the emitted bytes and never from a separate computation. It is a MAY and no Level requires it, so the required header set of this rule and the bytes build-0012 pins are unchanged. (Rationale: a reader holding one fetched file can check it without a second fetch of the discovery document.) [PRD-020, RFC 7763, RFC 9530]
  • AGSC-06-18 One licence policy is expressed in exactly three machine-readable dialects at 1.x, and no more: the AI-usage signals of robots.txt (RFC 9309); the TDMRep policy at /.well-known/tdmrep.json (the TDM Reservation Protocol well-known location, and the only route that carries it — the duplicate copy at /tdmrep.json is not emitted); and the schema:license/schema:usageInfo members of the JSON-LD views together with llms.txt. rsl.xml and the aipref Content-Usage field are not emitted at 1.x, and no rule, route or claim may assert them. The three dialects express one policy at three levels of precision, and only what is comparable is compared: a TDMRep tdm-reservation of 1 MUST be accompanied by a robots.txt group User-agent: <token> with Disallow: / for every product token (RFC 9309 §2.2.1) of site.tdm_crawlers[] (AGSC-01-18), and by a schema:usageInfo naming the Content Use Terms; a disagreement on those three comparable facts MUST fail the build, and nothing else is compared. site.tdm_crawlers[] is the publisher's own, maintained list of the product tokens whose operators state that they collect content in order to train a machine-learning model; it is configuration and never a constant of this specification, because vendors rename tokens and add them and a list frozen into a standard goes stale where it matters most. A writer MUST emit one such group per token, in the order the configuration states them and before the User-agent: * group, and MUST NOT emit a Disallow for any token the list does not name — a fetch made on a person's behalf, and a search crawler, stay invited, which is what keeps a node readable by the agents it exists for. An empty site.tdm_crawlers[] on a node that publishes tdm-reservation: 1 is AGSC-E202 at build, because the Content Use Terms text this rule pins by hash tells the reader that the reservation is stated machine-readably by the TDM reservation file and the robots signals of this node: with no token named, those signals carry no reservation and the node's own prose is false. (Rationale: with no token named, the Disallow conjunct would be vacuously true, and the one machine-checkable link between the strongest dialect and the weakest could never fail.) robots.txt expresses crawler access, not licence: RFC 9309 defines only User-Agent, Allow and Disallow and says of them "These rules are not a form of access authorization" (read 2026-09-19). (Rationale: no rule defines a mapping between the three dialects, and RFC 9309 has no vocabulary in which a TDM reservation or a schema:license can be expressed at all, so only the comparable facts are compared.) The Content Use Terms identifier is the constant LicenseRef-AgenticSystemCore-Content-Use-1.0. The Content Use Terms accompany the prose only where the publisher adopts them — bundle.license_prose is that identifier, or is absent and defaults to it (AGSC-01-18) — and every prose-carrying export of such a node MUST embed the identifier; a build omitting it MUST fail. A Bundle whose prose carries another licence MUST NOT be presented under terms narrower than that licence: wherever this specification places the Content Use Terms identifier — the terms: line of AGSC-06-13a, the terms member of a chunk line (AGSC-06-26), a skill pack or a Harness (AGSC-07-16), schema:usageInfo (AGSC-05-26) — such a node places the value of bundle.license_prose; it publishes tdm-reservation: 0 and no crawler group, and its pages name its own licence and not the Content Use Terms. license and terms are two members with two meanings even when their strings coincide. (Rationale: the Content Use Terms reserve model training, and a licence that grants more may forbid adding restrictions to it.) The Content Use Terms text is shipped as LICENSE-CONTENT at the Bundle root (AGSC-01-26); a distribution without it is incomplete. The text the identifier names is the file LICENSE-CONTENT at the root of this specification's distribution, whose SHA-256 over its bytes is b2e8da62e6a41886296d2d2358fb4642cc7418e806eb4a29ada12b588ac32857 (2133 bytes). A distribution that ships different text MUST use a different identifier: the identifier names terms, not a file name, and reusing it over other wording would make every terms: line of AGSC-06-13a and every schema:usageInfo of AGSC-05-26 unverifiable. A reader MAY check the hash; nothing requires a node to publish it, because the terms are the same terms for every node that carries the identifier. A writer MUST emit /legal/ from that LICENSE-CONTENT file when the Bundle root carries one, and MUST NOT emit the Content Use Terms link on any page when it does not; /about/ remains authored and optional, and /changelog/ is derived from the git-log file and emitted when the build is given it (AGSC-06-01) (amended 2026-10-02 for 1.0.0: /changelog/ was called authored and optional). The /legal/ page MUST also carry, each only where the Bundle supplies its input: the publisher's privacy notice and retention statement, from an authored PRIVACY.md in the Bundle root, rendered unchanged; an identification of the operator, derived from site.author and bundle.operator (AGSC-01-18, AGSC-01-25); and the AI-assistance statement of AGSC-06-15, in the same words the provenance header of every agent-facing export carries. A writer MUST NOT invent any of them — a privacy notice that is not the publisher's own words is worse than none — and an absent input omits that section and is the warning AGSC-E406, naming what is missing. (Rationale: PRD-019 asks this page for the Content Use Terms, a privacy notice, the operator and a retention statement.) [PRD-019]
  • AGSC-06-19 sitemap.xml MUST list every published route with lastmod from the build instant, ordered by URL. A published route is every route of AGSC-06-01 that the build emits as an HTML page — the home page, every item page, every index page (/<type-plural>/, /clusters/, /clusters/<slug>/, /tags/<tag>/, /<route>/page-<n>/), /now/, /compose/, /search/, /skills/ and, where the build emits them, /about/, /legal/, /changelog/, /conformance/, /boards/<cluster-slug>/ and /specs/** — and never /404.html or a machine file. Schema.org JSON-LD (TechArticle, DefinedTerm, Dataset) MUST be embedded in item and index pages. [PRD-020]
  • AGSC-06-20 Generated HTML MUST meet WCAG 2.2 AA — semantics, keyboard operability, contrast, and alt text from the diagram's alt key. [NFR-08]
  • AGSC-06-21 Budgets are normative and MUST fail the build when exceeded: ≤100 KB per HTML page; ≤1 MB per index document — /search.json at or below 500 items, and each /search-<nn>.json shard above it, every shard carrying the docs of at most 500 items (AGSC-06-31 already describes this rule's sharding that way); ≤60 s build per 500 items (external page requests are already impossible under AGSC-06-05). KB and MB are the decimal prefixes — 1,000 and 1,000,000 UTF-8 bytes of the emitted document — and AGSC-01-16 writes MiB where it means the binary prefix. (Rationale: AGSC-06-23 puts each item's body into the index, so the index costs what the prose costs, and per-item bytes fall as a Bundle grows, because the vocabulary amortises, and rise with body length; the budget is therefore stated once, on the artefact a reader actually downloads. At a full 500-item shard this bound is 2 KB of index per published item; how much one item can contribute to a page is already bounded by the 100 KB page budget of this rule.) Above 500 items a writer MUST shard the index as /search-<nn>.json (<nn> zero-padded from 01, in slug order) with /search.json as the manifest {shards:[…], docs_total} (and /chunks.jsonl sharded on the same trigger and in the same shape, AGSC-06-31), and MUST paginate any index route carrying more than 500 entries as /<route>/page-<n>/ (<n> from 2; page 1 is the route itself). The index routes are exactly these and no others: /; each /<type-plural>/ — /concepts/, /procedures/, /lessons/, /episodes/, /gates/, /clusters/; each /tags/<tag>/; and /search/. An item page, /now/, /compose/, /about/, /legal/, /changelog/, /specs/**, /ns/** and /skills/** are not index routes and are never paginated. A cluster's item page therefore lists at most 500 of its members, in the published order; above that it states how many members there are and says where the full list is — the search index and the graph, in which every member names the cluster (amended 2026-10-02 for 1.0.0: the bound the reference writer applies was not stated). Each /search-<nn>.json shard is a complete AGSC-06-16 index over the items of its own slice: its docs[] is the contiguous run of the slug order that the shard carries, and its posting values are indices into its own docs[], counted from zero. A reader reconstructs the whole index by concatenating the shards' docs[] in manifest order and adding, to every posting of a shard, the number of documents the earlier shards carry. A reader that cannot obtain every shard the manifest names MUST report AGSC-E901 rather than answer over the part it holds. (Rationale: the other reading of a shard's docIndex answers wrongly and silently on every shard but the first.) The budgets are therefore per-scale, not absolute, and a 5,000-item Bundle conforms: it publishes ten index shards, each under the bound. Exceeding a budget that no sharding rule relieves MUST fail the build, with AGSC-E904 (the code of the size caps of AGSC-01-16 and AGSC-01-34). [NFR-06]
  • AGSC-06-22 /now/ and /now.md MUST be generated from stored state only — counts, last build, stale items, open Lessons, monthly spend — never hand-edited. A section whose input is absent MUST be omitted, not guessed. Both MUST carry, as one line and its own paragraph, content version <bundle_version>, built at <instant>, fingerprint <bundle-hash>, specification <spec_version> — the four values of AGSC-04-25, AGSC-04-09, AGSC-04-15 and AGSC-00-17, in that order and with those separators — so that a reader who opens one file learns which content, built when, hashing to what, against which version of this specification; the rest of the page's layout is implementation-defined and no rule pins a byte of it. [PRD-015]
  • AGSC-06-24 /about/ MUST include a "Quickstart" section with one ≤10-line path per persona P0–P11 (P0 first: init, then the security contact of AGSC-06-36, then one commit or a set SOURCE_DATE_EPOCH so that the build has an instant (AGSC-04-09), then ci), generated from a template so it cannot drift from the verb set. /about/ and the Internet-Draft's Security Considerations MUST both carry the AGSC-08-19 honest-limit statement verbatim. When a Bundle authors /about/ itself (AGSC-06-01), the writer MUST still insert the generated Quickstart section and the AGSC-08-19 statement into that page; a node that emits no /about/ — the route is conditional — has no obligation under this rule. (Amended 2026-10-06 for 1.0.0: P0's path read "the three commands"; it now names the two steps between init and a passing ci that AGSC-02-94 and AGSC-04-09 already require, the publisher's security contact and a build instant. A clarification: no path and no byte changes.) [PRD-052]
  • AGSC-06-25 A writer (Level 2 and above) MUST emit, in the <head> of every generated HTML page, <link rel="describedby" href="/.well-known/knowledge-linkset" type="application/linkset+json">, and SHOULD send the equivalent Link: </.well-known/knowledge-linkset>; rel="describedby"; type="application/linkset+json" response header on / and MAY send it on any other page (AGSC-11-05). A Level-0 publisher SHOULD do the same, so that a CMS or wiki export that cannot inject a <head> element still claims Level 0 (AGSC-10-02). describedby is the IANA-registered relation — registered by the W3C POWDER Recommendation (POWDER-DR Appendix D, used in §4.1.4, 2009); RFC 6892 registers its inverse describes — whose meaning — "the target describes the context" — is exactly this link's; what kind of description is said by the target's media type and by the profile URI (AGSC-06-07), never by a new relation name. A page may carry several describedby links (llms.txt v2 uses the same relation for its context file): a reader selects this one by type="application/linkset+json", and a reader that fetches it confirms the profile. No link relation is requested from IANA: the Internet-Draft requests registration of the well-known suffix only, and the Profile URI is registered in the IANA Profile URIs registry under RFC 7284 (AGSC-06-07), so no extension-URI spelling and no later alias ever exist. (Amended 2026-10-07 for 1.0.0: the sentence said that the registration of the Profile URI "is requested separately"; IANA has registered it. The Internet-Draft's part is unchanged.) [PRD-024, RFC 6892, RFC 9264]
  • AGSC-06-34 Agent card, OPTIONAL emission. A node MAY emit /.well-known/agent-card.json only when it declares both the a2a-card and a responder surface (AGSC-11-16, AGSC-11-21): the card is the Agent2Agent 1.0 Agent Card whose interfaces point at that responder, with protocolVersion equal to the agsc-surface-version declared for a2a-card, serialised JCS-canonical (AGSC-04-05) plus one trailing LF, and it MAY carry signatures[] per A2A §8.4 (JWS over the JCS form). A node with no responder MUST NOT emit the card (AGSC-06-07). [A2A 1.0 §8]
  • AGSC-06-36 The security contact file. /.well-known/security.txt (AGSC-06-01) MUST be a conforming RFC 9116 file, and its fields are the publisher's rather than the writer's: they are authored in the Bundle root's .well-known/security.txt and published verbatim, in the authored order, one Name: value line each with the field name in the registry's case and every value neutralised to a single line (AGSC-02-24). A writer MUST NOT emit the route, and MUST report AGSC-E901, where the Bundle root carries no such file; it MUST NOT emit the route, and MUST report AGSC-E202, where the authored file states no Contact: field — RFC 9116 §2.5.3: "This field MUST always be present in a 'security.txt' file". A Contact: value that is not a URI — a scheme, : and no white space, the RFC 3986 syntax §2.5.3 requires ("This means that 'mailto' and 'tel' URI schemes must be used when specifying email addresses and telephone numbers") — or that is an http: address ("If this field indicates a web URI, then it MUST begin with 'https://'") is AGSC-E204, and the route is not emitted (Amended 2026-10-06 for 1.0.0: a bare e-mail address was published unchanged, so the file the writer emitted was not the conforming RFC 9116 file this rule requires). A line that is neither blank, a comment nor a name: value field is AGSC-E204, and so is a second Expires field (§2.5.5: "This field MUST always be present and MUST NOT appear more than once"), an Expires value that is not an instant of AGSC-04-10, and an Expires that is not after the build instant; an Expires more than one year after the build instant is a warning under the same code (§2.5.5: "It is RECOMMENDED that the value of this field be less than a year into the future to avoid staleness"). Where the authored file states none, and only then, the writer derives Expires as the build instant plus 364 days, Canonical as the absolute URL of this route, and Policy as the absolute URL of /legal/ — the last only where that route is emitted, because a Policy naming a route the same build does not produce is worse than no Policy. A writer MUST NOT derive an Expires from a build instant that is the AGSC-04-09 default of 0: it MUST report AGSC-E204, emit nothing for this route, and say that the publisher must commit the Bundle once or set SOURCE_DATE_EPOCH — 364 days after epoch 0 is a security contact that expired decades before it was published. Nothing in this rule reads a clock: every derived value is a function of the build instant, so the file stays byte-reproducible (AGSC-04-02). [PRD-047, PRD-011]

6.5 Agent-retrieval chunk export

  • AGSC-06-26 A Level ≥ 2 writer MUST emit /chunks.jsonl: one JCS-canonical JSON object per LF-terminated line, one line per chunk, UTF-8, NFC, no blank lines, one trailing LF. The file is the Bundle's agent-retrieval export: a stable, citable, pre-split unit set with provenance, so that any agent can use the Bundle as remote memory without re-chunking, guessing boundaries or inventing identifiers. Embeddings are out of scope; the record is embedding-ready. The file is declared as the chunks surface (AGSC-11-16). This shape holds unless AGSC-06-31 applies, in which case this document is the manifest that rule defines. [PRD-061]
  • AGSC-06-27 Boundary rule. Chunks are cut after the AGSC-04-07 normalisation of the item body; fenced code is NOT removed (code stays in its chunk). Cut 1: at every ATX heading of level 2 or 3 (## , ### ) that lies outside any fenced code block, per CommonMark 0.31.2 (AGSC-02-20) — a ## line inside a fence is content, and setext headings are not cut points — the text before the first such heading is chunk 0 (an empty chunk 0 — a body that begins with a cut heading, or an empty body — is not emitted), and each heading with its following text is one chunk, the heading line included. The blank line(s) immediately preceding a cut belong to neither chunk, so a chunk's text ends with exactly one LF and never begins with one. Cut 2: a chunk whose UTF-8 byte length exceeds chunks.max_bytes (AGSC-11-01; default 4096, maximum 65536) is split at the last paragraph boundary (a blank line, i.e. two consecutive LFs) at or before the bound — the chunk's byte length, excluding the separating blank line, MUST NOT exceed the bound — repeatedly; a single paragraph longer than the bound is split at the last LF at or before the bound, and, failing that, at the bound on a code-point boundary — only in that last case may a chunk's text end without LF and the next begin mid-line. No overlap. The heading is not repeated into continuation chunks. [design]
  • AGSC-06-28 Identifier. id is the lowercase-hex SHA-256 of the UTF-8 bytes of the item IRI, then one U+0000 (NUL) byte, then the section path, then one U+0000 (NUL) byte, then the ordinal in decimal — where the section path is the AGSC-03-13 anchor of the chunk's heading (the empty string for chunk 0) and the ordinal is the zero-based index of the chunk within that section after Cut 2. Two conforming writers therefore derive identical ids from identical sources; an agent cites a chunk back as the item IRI followed by #chunk- and the first 16 hex characters of id, which a page MUST render as an in-page anchor on the chunk's heading (the top of the page for chunk 0). [design]
  • AGSC-06-29 Record shape. Members, all REQUIRED unless marked: digest (lowercase-hex SHA-256 of the UTF-8 bytes of text), id, iri (the item IRI), item (the slug), kind (the item type), subkind (OPTIONAL: the concept kind, present only on concepts), license (bundle.license_prose), links (the item's authored Links as an object of key → slug arrays (anchors stripped; each array in code-point order) in JCS order; a target naming an item excluded by AGSC-06-30 is dropped from its array and a key emptied by that drop is omitted (the exclusion every other surface applies); OPTIONAL when empty), ordinal, section (the anchor; empty for chunk 0), terms (the Content Use Terms identifier of AGSC-06-18), text, title, trust (always untrusted — the value an agent MUST attach when the text re-enters a model, AGSC-08-18), type (text, or the media type of an attachment chunk, AGSC-06-30). A 1.0 writer emits no other member; x-<vendor>-<key> members MAY follow (AGSC-02-05a), a later MINOR may add members, and a reader MUST ignore a member it does not know (AGSC-00-21). Lines are ordered by item slug (code point), then section (code point), then ordinal ascending numerically. [PRD-061, AGSC-11-18]
  • AGSC-06-30 Exclusions and attachments. Items with status retired (AGSC-11-22) or draft, and items held back by the releases switchboard (AGSC-01-20), are excluded — the same set that search.json and /llms.txt exclude; a cluster contributes one chunk (its description; a cluster without description contributes no chunk). Each attachment of an item (AGSC-02-98) contributes one chunk whose type is the attachment's media type, whose text is the attachment's alt text for binary media and the file's full text for image/svg+xml and other text media, whose section is attachment-<n> (<n> the 1-based index in attachments[]) and whose ordinal is 0; a cluster's chunk has item = the cluster slug, iri = the cluster IRI, section empty and ordinal 0. The in-page anchor of AGSC-06-28 is required only for chunks that begin with a heading; every other chunk is cited at the top of its page. Peer-derived content never appears in a node's own export (AGSC-11-11). [design]
  • AGSC-06-31 Budgets: /chunks.jsonl MUST NOT exceed 8 KB per published item on average; above 500 items a writer MUST shard as /chunks-<nn>.jsonl (<nn> zero-padded from 01, each shard the lines of at most 500 items in slug order, no item split across shards) with /chunks.jsonl becoming the JCS-canonical manifest {"bundle_version": <string>, "lines_total": <integer>, "shards": ["/chunks-01.jsonl", …]} (paths in shard order; bundle_version is the content version of AGSC-04-25, and a chunk line does not carry it, its member set being closed by AGSC-06-29), exactly as AGSC-06-21 shards the index. A chunk line carries no index into any other line, so AGSC-06-21's shard-reading rule has no counterpart here: a reader concatenates the shards in manifest order and needs nothing else (so that a reader of the two sharding rules does not look for a rule that is deliberately absent). [AGSC-06-21]

6.6 JSON-LD context file

  • AGSC-06-32 A Level ≥ 2 writer MUST emit /ns/context.jsonld, the target of the …/rel#context link (AGSC-06-10) and of the application/ld+json branch of /ns/ negotiation (AGSC-06-06). It MUST be generated from ontology/agsc.ttl by a deterministic mapping — every asc: term becomes a term definition whose @id is its IRI, object properties carry @type @id, datatype properties carry the @type of their declared range, and — because graph.jsonld also uses external vocabularies — the prefixes dcterms, prov, rdfs, schema, skos and xsd are defined together with a typed term definition for every external property a rule of §05, §06 or §11 emits (rdfs:seeAlso as @id, the SKOS, DCTerms, PROV and schema.org properties named in AGSC-05-14…20, 05-27, 05-29, 06-18 and 11-12); no term is ever mapped to null (a null term definition, which JSON-LD 1.1 keeps as a blocked term so that it can never be used); @version 1.1 and @protected true are set — sorted per AGSC-04-05, and MUST round-trip: expanding graph.jsonld with it and re-compacting MUST reproduce graph.jsonld as a value, and MUST reproduce it byte for byte once the compacted result is serialised in the canonical form of AGSC-04-05 (JCS over NFC strings), which is the form graph.jsonld is written in — a JSON-LD processor fixes no member order, so the canonical serialisation is the step that makes the comparison a byte comparison. The term name of an asc: term is its local name; the term name of an external property is its local name, or its compact IRI (<prefix>:<local>) where that local name is also an asc: term name or is shared by two external properties. The full context file is therefore a constant of this specification, derived from ontology/agsc.ttl and from nothing about a node, and a node's /ns/context.jsonld MUST equal it byte for byte (AGSC-05-09). (Rationale: the member names of graph.jsonld are these term names, and AGSC-04-24 claims byte-identity for graph.jsonld across implementations; the vector graph-0011 uses the bare local name.) Released context files are immutable (AGSC-00-16); the versioned copy lives at /ns/<version>/context.jsonld. [AGSC-05-09]

6.7 Static query fragments (SHOULD, sacrificial)

  • AGSC-06-33 A Level ≥ 2 writer SHOULD emit /graph/fragments/s/<subject-hash>.nq for every distinct subject IRI and /graph/fragments/p/<predicate-hash>.nq for every distinct predicate IRI of graph.nq — each file the byte-sorted N-Quads lines sharing that term, the hash being the first 16 hex characters of the SHA-256 of the IRI — plus /graph/fragments/index.json {subjects, predicates, generated_at} — JCS-canonical, subjects and predicates arrays of file paths in code-point order. Object fragments are NOT emitted at 1.x. A writer that does not emit fragments MUST NOT emit the index. (Non-normative: a static subset of the Triple Pattern Fragments interface at the dump end of the Linked Data Fragments spectrum; counts and controls are omitted at 1.x.) [design]

6.8 Dataset vocabularies — VoID and DCAT (informative)

VoID is cited as complementary prior art by AGSC-06-12 (a MUST). DCAT 3 (W3C Recommendation, 22 August 2024) is the catalogue vocabulary a publisher or an aggregator MAY use to describe a Bundle as a dataset; this specification defines no DCAT emission and no rule depends on one, so the mapping below is a courtesy to catalogue maintainers and adds no term to ontology/agsc.ttl. Where a publisher emits it, the natural mapping is: the Bundle IRI is a dcat:Dataset (and, being a skos:ConceptScheme, also the dcat:themeTaxonomy of its own catalogue record); dcterms:title/dcterms:description from site.title/content/index.md; dcterms:license from bundle.license_prose; dcterms:modified from the build instant; each machine artefact of AGSC-06-01 is a dcat:Distribution with dcat:accessURL the route, dcat:mediaType the served type and spdx:checksum the same SHA-256 the link set carries as digest; the discovery document itself is the dcat:landingPage-adjacent entry point, and the …/rel#graph targets are the distributions a triple-store consumer wants. A VoID description (void:Dataset, void:dataDump = /graph.nq, void:vocabulary = the /ns/ IRI) may sit beside it at /.well-known/void; both are optional, both point at artefacts this specification already pins, and neither is a conformance target at 1.x.
