AGSC-00 — Overview, terms, conformance model

SummaryWhat the specification covers, the words it uses, what it means to conform, and how versions change.

Status of this document

Specification 1.1.0, a draft of this version, not yet tagged. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

Part 1 of 2, 0.1 to 0.4. This section is published in two parts so that each page stays within the budget of AGSC-06-21; a rule's link names the part that carries it. Part 2 carries 0.5 to 0.7.

In plain language

What it is. AgenticSystemCore is a file format plus a few fixed outputs. You write knowledge as Markdown files with a small YAML header, keep them in one directory with one configuration file, and a conforming tool turns that directory into a website, a graph, a search index, an agent-facing text file, a chunk export and a discovery document — the same bytes every time, on any machine.

What conformance means. A tool is a reader, a writer or a full engine; a published site is a node at Level 0 to 3. A claim names the class or Level, the spec_version and the test vectors passed. There is no badge and no registry — the vectors are the proof.

Terms you will meet. A Bundle is the directory. An Item is one file; its type is one of concept, episode, procedure, lesson, cluster or gate. NOW is a generated summary page. Words like card, deck or page are never types.

How versions move. The spec_version is MAJOR.MINOR.PATCH. A MINOR adds and never removes; a reader must ignore what it does not know and must not fail on a higher MINOR. Only a MAJOR may break.

Where requirements live. Every product requirement that is served by the shape of the artefacts rather than one sentence is cited in §0.5, so a validator can check the citation.

Two terms complete the language for Mode 5 — an agent lane (a declared, budgeted agent that proposes, never writes) and the live board — and one rule names the whole declared scope of the specification with the version at which each part becomes normative.

One section states what readers and writers must do across versions — ignore and keep what they do not know, carry it through a round trip, never emit for a version they do not claim — closes the list of plugin kinds at eight, and reserves names for version 1.1.

This box explains; the rules below decide. New to the notation? See how to read the specification.

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this specification are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174) when, and only when, they appear in all capitals, as shown here. Each rule has a stable id AGSC-<section>-<nn>; ids are never reused or renumbered. Section numbers are stable in the same way, so a number that no section carries (§2.6 to §2.8 and §9.5 to §9.8) is unused on purpose. A rule marked (reference distribution) binds, in the clauses that name it, the reference distribution of this specification (its engine, validators and test suite), not a node or another implementation. Trailing brackets cite the requirement each rule serves: a requirement id of the product requirements (PRD-nnn, NFR-nn, ADR-nnn), an external standard, or a related rule; a bracket that reads [design] marks a rule settled in design review with no single listed requirement.

0.2 Terms

  • AGSC-00-04 Bundle — one directory tree of Markdown items plus exactly one agsc.config.json; the unit of publication and of conformance. [design]
  • AGSC-00-05 Item — one .md file with YAML frontmatter whose type is one of concept, episode, procedure, lesson, cluster, gate. "Item" is a term of this specification only; no common superclass exists in the ontology (§05). A published item is one that is neither draft nor held back by the releases switchboard (AGSC-01-20); a listed item is a published item that is not retired. A retired item is published — it keeps its page, its per-item copies, its place in the graph exports (AGSC-11-22) and its resource on the local tool server (AGSC-09-14b) — and is not listed: it leaves search.json, /llms.txt, /llms-full.txt, /chunks.jsonl, the skill packs, agsc-counts, the index pages that list items (a type's, a tag's, a cluster's members, the home page and the search page), every composition selection and what the page tools see (AGSC-09-16). A rule that names "the published set (AGSC-06-30)" means the listed set. The local tool server of AGSC-09-13 is not a published surface: it reads the author's own Bundle, draft and held-back items included. (Amended 2026-10-02 for 1.0.0: "published" had these two extents and no definition.) (Amended 2026-10-06 for 1.0.0: the index pages are named among what a retired item leaves; until 1.0.0-rc.6 the reference engine also dropped its page, its per-item copies and its graph entry, against AGSC-11-22.) (Amended 2026-10-10 for 1.0.0: the lists of what a retired item keeps and leaves did not name the tool server's resources, /llms-full.txt or the page tools, and the local tool server, which reads drafts, was not set apart from the published surfaces) [design]

  • AGSC-00-06 Concept (with a kind qualifier), Episode, Procedure, Lesson, Cluster, Gate are the six item types. Link, Source, Proposal, Review, Bundle, Harness complete the ubiquitous language; Proposal and Review have no file (they are a forge pull request and its verified[] evidence), Source is an inline sources[] entry, and a Harness is generated output only. The rules also use the terms below, each defined once here; none of them is a type, a schema key or an ontology term. A mode is a way of using one Bundle: no mode adds a type, a key or a term, and a conformance claim names a Level (§10), never a mode.

    • Mode 0 — the auto-wiki: Markdown items built into a site with a graph, search, the agent-facing text files and a discovery document, with no model anywhere (§6). The agent lane of AGSC-00-19 is optional in every mode.
    • Mode 1 — distributed agentic memory: agents read a node through the local tool server or the page tools (§9) and change it only by Proposals that a person ratifies (§8); nodes federate on the client side (§11).
    • Mode 2 — live specifications and engineering memory: Concepts of kind principle, decision, spec, task and term, with gates and episodes, joined by the five Mode-2 Links implements, verifies, covers, blocked-by and decided-by (AGSC-03-01), and read as boards in project mode (§10.5).
    • Mode 3 — the evolving skills wiki: Procedures exported as one skill pack per cluster (§7.4), and lessons kept as the record of failures.
    • Mode 4 — runnable knowledge: a composition of Concepts yields a Harness (§7).
    • Mode 5 — the live board of AGSC-00-19 and §10.6.
    • Persona — one of the people and agents the requirements document describes, numbered P0 to P15 (docs/PRD.md §1). A rule that names a persona names a reader a node serves; it binds no persona.
    • Forge — the service that hosts the Bundle's git repository and runs its pull requests, rulesets and continuous integration. The reference distribution ships a forge shim for GitHub only (AGSC-08-12, AGSC-00-20).
    • Content branch — the branch of the Bundle's repository that a node is built and published from. Continuous integration never commits to it, except for the channel:auto merge of AGSC-08-26 (AGSC-08-02), and the tool server hands its changes to it as Proposals and never writes to it (AGSC-09-14b).
    • Namespace document site — the one origin that the w3id redirects of AGSC-06-06 resolve to, https://agenticsystemcore.com/. It serves this specification's vocabulary, JSON-LD context and schemas under /ns/ and its pages under /specs/; a content node does not serve those routes (AGSC-06-01).
    • Launch pipeline — the ci and review lanes and everything they call; AGSC-08-27 keeps every model call out of it.
    • refs[] — on an Episode (AGSC-02-14), an optional list of distinct http: or https: URLs of what the occurrence concerns, such as a pull request, an issue or a run log. It is kept as authored; it makes no Link, and no rule derives anything from it at 1.0.
    • Private names — urn:agsc: (the source forms of AGSC-02-10 and AGSC-08-28) and memory: (the alias of AGSC-05-04…05-04b) are names private to this specification: the URN namespace agsc is not registered under RFC 8141 and the URI scheme memory is not registered under RFC 7595. Each is never dereferenced over a network and means only what the rule that uses it says.

    (Amended 2026-10-10 for 1.0.0: the terms that the rules use without a definition were defined here — the six modes and the Mode-2 Links, persona, forge, content branch, namespace document site, launch pipeline and refs[] — and the two unregistered private names were stated as such.) [design]

  • AGSC-00-07 NOW is generated context, never an item and never hand-edited. [design]
  • AGSC-00-08 Card, page, deck and note are UI or import vocabulary; they MUST NOT appear as a type, a schema key or an ontology term. [design]
  • AGSC-00-19 Agent lane and live board complete the language for Mode 5. An agent lane is the OPTIONAL, configured capability by which a model-driven or programmatic agent creates, edits, reviews and updates items non-deterministically — always as Proposals, never as writes (AGSC-01-36, AGSC-08-28…30). A live board is a Bundle used as the shared working memory and pull-based task board of people and agents, local or remote: work is pulled by whoever claims a task, at most max_claims at a time, until the board is done (AGSC-10-16…18). The name says what it is — a board that is live, shared and always current; its operating discipline is Kanban's pull with a work-in-progress limit, and the blackboard architectural pattern (Hayes-Roth 1985, Nii 1986 — docs/RELATED-WORK.md) is its lineage. Neither adds a type, an item key or an ontology term; both are realised entirely with the objects §0.2 already names. [design]

(Amended 2026-11-09 for 1.1.0: the direct memory adapters for Mem0, Letta, Zep and CSV, and for Basic Memory and Claude Code's memory files, move from the capabilities planned for a later MINOR to the capabilities of the reference distribution in 1.1, as settled on 9 November 2026. They are adapters under AGSC-01-26a, which already permits them (MAY); no rule, no case and no conformance claim changes, and no Bundle's emitted bytes change.) (Amended 2026-11-11 for 1.1.0: three places gave the later MINOR a version number; they now say "not in 1.1" and "a later MINOR", because this specification names no version after 1.1 for what it defers. A clarification: no tool behaviour and no emitted byte changes.) (Amended 2026-11-11 for 1.1.0: in (d), site.query_page switches off the /query/ page alone (AGSC-06-39); the graph view with backlinks (AGSC-06-38) has no switch. A clarification: no tool behaviour changes.) [PRD-065, AGSC-00-14]

0.3 Conformance classes

  • AGSC-00-09 A reader MUST implement §01–§03 and §05 read-side: locate items, parse the frontmatter subset, validate against schema/item.schema.json, resolve the fourteen Link keys — nine core + five Mode-2, only the core nine driving composition — and compute their inverses. A reader MUST pass every required vector in the areas frontmatter/, slug/, links/. [PRD-002, PRD-003]
  • AGSC-00-10 A writer MUST implement §04, §05 and §06: canonical JSON, the four RDF views, the route set and the discovery files. A writer MUST pass every required vector in jcs/, graph/ and discovery/, and MUST be a conforming reader. [PRD-004, PRD-022, PRD-024]
  • AGSC-00-11 A full engine MUST additionally implement §07 (composition), §08 (governance) and §09 (CLI contract) and MUST pass every required vector in every area. [PRD-036, PRD-042, PRD-001]
  • AGSC-00-12 An implementation claiming conformance MUST state its Level (AGSC-10-01 maps the class names of AGSC-00-09…11 to Levels 0–3, once), its spec_version and the vector set it passed — the full list of what a claim states is AGSC-09-01. It MUST NOT claim a class whose vectors it does not pass. (Amended 2026-10-02 for 1.0.0: the pointer to AGSC-09-01 added.) [PRD-010]
  • AGSC-00-13 Optional vectors ("level": "optional") MAY fail without losing conformance; they cover SHOULD-level rules. A withdrawn vector (AGSC-00-16) is excluded from every class's required set and MUST NOT be run for a conformance claim. [design]

0.4 Versioning

  • AGSC-00-14 spec_version is SemVer 2.0.0. MAJOR means a file valid under the previous MAJOR MAY fail validation; MINOR adds optional keys, enum values, link semantics or vectors; PATCH clarifies text or adds vectors that conforming implementations already pass. A MINOR MAY also make a tool's output more cautious — a warning where a tool gave none, the status draft where it kept a source's status, a check of what the tool itself writes — provided no file and no Bundle that was valid under the previous MINOR becomes invalid: a check that would refuse such input ships as a warning, unless a rule of the same MAJOR already required the refusal. Bytes that a Bundle valid under the previous MINOR makes a writer emit change only where a rule of the new MINOR says so and names them. Two named exceptions are listed in the change log. (1) A key that a MINOR adds is validated from that MINOR on, in any item that carries it, even where a Bundle of the previous MINOR used the same key name with another value: a tool of the previous MINOR preserved such a key and ignored it (AGSC-00-21, AGSC-02-05), so no Bundle could rely on its value (AGSC-02-25, AGSC-03-27, AGSC-05-40). (2) Three answers that a client of 1.0 can see are replaced by the answers the protocol or the conformance run defines: a call of a tool that the server does not serve is a JSON-RPC error and no longer an envelope with AGSC-E001, a failed conformance case is AGSC-E005 and no longer AGSC-E001, and search answers at most 100 hits (AGSC-09-13, AGSC-09-13a, AGSC-09-02). (Amended 2026-10-29 for 1.1.0: the sentence on cautious output and on named byte changes added, and the two named exceptions; the import rule of AGSC-01-22 and the warnings of AGSC-01-40 and AGSC-08-32 rest on it) [design]
  • AGSC-00-15 A reader MUST accept any Bundle whose spec_version MAJOR equals its own — except its configuration, below — MUST tolerate unknown keys and unknown link keys, and MUST NOT reject a file for them. (Amended 2026-10-02 for 1.0.0: "except its configuration, below" added; the sentence that follows already made agsc.config.json the exception.) This key tolerance governs item frontmatter (AGSC-02-05) and documents a reader did not author — a received discovery document, a peer board, a file under import or --peer (AGSC-11-02). agsc.config.json is deliberately closed (AGSC-01-18) and is the one asymmetry of docs/SPEC.md §6(10): a MINOR that adds a configuration key therefore also raises the MINOR a tool must claim in order to read that Bundle's configuration, and a 1.0 tool reports AGSC-E004 — loudly, by design (AGSC-00-20). §0.6 states this tolerance in full, construct by construct, together with what survives a round trip and what a tool may never originate (AGSC-00-21…23). A writer MUST refuse, with AGSC-E004 and exit 2, a Bundle whose spec_version in agsc.config.json has a MAJOR it does not implement, and SHOULD warn (AGSC-E506) when that version is a newer MINOR of its own MAJOR — the acceptance above is of MAJOR-equal Bundles, and an import refuses a foreign MAJOR (AGSC-01-22). [OKF v0.2]
  • AGSC-00-16 A released version is immutable: its tag is the permanent copy of every file of spec/, schema/, ontology/ and tests/vectors/, and a versioned context or vocabulary copy, once published, never changes (AGSC-05-25, AGSC-06-06). For a later version the chapters of spec/ are amended in place, each changed rule carrying the dated note this rule requires below. A vector that AGSC-00-03 shows to be wrong MUST NOT be edited in place: the corrected case ships as a new versioned vector file and the superseded file is retained with its level republished as withdrawn (excluded from every claim, AGSC-00-13). Editing, at an rc bump or at the release, the specification-version string a released vector carries — options.spec_version, and the same string wherever the case's input or expected states the version an implementation reports or emits — or re-pointing its rule to the rule that absorbed a retired one, is not a change to the case and is done in place. A rule changed by a later version keeps its id and carries a dated amendment note that states the change; a rule withdrawn by a later version keeps its id as reserved, and the id is never reused. Ontology terms are never deleted — they are marked owl:deprecated true with dcterms:isReplacedBy. (Amended 2026-10-02 for 1.0.0: until 1.0.0-rc.6 this rule began "Released spec sections, JSON-LD context files and vector files are immutable; a change creates a new versioned file", which chapters amended in place could not follow; the tag is the immutable copy.) [design]
  • AGSC-00-17 spec_version MUST appear in the Bundle root content/index.md and in agsc.config.json; it MAY appear per item and, when present, MUST have the same MAJOR. An item whose spec_version carries another MAJOR is AGSC-E204 — the value fails the MAJOR the Bundle fixes, which is a pattern constraint on that key. Where the root document and the configuration carry different values, the configuration's value governs: it is the value an item's MAJOR is compared with, here, and the one a writer checks against its own version (AGSC-00-15). At 1.0 the root document's value is compared with neither, so the two are meant to be equal. From 1.1 a tool reports a difference between them as the warning AGSC-E506, which changes no exit code and no emitted byte. (Amended 2026-10-10 for 1.0.0: the rule did not say which value governs when the two differ; the item check compares with the configuration's value, which "the MAJOR the Bundle root fixes" did not say.) (Amended 2026-10-29 for 1.1.0: the finding for a difference between the two values, which 1.0 left to a later version, is added as a warning) [design]
