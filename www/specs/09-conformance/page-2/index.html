AGSC-09 — Conformance: classes, vectors, error codes, CLI contract

SummaryHow a claim is made and checked: classes and Levels, the vector format, the command-line contract, the error-code registry and the independent validators.

Status of this document

Specification 1.1.0, released and tagged on 2026-11-13. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

Part 2 of 3, 9.3 (continued) to 9.4. This section is published in three parts so that each page stays within the budget of AGSC-06-21; a rule's link names the part that carries it. Part 1 carries 9.1 to 9.3; Part 3 carries 9.4 (continued) to 9.9.

In plain language

Classes and claims. Reader, writer, full engine; a claim names the class, the version and the vectors passed.

Vectors. One JSON file per test case under tests/vectors/<area>/, with an input, an expected result and the rule it proves. Twenty-five areas exist; a required vector that is skipped counts as a failure. Withdrawn vectors are kept for history and never run.

The CLI. Sixteen verbs, a JSON envelope on every result, exit codes with fixed meaning, no stray output on the tool channel. The local tool server exposes exactly ten tools.

Error codes. AGSC-E<nnn> in blocks by area (0xx CLI, 1xx parse, 2xx schema and boundary configuration, 3xx links, 4xx lint, 5xx provenance and adoption, 6xx canonicalization and determinism, 7xx ledger, 8xx composition, 9xx I/O and federation), registered once each; every code used has a registry row that names the rule that raises it.

Validators. A reference distribution ships standalone validators for the spec text, schemas, ontology, vectors, discovery file, features and diagrams, plus four generators — eleven command contracts in all (AGSC-09-90) — so that an independent party can check every normative artefact.

This box explains; the rules below decide. New to the notation? See how to read the specification.

9.3 CLI contract (continued)

  • AGSC-09-19 MCP revisions. The tool server speaks MCP revision 2026-07-28 (https://modelcontextprotocol.io/specification/2026-07-28, read 2026-10-29) and, over standard input and output only, revision 2025-11-25 as well. A request that carries io.modelcontextprotocol/protocolVersion in its _meta is served under 2026-07-28, statelessly; a client that opens with initialize is served under the revision that request negotiates, as 1.0 serves it (AGSC-11-18). Under 2026-07-28 the server:

    1. implements server/discover: its result is {resultType: "complete", supportedVersions, capabilities, ttlMs, cacheScope, _meta}, where supportedVersions lists the revisions of the transport — ["2026-07-28", "2025-11-25"] on standard input and output, ["2026-07-28"] over HTTP (AGSC-09-18) —, capabilities is the object AGSC-11-18 pins (the capabilities prompts, resources and tools, none with listChanged or subscribe, and the extensions map with the identifier com.agenticsystemcore/knowledge) and _meta holds io.modelcontextprotocol/serverInfo with the server's name and version; 2. puts resultType: "complete" on every result and the members ttlMs 0 and cacheScope "private" on the results of server/discover, tools/list, prompts/list, resources/list, resources/templates/list (the server holds no templates, so the result is an empty list that still carries both members) and resources/read: the server answers from the Bundle on disk (AGSC-09-13), which can change between two requests and holds items that are not listed, so no result is fresh for a moment and none may be shared; 3. lists tools in code-point order of name, and returns no resultType: "input_required" — it asks a client for nothing, because every write it offers returns prepared text (AGSC-11-18) — and does not implement subscriptions/listen, answering it as an unknown method; 4. answers a resources/read of a URI that names no resource with the JSON-RPC error -32602 and data {"uri": <the URI>}; under 2025-11-25 the code is -32002, with the same data; 5. answers a tools/call that names a tool it does not serve, and a request whose parameters fail MCP's own schema, with a JSON-RPC error -32602, under both revisions, and sets isError of the result of any other call as AGSC-09-13a says; 6. gives every tool of tools/list annotations with readOnlyHint as AGSC-11-18 sets it, openWorldHint false — the world of this server is its Bundle, and the default of the protocol is true — and, on propose and remember, destructiveHint false, since they only return text and the default of the protocol is true; the same annotations are given under 2025-11-25.

    The mcp surface of a node whose server speaks both revisions declares one value, 2026-07-28, as its agsc-surface-version (AGSC-11-16): the newest revision it speaks, which a client of 2025-11-25 does not need to know, since it is served on standard input and output without it. The constant that a distribution names as its protocol version is that value, and a distribution whose server speaks 2025-11-25 only declares that revision, as AGSC-11-16 says. Over standard input and output the first request other than server/discover fixes the revision of the process (MCP 2026-07-28, basic/versioning: the semantics of the earlier revision are scoped to the stdio process): a later request of the other revision, or of a revision the server does not speak, is the JSON-RPC error -32022, whose data.supported names the revision of the process alone; before the first such request it names both. Vectors cli-0032, cli-0033, cli-0034 and cli-0035. (Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: the server now answers the current revision beside the one 1.0 spoke, and the error reporting, the annotations and the error code of a missing resource follow the revision that is negotiated) (Amended 2026-11-10 for 1.1.0: the sentence on the stdio process is added; a process fixed to 2026-07-28 by a first request now names that revision alone in -32022, as one fixed to 2025-11-25 by initialize already did, and the case modern of cli-0034 states it) [design, AGSC-11-18]

9.4 Error-code registry

Codes are AGSC-E<nnn> and nothing else; the hundreds digit is the area (0 CLI, 1 PARSE, 2 SCHEMA, 3 LINK, 4 LINT, 5 PROV, 6 DET, 7 LEDGER, 8 COMPOSE, 9 IO). No other code format (AGSC-<AREA>-<nnn>, AGSC-DET-nnn) exists anywhere in this system; prose or a diagram using one is a defect of that document.

Precedence. Where two codes could name one fault, the more specific one wins: AGSC-E203 is reported for every enum and tags.allowed violation, AGSC-E204 for every pattern violation and every minLength/maxLength violation, and AGSC-E201 only for a schema failure that no more specific registered code, in any block, names — a maxItems violation on a cluster's broader is AGSC-E308, not AGSC-E201. Two conforming engines therefore report the same code for the same input. Applying that rule to one pair: an out-of-range value inside federation{}, chunks{}, contribute[], visibility or related[] is AGSC-E209, never AGSC-E201, because AGSC-E209 names exactly those objects and is therefore the more specific code; an engine reports one code, not both (AGSC-09-15, AGSC-00-09, AGSC-09-11). (Amended 2026-10-10 for 1.0.0: the requirement to report one code moved into AGSC-09-15)

Severity. Each code has the severity its row gives, in the last column; where the severity depends on the context, the row names each context. An error makes the verb that found it exit 1 — or 2 where the row says so, the usage and configuration class of AGSC-09-08 — and a gate fail; a warning is reported and never changes an exit code. A rule that names a code never gives it another severity than its row. (Amended 2026-10-02 for 1.0.0: until 1.0.0-rc.6 the registry had no severity column, "(warning)" stood in some rows only, and AGSC-E108, AGSC-E204, AGSC-E401, AGSC-E402 and AGSC-E407 took a severity stated in another chapter; the column states what those rules already say and changes no severity.)
