AGSC-09 — Conformance: classes, vectors, error codes, CLI contract

SummaryHow a claim is made and checked: classes and Levels, the vector format, the command-line contract, the error-code registry and the independent validators.

Status of this document

Specification 1.0.0-rc.7, a release candidate tagged on 2026-10-08. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

Part 2 of 2, 9.4 to 9.9. This section is published in two parts so that each page stays within the budget of AGSC-06-21; a rule's link names the part that carries it. Part 1 carries 9.1 to 9.3.

In plain language

Classes and claims. Reader, writer, full engine; a claim names the class, the version and the vectors passed.

Vectors. One JSON file per test case under tests/vectors/<area>/, with an input, an expected result and the rule it proves. Twenty-five areas exist; a required vector that is skipped counts as a failure. Withdrawn vectors are kept for history and never run.

The CLI. Sixteen verbs, a JSON envelope on every result, exit codes with fixed meaning, no stray output on the tool channel. The local tool server exposes exactly seven tools.

Error codes. AGSC-E<nnn> in blocks by area (0xx CLI, 1xx parse, 2xx schema and boundary configuration, 3xx links, 4xx lint, 5xx provenance and adoption, 6xx canonicalization and determinism, 7xx ledger, 8xx composition, 9xx I/O and federation), registered once each; every code used has a registry row that names the rule that raises it.

Validators. A reference distribution ships standalone validators for the spec text, schemas, ontology, vectors, discovery file, features and diagrams, plus two generators — nine command contracts in all (AGSC-09-90) — so that an independent party can check every normative artefact.

This box explains; the rules below decide. New to the notation? See how to read the specification.

9.4 Error-code registry

Codes are AGSC-E<nnn> and nothing else; the hundreds digit is the area (0 CLI, 1 PARSE, 2 SCHEMA, 3 LINK, 4 LINT, 5 PROV, 6 DET, 7 LEDGER, 8 COMPOSE, 9 IO). No other code format (AGSC-<AREA>-<nnn>, AGSC-DET-nnn) exists anywhere in this system; prose or a diagram using one is a defect of that document.

Precedence. Where two codes could name one fault, the more specific one wins: AGSC-E203 is reported for every enum and tags.allowed violation, AGSC-E204 for every pattern violation and every minLength/maxLength violation, and AGSC-E201 only for a schema failure that no more specific registered code, in any block, names — a maxItems violation on a cluster's broader is AGSC-E308, not AGSC-E201. Two conforming engines therefore report the same code for the same input. Applying that rule to one pair: an out-of-range value inside federation{}, chunks{}, contribute[], visibility or related[] is AGSC-E209, never AGSC-E201, because AGSC-E209 names exactly those objects and is therefore the more specific code; an engine MUST report one code, not both (AGSC-00-09, AGSC-09-11).

Severity. Each code has the severity its row gives, in the last column; where the severity depends on the context, the row names each context. An error makes the verb that found it exit 1 — or 2 where the row says so, the usage and configuration class of AGSC-09-08 — and a gate fail; a warning is reported and never changes an exit code. A rule that names a code never gives it another severity than its row. (Amended 2026-10-02 for 1.0.0: until 1.0.0-rc.6 the registry had no severity column, "(warning)" stood in some rows only, and AGSC-E108, AGSC-E204, AGSC-E401, AGSC-E402 and AGSC-E407 took a severity stated in another chapter; the column states what those rules already say and changes no severity.)

9.9 Independent validation tooling

  • AGSC-09-90 The reference 1.0.0 distribution MUST include the tools/ validators of PRD-054, each runnable standalone — no import from src/; a validator MAY use the same pinned libraries as the engine (what the rule protects is independence from the engine, not abstinence from libraries) — so that every normative artifact (schemas, spec text, ontology, vectors, well-known file, features, diagrams) is checkable by an independent party; any other distribution MAY substitute its own implementation of the same nine command contracts (same names, same flags, same AGSC-09-11 envelope, same codes), and a conformance claim names which it ran. A validator's --json output MUST be the AGSC-09-11 envelope with verb set to the tool's own name (validate-spec, validate-schemas, validate-ontology, validate-vectors, validate-wellknown, validate-features, validate-diagrams, and the generators gen-spec-html and gen-ns) and version set to the tool distribution's own package version (the envelope's spec_version member already carries the version validated against, so the two never duplicate); findings use the same finding object, the same (file, line, col, code) ordering (AGSC-09-10) and the same AGSC-E<nnn> codes. Seven validators and two generators therefore speak one diagnostic language, and no tool invents a shape. No further validator may be added for a job an existing validator already carries: the federation check of AGSC-10-12 is the --peer flag of tools/validate-wellknown, never a separate binary. A validator MUST fail, with AGSC-E901, when the inputs its contract names are absent, or are present and carry nothing it can validate — no file read, no rule found, no vector found; a pass MUST mean that something was checked, and each validator's human-readable summary MUST state how many input files it read, so that a reader can tell "nothing is wrong" from "nothing was looked at" (Rationale: a merge gate that cannot fail protects nothing). A declared vector area with no vector file is not a failure; tools/validate-vectors MUST report it as an informational count, and only a required vector's absence for a rule that names one is a failure; the two clauses do not conflict — one is about an empty area, the other about an empty input set. [PRD-054]

  • AGSC-09-91 tools/validate-spec MUST fail on: duplicate rule id; a rule id referenced but undefined; an error code used in spec/01–11 but absent from the §9 registry; a MUST/SHOULD sentence with no rule id; a trace tag naming a nonexistent PRD/D id; a code appearing in more than one registry row; a code used in spec/01–11 whose registry row does not name the rule that raises it; a registry row naming a rule id that does not exist (grouped-fault rows such as AGSC-E108 and AGSC-E401 stay legal — the hundreds-digit block, not the row, is the unit of precision); a spec_version literal in spec/, tests/vectors/** or docs/ that differs from the spec/00 declaration; a rule id <n>a that does not immediately follow rule <n>.

    Two carve-outs:

    (a) Historical notes. A version literal that differs from the declaration is NOT a fault when it sits on a line that is plainly a record of the past — a line carrying, before the literal, one of the words at, since, amended, added, withdrawn, before, until, from, for, against, written, re-verified as a whole word, or a full date in YYYY-MM-DD form — so that a dated record of the past stays as written instead of being falsified. tools/count-artifacts implements exactly this carve-out and is the reference behaviour.

    (b) Trace brackets after a block. A rule whose text includes a table, a fenced block or an ABNF block carries its trace bracket after that block rather than at the end of its first paragraph — AGSC-01-28, AGSC-07-12, AGSC-08-06 and AGSC-09-11 are the four — and the "MUST/SHOULD sentence with no rule id" and trace-bracket checks MUST treat the bracket that follows the block as that rule's. A rule with no trace bracket anywhere is still a fault. (AGSC-07-12, AGSC-08-06 and AGSC-09-11 also carry the bracket at the end of their first paragraph, as AGSC-05-26 does, so that a reader that takes a rule's list item alone finds one; the carve-out still admits a bracket after a block.) [PRD-054, NFR-03]

  • AGSC-09-92 CI MUST run all validators on every PR; a validator failure blocks merge like any Gate. [PRD-054, PRD-049]
  • AGSC-09-93 tools/validate-wellknown <url|file> MUST check: the response media type is application/linkset+json or a Link: …; rel="profile" header names the profile URI (AGSC-06-07); linkset is the sole top-level member; every relation name is registered or an …/rel#<name> extension URI of AGSC-06-10; every extension target attribute value is an array of strings and type, title and media are strings (AGSC-06-10); at --level 0 the absence of every digest/agsc-* attribute is accepted, and at --level 2 and above their presence is REQUIRED and each digest is recomputed over the fetched target — except on a node carrying agsc-visibility: ["restricted"], where AGSC-11-20 requires agsc-counts, agsc-bundle-hash, agsc-bundle-version and agsc-ledger-head to be absent, together with the …/rel#ledger link, and a validator MUST accept their absence and report their presence as AGSC-E210. At --level 2 and above a document whose node is not restricted MUST carry the …/rel#ledger link (AGSC-10-04), and its absence is AGSC-E202. When the document's agsc-spec-version has the validator's MAJOR and a newer MINOR, a relation name outside AGSC-06-10 and AGSC-06-35 and a target attribute outside AGSC-06-08 and AGSC-11-16 are ignored, with the warning AGSC-E506 naming the newer version, and are never reported as AGSC-E209 or AGSC-E202 (AGSC-00-21); a document that declares another MAJOR has no such tolerance. Its --peer <url|file> flag performs the mutual-conformance check of AGSC-10-12 and MUST accept two local files so the check runs with no network. Its --dev flag admits plain http to a loopback address, and nothing else (AGSC-11-07, AGSC-11-08). Its --json output is the AGSC-09-11 envelope with verb: "validate-wellknown". (amended 2026-10-02 for 1.0.0: --dev was missing from the contract) Given a URL, it MUST also read the response headers of the discovery document and of every same-origin public artefact of AGSC-11-03 it fetches, and check AGSC-11-03 — Access-Control-Allow-Origin: *, an Access-Control-Expose-Headers that names Link, ETag and Content-Type, and no Access-Control-Allow-Credentials; on a restricted node, on the discovery document alone (AGSC-11-20) — and AGSC-11-05 — an ETag on each, Cache-Control: no-cache on the discovery document, /now.md and /ledger.jsonl, and immutable on none. A missing header or value is AGSC-E202 and a header or value the rules forbid is AGSC-E201; each is an error at --level 2 and above and a warning below, because Levels 0 and 1 do not include the boundary rules (AGSC-10-02, AGSC-10-03) and AGSC-11-05 makes the same a SHOULD for a Level-0 publisher. A file argument carries no response headers, and these checks do not run on it. (Amended 2026-10-06 for 1.0.0: the checker read only the media type, so a node that served none of these headers passed.) [PRD-054]
  • AGSC-09-94 run and trace are the two opt-in verbs of AGSC-09-07 and have no effect unless run.enabled is true in agsc.config.json (AGSC-01-18; default false); with it false both MUST exit 2 with AGSC-E004 — a configuration the tool cannot run against, AGSC-09-08's exit-2 class — reported, as every resolved verb reports a finding, in the envelope of AGSC-09-10, and no run block is read (amended 2026-10-06 for 1.0.0: the reference engine printed no envelope on stdout under --json for this refusal, and cli-0013 required that; cli-0017 supersedes it). run <slug> executes the fenced blocks of a Procedure whose info string is run and compares each captured result with the immediately following expect block (the two info strings are spelled as AGSC-02-22 spells them); the executable info strings, their restriction to procedure items and the rendering-hint status of every other info string are AGSC-02-22's. Execution MUST be refused unless the command's program name is listed in run.allow[]; it MUST run with no network, no shell interpolation, a scrubbed environment and a timeout, and it MUST NOT write inside the Bundle. A command whose program name is not listed is AGSC-E203 — run.allow[] is a closed operator list of exactly the shape that code names — and a captured result that differs from its expect block is AGSC-E602, a recorded result that the run did not reproduce. --dry-run MUST print the resolved command list and execute nothing. trace <file.json> is a pure function: it maps an already-captured agent-run record to an Episode item through the AGSC-01-22/AGSC-02-14 import path and executes no process. A trace record is a JSON object carrying at least started (an instant, AGSC-02-06), and OPTIONALLY ended, actor (AGSC-02-09), title, outcome (AGSC-02-14's enum), body and usage (AGSC-02-14); every other member is preserved under the x-<vendor>-<key> namespace of AGSC-02-05a (Rationale: the record's shape is fixed so that a record written for one engine imports into another, which is the interoperability AGSC-01-22 exists to provide). Neither verb may be required by any conformance Level (AGSC-10-01…06). [PRD-001]
