AGSC-09 — Conformance: classes, vectors, error codes, CLI contract

SummaryHow a claim is made and checked: classes and Levels, the vector format, the command-line contract, the error-code registry and the independent validators.

Status of this document

Specification 1.1.0, a draft of this version, not yet tagged. It is an independent specification: it is not a standard of the IETF, the W3C or any other body, and no standards body has reviewed or adopted it. Released sections are immutable; a correction ships as a new version.

Part 3 of 3, 9.4 (continued) to 9.9. This section is published in three parts so that each page stays within the budget of AGSC-06-21; a rule's link names the part that carries it. Part 1 carries 9.1 to 9.3; Part 2 carries 9.3 (continued) to 9.4.

In plain language

Classes and claims. Reader, writer, full engine; a claim names the class, the version and the vectors passed.

Vectors. One JSON file per test case under tests/vectors/<area>/, with an input, an expected result and the rule it proves. Twenty-five areas exist; a required vector that is skipped counts as a failure. Withdrawn vectors are kept for history and never run.

The CLI. Sixteen verbs, a JSON envelope on every result, exit codes with fixed meaning, no stray output on the tool channel. The local tool server exposes exactly ten tools.

Error codes. AGSC-E<nnn> in blocks by area (0xx CLI, 1xx parse, 2xx schema and boundary configuration, 3xx links, 4xx lint, 5xx provenance and adoption, 6xx canonicalization and determinism, 7xx ledger, 8xx composition, 9xx I/O and federation), registered once each; every code used has a registry row that names the rule that raises it.

Validators. A reference distribution ships standalone validators for the spec text, schemas, ontology, vectors, discovery file, features and diagrams, plus four generators — eleven command contracts in all (AGSC-09-90) — so that an independent party can check every normative artefact.

9.4 Error-code registry (continued)

  • AGSC-09-15 Codes are permanent. A retired code MUST NOT be reused; new codes take the next free number in their block. Where two codes could name one fault, an engine MUST report the one code the precedence paragraph of §9.4 selects, never both. (Amended 2026-10-10 for 1.0.0: the second requirement stood in the precedence paragraph of §9.4, without a rule id) [AGSC-00-16]

9.9 Independent validation tooling

  • AGSC-09-90 (reference distribution) The reference 1.0.0 distribution MUST include the tools/ validators of PRD-054, each runnable standalone — no import from src/; a validator MAY use the same pinned libraries as the engine (what the rule protects is independence from the engine, not abstinence from libraries) — so that every normative artifact (schemas, spec text, ontology, vectors, well-known file, features, diagrams) is checkable by an independent party; any other distribution MAY substitute its own implementation of the same eleven command contracts (same names, same flags, same AGSC-09-11 envelope, same codes), and a conformance claim names which it ran. A validator's --json output MUST be the AGSC-09-11 envelope with verb set to the tool's own name (validate-spec, validate-schemas, validate-ontology, validate-vectors, validate-wellknown, validate-features, validate-diagrams, and the generators gen-spec-html, gen-ns and, from 1.1, gen-shapes and gen-dc-profile) and version set to the tool distribution's own package version (the envelope's spec_version member already carries the version validated against, so the two never duplicate); findings use the same finding object, the same (file, line, col, code) ordering (AGSC-09-10) and the same AGSC-E<nnn> codes. Seven validators and four generators therefore speak one diagnostic language, and no tool invents a shape. No further validator may be added for a job an existing validator already carries: the federation check of AGSC-10-12 is the --peer flag of tools/validate-wellknown, never a separate binary. A validator MUST fail, with AGSC-E901, when the inputs its contract names are absent, or are present and carry nothing it can validate — no file read, no rule found, no vector found; a pass MUST mean that something was checked, and each validator's human-readable summary MUST state how many input files it read, so that a reader can tell "nothing is wrong" from "nothing was looked at" (Rationale: a merge gate that cannot fail protects nothing). A declared vector area with no vector file is not a failure; tools/validate-vectors MUST report it as an informational count, and only a required vector's absence for a rule that names one is a failure; the two clauses do not conflict — one is about an empty area, the other about an empty input set. (Amended 2026-10-10 for 1.0.0: marked (reference distribution) for the obligation on the reference distribution to ship the validators) (Amended 2026-10-29 for 1.1.0: the reference distribution also ships the generators tools/gen-shapes and tools/gen-dc-profile (AGSC-05-24, AGSC-05-26), so that it ships seven validators and four generators (tools/gen-glossary writes docs/GLOSSARY.md, speaks no envelope and is a documentation helper outside this count); they generate files from the schema and the specification and validate nothing, so the closed count of validators and the rule against a further validator stand, and each speaks the same diagnostic language of AGSC-09-11) (Amended 2026-11-10 for 1.1.0: "nine" became "eleven" command contracts, the count of the 1.1.0 amendment of AGSC-09-90 (seven validators and four generators, each answering with the AGSC-09-11 envelope); a factual erratum) [PRD-054]

  • AGSC-09-91 tools/validate-spec MUST fail on: duplicate rule id; a rule id referenced but undefined; an error code used in spec/01–11 but absent from the §9 registry; a MUST/SHOULD sentence with no rule id — one in a table row or in a paragraph outside every rule is such a sentence even when it cites a rule id, since a cross-reference is not its own id; a key word joined to a lower-case negation, or to a capital word with which it forms no key word of RFC 8174; a key word that the text uses and the key-words sentence of spec/00 does not list; a dated amendment note that does not open with the word Amended, one date in YYYY-MM-DD form, the word for, a version and a colon; a trace tag naming a nonexistent PRD/D id; a code appearing in more than one registry row; a code used in spec/01–11 whose registry row does not name the rule that raises it; a registry row naming a rule id that does not exist (grouped-fault rows such as AGSC-E108 and AGSC-E401 stay legal — the hundreds-digit block, not the row, is the unit of precision); a spec_version literal in spec/, tests/vectors/** or docs/ that differs from the spec/00 declaration; a rule id <n>a that does not immediately follow rule <n>.

    Two carve-outs:

    (a) Historical notes. A version literal that differs from the declaration is NOT a fault when it sits on a line that is plainly a record of the past — a line carrying, before the literal, one of the words at, since, amended, added, withdrawn, before, until, from, for, against, written, re-verified as a whole word, or a full date in YYYY-MM-DD form — so that a dated record of the past stays as written instead of being falsified. tools/count-artifacts implements exactly this carve-out and is the reference behaviour.

    (b) Trace brackets after a block. A rule whose text includes a table, a fenced block or an ABNF block carries its trace bracket after that block rather than at the end of its first paragraph — AGSC-01-28, AGSC-07-12, AGSC-08-06 and AGSC-09-11 are the four — and the "MUST/SHOULD sentence with no rule id" and trace-bracket checks MUST treat the bracket that follows the block as that rule's. A rule with no trace bracket anywhere is still a fault. (AGSC-07-12, AGSC-08-06 and AGSC-09-11 also carry the bracket at the end of their first paragraph, as AGSC-05-26 does, so that a reader that takes a rule's list item alone finds one; the carve-out still admits a bracket after a block.) (Amended 2026-10-10 for 1.0.0: four faults were added to the list — a table row or a paragraph outside every rule that only cites a rule id, a malformed key word, a key word the key-words sentence does not list, and a dated note not in the one form) [PRD-054, NFR-03]

  • AGSC-09-92 (reference distribution) The reference distribution's CI MUST run all validators on every pull request; a validator failure blocks merge like any Gate. (Amended 2026-10-10 for 1.0.0: whose CI was not said; the validators check the specification's own artefacts, which the reference distribution holds) [PRD-054, PRD-049]
  • AGSC-09-93 tools/validate-wellknown <url|file> MUST check: the response media type is application/linkset+json, and the profile URI is named by its profile parameter or by a Link: …; rel="profile" header (AGSC-06-07); linkset is the sole top-level member; every relation name is registered or an …/rel#<name> extension URI of AGSC-06-10; every extension target attribute value is an array of strings and type, title and media are strings (AGSC-06-10); at --level 0 the absence of every digest/agsc-* attribute is accepted, and at --level 2 and above their presence is REQUIRED and each digest is recomputed over the fetched target — except on a node carrying agsc-visibility: ["restricted"], where AGSC-11-20 requires agsc-counts, agsc-bundle-hash, agsc-bundle-version and agsc-ledger-head to be absent, together with the …/rel#ledger link, and a validator MUST accept their absence and report their presence as AGSC-E210. On such a node it also checks, at every Level, that the document carries exactly one …/rel#access link (AGSC-11-20): none is AGSC-E202 and more than one is AGSC-E210. At --level 2 and above a document whose node is not restricted MUST carry the …/rel#ledger link (AGSC-10-04), and its absence is AGSC-E202. When the document's agsc-spec-version has the validator's MAJOR and a newer MINOR, a relation name outside AGSC-06-10 and AGSC-06-35 and a target attribute outside AGSC-06-08 and AGSC-11-16 are ignored, with the warning AGSC-E506 naming the newer version, and are never reported as AGSC-E209 or AGSC-E202 (AGSC-00-21); a document that declares another MAJOR has no such tolerance. Its --peer <url|file> flag performs the mutual-conformance check of AGSC-10-12 and MUST accept two local files so the check runs with no network. Its --dev flag admits plain http to a loopback address, and nothing else (AGSC-11-07, AGSC-11-08). Its --json output is the AGSC-09-11 envelope with verb: "validate-wellknown". (Amended 2026-10-02 for 1.0.0: --dev was missing from the contract) Given a URL, it MUST also read the response headers of the discovery document and of every same-origin public artefact of AGSC-11-03 it fetches, and check AGSC-11-03 — Access-Control-Allow-Origin: *, an Access-Control-Expose-Headers that names Link, ETag and Content-Type, and no Access-Control-Allow-Credentials; on a restricted node, on the discovery document alone (AGSC-11-20) — and AGSC-11-05 — an ETag on each, Cache-Control: no-cache on the discovery document, /now.md and /ledger.jsonl, and immutable on no address except the files under a version directory /ns/<major>.<minor>.<patch>/ (AGSC-06-06). It also checks, given a URL, (a) the Link header of /: it carries the describedby link of AGSC-06-25 whose target is the discovery document, and its absence is a warning under AGSC-E202 (AGSC-06-40); (b) at --level 2 and above, on a document whose agsc-spec-version is 1.1.0 or later and whose chunks surface is not declared with the access class credential (a restricted node, AGSC-11-20, omits these attributes), that the …/rel#surface link of the chunks surface carries digest, agsc-chunk-count and agsc-chunk-set recomputed over the fetched /chunks.jsonl (the manifest when sharded), absence being AGSC-E202, while an earlier document is accepted without them (AGSC-06-44); and (c) that agsc-ledger-length, when present, equals the number of entries of the fetched ledger (AGSC-06-44). Cases disc-0026 and disc-0033. A missing header or value is AGSC-E202 and a header or value the rules forbid is AGSC-E201; each is an error at --level 2 and above and a warning below, because Levels 0 and 1 do not include the boundary rules (AGSC-10-02, AGSC-10-03) and AGSC-11-05 makes the same a SHOULD for a Level-0 publisher. A file argument carries no response headers, and these checks do not run on it. (Amended 2026-10-06 for 1.0.0: the checker read only the media type, so a node that served none of these headers passed.) (Amended 2026-10-10 for 1.0.0: the media type is required in every case, as AGSC-06-07 says; the Link header replaces only the profile parameter, and the sentence had accepted either the media type or the header) (Amended 2026-10-10 for 1.0.0: the check of a restricted node's one access link, which AGSC-11-20 requires and the checker did not make, is stated.) (Amended 2026-10-29 for 1.1.0: immutable is allowed on the versioned /ns/ files, and the checks of the describedby header and of the chunk-surface attributes are added; a document of 1.0 is accepted as before) [PRD-054]
  • AGSC-09-94 run and trace are the two opt-in verbs of AGSC-09-07 and have no effect unless run.enabled is true in agsc.config.json (AGSC-01-18; default false); with it false both MUST exit 2 with AGSC-E004 — a configuration the tool cannot run against, AGSC-09-08's exit-2 class — reported, as every resolved verb reports a finding, in the envelope of AGSC-09-10, and no run block is read (Amended 2026-10-06 for 1.0.0: the reference engine printed no envelope on stdout under --json for this refusal, and cli-0013 required that; cli-0017 supersedes it). run <slug> executes the fenced blocks of a Procedure whose info string is run and compares each captured result with the immediately following expect block (the two info strings are spelled as AGSC-02-22 spells them); the executable info strings, their restriction to procedure items and the rendering-hint status of every other info string are AGSC-02-22's. Execution MUST be refused unless the command's program name is listed in run.allow[]; it MUST run with no network, no shell interpolation, a scrubbed environment and a timeout, whose value this specification leaves to the implementation (the reference engine's process runner stops a command after 10 seconds), and it MUST NOT write inside the Bundle. A command whose program name is not listed is AGSC-E203 — run.allow[] is a closed operator list of exactly the shape that code names — and a captured result that differs from its expect block is AGSC-E602, a recorded result that the run did not reproduce. --dry-run MUST print the resolved command list and execute nothing. trace <file.json> is a pure function: it maps an already-captured agent-run record to an Episode item through the AGSC-01-22/AGSC-02-14 import path and executes no process. A trace record is a JSON object carrying at least started (an instant, AGSC-02-06), and OPTIONALLY ended, actor (AGSC-02-09), title, outcome (AGSC-02-14's enum), body and usage (AGSC-02-14); every other member is preserved under the x-<vendor>-<key> namespace of AGSC-02-05a, the vendor name being the implementation's own (the reference engine writes x-trace-<key>) (Rationale: the record's shape is fixed so that a record written for one engine imports into another, which is the interoperability AGSC-01-22 exists to provide). Neither verb may be required by any conformance Level (AGSC-10-01…06). (Amended 2026-10-10 for 1.0.0: the timeout's value and the vendor name of a kept trace member were not said) [PRD-001]
