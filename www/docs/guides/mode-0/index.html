Mode 0 guide: a folder of notes becomes a checked site

SummaryFor a person with Markdown notes: install the package, adopt the notes, add a security contact, commit once, check and build the site, change a note as a proposal, and get it ready to publish.

Who it is for: a person with a folder of Markdown notes, or a team with a handbook, who wants a website out of it that refuses to publish a broken link.

What you get: a static website of your notes, with search and every page also as Markdown; a graph of the notes; text files an assistant can read (llms.txt, chunks.jsonl); a discovery document that lists all of it with SHA-256 digests. No language model, no server, no account. A change to a note becomes a proposal a person merges.

Read after: the guides. Next: Mode 1.

---

Before you start

You need Node.js 22.13 or later, git with your name and e-mail set, and a POSIX shell (bash; on Windows, Git Bash). Install the package once, in a working folder:

mkdir agsc-work && cd agsc-work
npm install agentic-system-core
export PATH="$PWD/node_modules/.bin:$PATH"             # puts agsc and agsc-host on the PATH
export ENGINE="$PWD/node_modules/agentic-system-core"  # the package: examples, checkers, licence texts

The two export lines last for this shell only; run them again in a new terminal. Every command below was run on the package and printed the lines quoted under it (other lines it printed are left out). The repository test tests/docs/guides.test.js runs them again on every change.

1. Adopt your notes

Use your own folder of .md files, or make three notes to follow along:

mkdir my-notes && cd my-notes
printf '# Sourdough starter\n\nFlour and water, fed once a day. How runny it is depends on its [hydration](%s).\n' hydration.md > sourdough.md
cat > hydration.md <<'NOTE'
# Hydration

The weight of the water divided by the weight of the flour.
NOTE
cat > oven-spring.md <<'NOTE'
# Oven spring

The last rise of a loaf, in the first minutes in a hot oven.
NOTE
agsc init
wrote: content/concepts/hydration.md
wrote: content/concepts/oven-spring.md
wrote: content/concepts/sourdough.md
wrote: agsc.config.json
wrote: content/index.md
before you build: add .well-known/security.txt with a Contact: line (RFC 9116); lint, build and ci report AGSC-E901 until it exists (AGSC-06-36)
before you build: commit once, or set SOURCE_DATE_EPOCH, so the build has an instant (AGSC-04-09); the security contact's expiry is checked against it
init: pass (0 error, 4 warn)

What init did, so nothing surprises you later:

  • it moved each note into content/concepts/ and put a short header at its top (a type, a title, kind: explainer, and who is accountable for it);
  • it wrote agsc.config.json (the site's name is the folder's name; the address is the placeholder http://localhost/), content/index.md (the home page), a .gitignore and a .env.example;
  • it took the accountable person's id from your git e-mail (the part before @). With no git e-mail it writes human:unknown; change bundle.operator in agsc.config.json and operator: in each note to human:<your-id> if you want a real name there;
  • it left out any note that already begins with a header (a first line --- closed by a later ---), even one with no type: line: such a note stays where it is, unchanged, and is not published. init names each one:
left as is: handoff.md already has a frontmatter block, so init neither changes nor moves it (AGSC-02-91); it is not an item until it has a type and lives under content/<type-plural>/ (AGSC-01-02)

To publish such a note, delete its header (keep the text) and run agsc init again: it adopts the note like the others and leaves the rest as they are.

2. Add a security contact, commit once, check

A published site must say where to report a security problem (RFC 9116), and a build needs an instant to stamp on what it writes. The commit gives it one:

mkdir -p .well-known && printf 'Contact: mailto:security@example.org\n' > .well-known/security.txt
git init -q -b main && git add -A && git commit -q -m 'my notes'
agsc ci
ci: pass (0 error, 7 warn)
warn: AGSC-E506 site.base is the development placeholder http://localhost/; set an https: base before publishing (AGSC-01-19) — agsc.config.json
warn: AGSC-E408 a concept carries no description (AGSC-02-21) — content/concepts/hydration.md
warn: AGSC-E305 "hydration" has no inbound Link and no clusters[] entry (AGSC-03-10) — content/concepts/hydration.md

Use your own address in Contact: (mailto: or https:). agsc ci checks every note, builds the site twice and compares the bytes, and verifies the result. A warning does not stop anything: here, notes without a one-line description, and notes no other note points at with a typed link (a link in the text is fine for readers but does not count; typed links are explained in the data model). An error stops the build and names the file and line.

3. Build, and look at it

ci checks; build writes the site into www/:

agsc build
ls www www/.well-known
wrote: 59 files under www/
build: pass (0 error, 4 warn)
index.html
llms.txt
graph.jsonld
chunks.jsonl
search.json
knowledge-linkset
security.txt

To read it in a browser, serve the folder (stop with Ctrl-C):

agsc-host serve
serving …/my-notes/www at http://localhost:8080/ — read-only; stop with Ctrl-C

To run the checkers against this address, see the publishing guide §6 — localhost, not 127.0.0.1, in site.base and on the command line.

Each note has a page under /concepts/<name>/ and a Markdown copy under /pages/<name>.md; /.well-known/knowledge-linkset is the discovery document an agent reads first.

A note that has typed links gets a Relations section on its page: a small drawing of the notes it links to and the notes that link to it, and a table with one row per link that gives the relation, its direction, the other note and what the relation means. The incoming rows are the note's backlinks. A cluster page also draws its members and the links among them. Drafts, retired notes and notes held back from a release never appear in either. No new file is written for this; the drawing is part of the page. Each arrow in a note's drawing has the class of its relation, such as agsc-rel-requires, so your own stylesheet can pick out one relation; the class adds no colour, and the cluster drawings do not carry it. In a diagram you write under content/diagrams/, rel=requires on an arrow, line or text line adds the same class. The three notes above have no typed link yet, so their pages have no Relations section; step 6 adds one.

The /clusters/ page lists the clusters, then shows how they connect: a drawing and a table count the links from the notes of one cluster to the notes of another. Radio buttons above the table show one relation at a time, without JavaScript. A legend below names the fourteen relations and what each means. Last comes an explorer: a picture of every published note and link, with a list beside it. With the keyboard, Tab reaches the list, the arrow keys move through it, Enter selects a note and shows its relations, and Escape clears. The explorer needs JavaScript and reads only /graph.jsonld of the same site; without JavaScript it does not appear, and the rest of the page is unchanged.

The /query/ page lets you ask the graph a question in SPARQL, the query language of RDF. Write a query and select Run (or press Ctrl+Enter): it runs in your browser, against /graph.nq of the same site, and no server takes part. The answer comes as a table; a CONSTRUCT or DESCRIBE query, or any query with three columns, is drawn as a picture too. Two links give the result as CSV and as JSON. The page answers SELECT, ASK, CONSTRUCT and DESCRIBE, and refuses a query that would change the graph or call another server. "Link to this query" gives an address that holds the query after its #: whoever opens it finds the query in the editor, and it runs only when they select Run. Below the editor, the ten questions every graph must answer come with their queries, ready to put in the editor. Each query is filled in with an item of your site, one the question has something to say about where there is one, and the sentence under it names the item and says when the answer is empty; change the item to ask about another. On this guide's three notes, which have no typed links yet, every example answers empty; the query already in the editor lists your notes. A table lists the classes and the fourteen relations with what each means. A site that declares its own questions and vocabulary (the domain object of agsc.config.json) has them listed after these. The page stores nothing, not even your last query. It needs JavaScript; the engine it runs, Oxigraph, is about 4.4 MB and loads only on this page. To leave the page out, set "query_page": false under site in agsc.config.json; the build then writes no /query/ and no link to it.

Search engines and data catalogues find the same files from the home page alone. The JSON-LD block of index.html describes the site as a dataset: its licence, who made it and one download for each graph file, the chunks and the discovery document. The Link header the host sends with / (written into _headers) names the same files and the address to cite. To give the dataset a creator and a licence that names a version, add them to agsc.config.json, for example "bundle": { "creator": { "name": "Josiah Carberry", "orcid": "0000-0002-1825-0097" }, "license_prose": "CC-BY-4.0", "license_url": "https://creativecommons.org/licenses/by/4.0/" } beside the keys bundle already has. license_url names a version of the licence that license_prose names: without license_prose the node's licence is the Content Use Terms, and each chunk would then name those terms beside a CC BY address. A description of content/index.md shorter than 50 characters gets a warning (AGSC-E202): dataset search ignores one that short. The one init wrote is long enough; write your own on the description: line of that file to say what the node holds.

4. Change a note — as a proposal

Give hydration a description. A note's header is plain YAML between two --- lines; this is the whole file after the edit. Before you copy it: the block writes operator: human:unknown, which is what init writes when git has no e-mail. In your own notes, add only the description: line and keep the operator: line init wrote, so that your real id is not overwritten:

cat > content/concepts/hydration.md <<'NOTE'
---
type: concept
title: Hydration
description: The weight of the water in a dough divided by the weight of the flour, as a percentage.
aliases:
  - hydration.md
prov:
  origin: human
  operator: human:unknown
kind: explainer
---

# Hydration

The weight of the water divided by the weight of the flour. Many starters use equal weights of both.
NOTE
agsc lint --fix
agsc propose hydration
wrote: dist/proposal/1.patch
wrote: dist/proposal/1.md
run: git checkout -b proposal/1
run: git add content/concepts/hydration.md && git commit
run: open a pull request with the body of dist/proposal/1.md
propose: pass (0 error, 0 warn)

propose compares your edit with the last commit and writes a patch and a pull-request text; it runs nothing. You run the lines it printed (with a commit message of your own):

git checkout -q -b proposal/1
git add content/concepts/hydration.md && git commit -q -m 'hydration: a description'
git log -1 --format=%s
hydration: a description

On a forge (GitHub, GitLab, …) you push the branch and open the pull request; a person merges it.

5. Before you publish

Three things a public site needs: its real https: address in site.base; the licence text of your notes (by default the Content Use Terms of the package — copy it in, or name another licence in bundle.license_prose); and the history checked:

cp "$ENGINE/LICENSE-CONTENT" .
node -e 'const fs = require("node:fs"), base = "https://notes.example.org/", f = "agsc.config.json", c = JSON.parse(fs.readFileSync(f, "utf8")); c.site.base = base; fs.writeFileSync(f, JSON.stringify(c, null, 2) + "\n"); const i = "content/index.md"; fs.writeFileSync(i, fs.readFileSync(i, "utf8").replace(/^base: .*$/m, "base: " + base));'
git add -A && git commit -q -m 'ready to publish'
agsc ci
agsc build
agsc verify --ledger
ci: pass (0 error, 6 warn)
wrote: 60 files under www/
verify: pass (0 error, 0 warn)

The node -e line sets site.base and the base of the root document content/index.md, which must agree (AGSC-01-04; from 1.1 lint warns when they differ); editing the two by hand does the same. The new warning asks for a PRIVACY.md beside LICENSE-CONTENT, which /legal/ then shows. Upload www/ to any host that serves files over HTTPS; agsc-host list names the profiles the engine can write host settings for, and the publishing guide takes the node from here to a live address and checks it there. The site agsc build writes is a Level 2 node, the Level a published node claims (spec/10); the publishing guide checks it at its address with validate-wellknown --level 2.

6. Link two notes, and draw one

A typed link is a line in a note's header. Say that the starter needs the hydration note, then build:

node -e 'const fs = require("node:fs"), f = "content/concepts/sourdough.md"; fs.writeFileSync(f, fs.readFileSync(f, "utf8").replace("kind: explainer\n", "kind: explainer\nrequires:\n  - hydration\n"));'
agsc build
grep -o '<td>requires</td><td>outgoing</td>' www/concepts/sourdough/index.html
grep -o '<td>requires</td><td>incoming</td>' www/concepts/hydration/index.html
<td>requires</td><td>outgoing</td>
<td>requires</td><td>incoming</td>

The sourdough page now has a Relations section with one outgoing requires row, and the hydration page shows the same link as a backlink. requires is one of the fourteen relations of the data model; the legend on /clusters/ names them all.

A note can also carry a drawing of your own. Write it as a short text file under content/diagrams/, named after the note, and name it in the note's header with a text alternative; the build turns it into an SVG on the note's page. Each line is one shape, and exactly one shape carries acc, the highlighted one:

mkdir -p content/diagrams
cat > content/diagrams/sourdough.diagram <<'DIAGRAM'
label "The starter needs the right hydration"
box starter 40 100 140 50 "starter" acc
box water 280 100 140 50 "hydration"
arrow starter water rel=requires
DIAGRAM
node -e 'const fs = require("node:fs"), f = "content/concepts/sourdough.md"; fs.writeFileSync(f, fs.readFileSync(f, "utf8").replace("kind: explainer\n", "kind: explainer\ndiagram:\n  file: sourdough.svg\n  alt: The starter, which requires the right hydration.\n"));'
agsc build
grep -c 'class="agsc-rel-requires"' www/concepts/sourdough/index.html
2

Two arrows carry the class now: the one in the Relations drawing and the one in yours. The whole language (twelve kinds of line, their options and what each draws) is rule AGSC-01-42 of the specification. When the build refuses a line of a diagram, it says AGSC-E412 with the file and the line; the troubleshooting page lists the usual causes.
